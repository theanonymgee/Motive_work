# --- A. Caddy already runs and serves <VPS_HOST> (approval step D) ---
# Add this block inside the EXISTING site block of that host name. Nothing else changes.
# Caddy keeps the original Host header and adds X-Forwarded-For by default, which is what the
# app's allowed_hosts check expects.
#
#   handle /workmcp/* {
#       request_body {
#           max_size 16MB
#       }
#       reverse_proxy 127.0.0.1:8765 {
#           flush_interval -1
#           transport http {
#               response_header_timeout 300s
#           }
#       }
#   }
#
# Order check (Caddy sorts directives by its own fixed order, not by where you write them): a
# site-level `redir`, `rewrite`, `basic_auth`, `forward_auth`, `header`, `encode` or `request_header`
# of the existing site block runs BEFORE any `handle`, so it would also act on /workmcp/* (a
# `basic_auth` would answer 401 to the bearer client; a `redir` would redirect it). If the existing
# block has any of these at site level, wrap them in their own `handle { ... }` first or ask the owner.
# Among several `handle` blocks the most specific path matcher wins, so `/workmcp/*` beats an existing
# catch-all `handle { ... }` or a shorter prefix. Check with the adapted config (read-only, prints JSON):
#   caddy adapt --config /etc/caddy/Caddyfile --pretty    (the /workmcp/ route must come before the others)
#
# Then:  caddy validate --config /etc/caddy/Caddyfile  &&  sudo systemctl reload caddy
# Rollback: delete the block, validate, reload.
#
