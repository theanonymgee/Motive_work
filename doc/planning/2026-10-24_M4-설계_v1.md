## 2. 데이터 모델

### 2.1 개념

| 개념 | 저장 | 비고 |
|---|---|---|
| 엔티티(사람·프로젝트·고객·조직·용어·기타) + 별칭 | `entities(kind, name, aliases_json, note, created_at, created_by, merged_into)` **[사실]** v1 | `UNIQUE(kind, name)`. 같은 문자열을 자동 병합하지 않는다(G0 §7 **[사실]**: "같은 문자열을 같은 개체로 자동 병합하지 않는다"). `merged_into`는 M4에서 쓰지 않음(M5 `merge_entities`) |
| 사실 | `assertions(kind='fact', entity_id=주어, predicate, object_entity_id=대상?, data_json={value, unit}, valid_from, valid_to, …)` | `value` 또는 `object_entity_id` 중 하나 이상. 예: `(고객A, "담당자", object=사람B)`, `(프로젝트P, "예산", value="3억", unit="원")`, `(용어T, "definition", value="…")` |
| 결정 | `assertions(kind='decision', entity_id?, statement, data_json={options[], chosen, rationale}, valid_from=결정일)` | `predicate`·`object_entity_id` NULL. 충돌 탐지 대상 아님 |
| 할 일 | `assertions(kind='todo', entity_id?, statement, data_json={state, due, owner_entity_id, done_at}, valid_from=만든 날)` | `state ∈ open\|done\|cancelled`. 상태·기한·담당 변경은 **`supersede`**(새 행) — 현재 상태는 체인의 열린 행 |
| 출처 | `evidence(assertion_id, version_id, chunk_id?, locator_json, quote, quote_sha256)` **[사실]** v1 | 행 불변. `source_kind='evidence'`면 1행 이상(`knowledge.py`가 강제, M0 §3.2) |
| 대체·충돌 관계 | `links(from_id, to_id, relation ∈ supersedes\|conflicts, recorded_at, recorded_by, resolved_at, resolved_by_id)` **[사실]** v1 | M4는 `supersedes`·`conflicts`만 쓴다(`supports`·`contradicts`·`relates`는 예약) |
| 상태 변화 이력 | **새** `assertion_events(assertion_id, at, kind, reason, related_id, recorded_by, call_id)` | 기록·철회·대체·충돌 표시·충돌 해소가 각각 한 행 |

- **[사실]** 현재 `assertions`의 상태 열 변경은 v1 트리거가 다음만 허용한다(`store.py` 119~141행, 테스트 `test_store_schema.py` 109~220행): 열린 행(`active`/`conflict`, `recorded_to IS NULL`)에서 `active↔conflict`, `active/conflict → withdrawn/superseded`(+`recorded_to`), `change_reason` 1회 설정; 내용 열·`supersedes_id`·id 변경, DELETE, 기존 id INSERT(REPLACE 우회)는 거부. M4는 **이 규칙 안에서만** UPDATE를 쓴다(정확히 두 종류: 닫기, 충돌 표시/해제).
- **[결정]** "상태 변화도 새 행"의 해석: 행의 닫힘(`recorded_to`)은 bitemporal 조회가 요구하는 최소 변경이고 v1 트리거가 한 번만 허용한다. 그 밖의 모든 변화(사유·행위자·시각·상대)는 `assertion_events`의 **새 행**이며, 할 일의 상태 변화는 `supersede`로 **새 assertion 행**이다. 내용은 어떤 경로로도 바뀌지 않는다.

### 2.2 `data_json` 확정 (M0 §3.2 [제안] → 결정)

```json
fact:     {"value": "3억" | null, "unit": "원" | null}
decision: {"options": ["A", "B"], "chosen": "A" | null, "rationale": "…" | null}
todo:     {"state": "open" | "done" | "cancelled", "due": "2026-11-30" | null,
           "owner_entity_id": 12 | null, "done_at": "2026-11-20" | null}
```

- 직렬화는 `json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(',', ':'))`(결정적 — 충돌 비교·테스트 비교에 쓰임). 모르는 키는 `argument_invalid`.
- 문자열 상한: `statement` ≤ 1,000자, `value` ≤ 1,000, `unit` ≤ 50, `predicate` 1~100, `options` ≤ 20개 × 200자, `chosen`·`rationale` ≤ 1,000, `reason` 1~500, `name` 1~200, `aliases` ≤ 20개 × 100자, `note` ≤ 1,000. 모두 NFC 정규화 + 양끝 공백 제거 후 길이를 잰다; 제어 문자(`[\x00-\x1f\x7f-\x9f]`, 탭·줄바꿈 제외)는 `argument_invalid`.
- 날짜(`valid_from`, `valid_to`, `due`, `done_at`, `decided_on`): `YYYY-MM-DD`만(`date.fromisoformat` 통과, 길이 10). `valid_to`가 있으면 `valid_from < valid_to`. 시각이 아닌 **날짜**인 이유: 업무상 적용 기간은 날짜 단위이고 문자열 비교가 순서와 같다(M0 부록 B L-13).

### 2.3 마이그레이션 v3 (`store.MIGRATIONS`에 **추가**, v1·v2 불변)

- **[사실]** `store.migrate`는 최신이면 읽기만으로 돌아오고, 필요할 때만 `BEGIN IMMEDIATE`로 적용한다(M3 검토 v2 N1). 
- **[사실]**(설계자 탐침 2026-10-25, 이 PC Python 3.12.13·SQLite 3.53.1, `store.open_home`으로 만든 v1+v2 저장소에 아래 DDL 22문을 `store.statements`로 적용) 전부 적용됨; `ALTER TABLE … ADD COLUMN … REFERENCES entities(id)`는 `foreign_keys=ON`에서 통과하고 없는 엔티티 id는 `FOREIGN KEY constraint failed`로 거부됨; 거부 사례 15종(predicate 없는 fact, entity 없는 fact, predicate 있는 todo, 날짜 형식·`valid_to == valid_from`, `predicate`/`object_entity_id` UPDATE, 엔티티 rename·DELETE·`(kind,name)` REPLACE, 링크 해소 되돌림·DELETE, 이벤트 UPDATE·DELETE)이 모두 거부되고 허용 사례 5종(fact 삽입, 주어 없는 decision, v1 상태 전이 `active→conflict`, 엔티티 `aliases_json`·`note` UPDATE, 링크 `resolved_at` 1회)이 통과함. 겹침 질의(§4.4)도 기대 행을 냄. 탐침 스크립트는 scratchpad에만 두고 저장소에 넣지 않았다(실행자가 `test_store_schema.py`로 같은 사례를 고정한다).
- **[결정]** DDL(`(3, 'knowledge_v3', SCHEMA_V3)`; 정확한 기준은 구현 뒤의 `store.py`):

```sql
-- 사실의 속성/관계와 대상 엔티티 (기존 행은 NULL; M4 이전 행은 없다)
ALTER TABLE assertions ADD COLUMN predicate TEXT;
ALTER TABLE assertions ADD COLUMN object_entity_id INTEGER REFERENCES entities(id);
CREATE INDEX assertions_subject ON assertions(entity_id, kind, predicate);   -- 충돌 탐지·엔티티 상세
CREATE INDEX assertions_object ON assertions(object_entity_id);              -- 관계 역조회
CREATE INDEX assertions_supersedes ON assertions(supersedes_id);             -- 이력 체인 앞으로 따라가기
-- v1 update_guard는 새 열을 모른다: 같은 규칙(내용은 불변)을 새 열에 적용
CREATE TRIGGER assertions_v3_update_guard BEFORE UPDATE ON assertions
  WHEN NEW.predicate IS NOT OLD.predicate OR NEW.object_entity_id IS NOT OLD.object_entity_id
  BEGIN SELECT RAISE(ABORT, 'assertion content is append-only'); END;
-- 날짜 형식과 순서(M0 부록 B L-13). 종결 시각 비교(recorded_to >= recorded_from)는 v1 트리거 그대로
CREATE TRIGGER assertions_v3_dates BEFORE INSERT ON assertions
  WHEN (NEW.valid_from IS NOT NULL AND NEW.valid_from NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]')
    OR (NEW.valid_to IS NOT NULL AND NEW.valid_to NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]')
    OR (NEW.valid_from IS NOT NULL AND NEW.valid_to IS NOT NULL AND NEW.valid_to <= NEW.valid_from)
  BEGIN SELECT RAISE(ABORT, 'valid_from/valid_to must be YYYY-MM-DD and valid_from < valid_to'); END;
-- 사실은 주어가 필수(결정·할 일은 선택), 할 일·결정은 predicate 없음
CREATE TRIGGER assertions_v3_shape BEFORE INSERT ON assertions
  WHEN (NEW.kind = 'fact' AND (NEW.entity_id IS NULL OR NEW.predicate IS NULL))
    OR (NEW.kind IN ('decision', 'todo') AND (NEW.predicate IS NOT NULL OR NEW.object_entity_id IS NOT NULL))
  BEGIN SELECT RAISE(ABORT, 'assertion shape: fact needs entity_id and predicate; decision/todo have neither'); END;

-- 엔티티: 정체(kind·name·created_*)는 불변, aliases_json·note는 갱신 가능(별칭 추가), merged_into는 한 번(M5)
CREATE TRIGGER entities_update_guard BEFORE UPDATE ON entities
  WHEN NEW.id <> OLD.id OR NEW.kind <> OLD.kind OR NEW.name <> OLD.name OR NEW.created_at <> OLD.created_at
    OR NEW.created_by <> OLD.created_by OR (OLD.merged_into IS NOT NULL AND NEW.merged_into IS NOT OLD.merged_into)
  BEGIN SELECT RAISE(ABORT, 'entity identity is append-only'); END;
CREATE TRIGGER entities_no_delete BEFORE DELETE ON entities BEGIN SELECT RAISE(ABORT, 'append-only'); END;
CREATE TRIGGER entities_no_replace BEFORE INSERT ON entities
  WHEN EXISTS(SELECT 1 FROM entities WHERE id = NEW.id) BEGIN SELECT RAISE(ABORT, 'append-only'); END;
CREATE TRIGGER entities_no_replace_name BEFORE INSERT ON entities          -- 두 번째 고유 키(kind, name)도 막는다
  WHEN EXISTS(SELECT 1 FROM entities WHERE kind = NEW.kind AND name = NEW.name) BEGIN SELECT RAISE(ABORT, 'append-only'); END;

-- 관계·충돌 링크: 내용 불변, resolved_at/resolved_by_id는 NULL→값 한 번(M0 §3.2 [제안] links_no_delete 채택)
CREATE INDEX links_from ON links(from_id, relation);
CREATE INDEX links_to ON links(to_id, relation);
CREATE TRIGGER links_update_guard BEFORE UPDATE ON links
  WHEN NEW.id <> OLD.id OR NEW.from_id <> OLD.from_id OR NEW.to_id <> OLD.to_id OR NEW.relation <> OLD.relation
    OR NEW.note IS NOT OLD.note OR NEW.recorded_at <> OLD.recorded_at OR NEW.recorded_by <> OLD.recorded_by
    OR (OLD.resolved_at IS NOT NULL AND (NEW.resolved_at IS NOT OLD.resolved_at OR NEW.resolved_by_id IS NOT OLD.resolved_by_id))
    OR (NEW.resolved_at IS NULL AND NEW.resolved_by_id IS NOT NULL)
  BEGIN SELECT RAISE(ABORT, 'link is append-only'); END;
CREATE TRIGGER links_no_delete BEFORE DELETE ON links BEGIN SELECT RAISE(ABORT, 'append-only'); END;
CREATE TRIGGER links_no_replace BEFORE INSERT ON links
  WHEN EXISTS(SELECT 1 FROM links WHERE id = NEW.id) BEGIN SELECT RAISE(ABORT, 'append-only'); END;

-- 상태 변화 이력: 사유·행위자·상대·시각. 추가 전용
CREATE TABLE assertion_events(id INTEGER PRIMARY KEY,
  assertion_id INTEGER NOT NULL REFERENCES assertions(id),
  at TEXT NOT NULL,
  kind TEXT NOT NULL CHECK(kind IN ('recorded','retracted','superseded','conflict_marked','conflict_cleared')),
  reason TEXT,                                   -- retracted·superseded: 필수(knowledge.py가 강제)
  related_id INTEGER REFERENCES assertions(id),  -- superseded: 새 행, conflict_*: 상대 행, recorded: supersedes_id
  recorded_by TEXT NOT NULL,                     -- "<client>/<tool>"
  call_id TEXT);                                 -- tool_calls.call_id(감사 대조용; 외래 키 없음 — 기록이 대기열에 있을 수 있음)
CREATE INDEX assertion_events_assertion ON assertion_events(assertion_id, id);
CREATE TRIGGER assertion_events_no_update BEFORE UPDATE ON assertion_events BEGIN SELECT RAISE(ABORT, 'append-only'); END;
CREATE TRIGGER assertion_events_no_delete BEFORE DELETE ON assertion_events BEGIN SELECT RAISE(ABORT, 'append-only'); END;
CREATE TRIGGER assertion_events_no_replace BEFORE INSERT ON assertion_events
  WHEN EXISTS(SELECT 1 FROM assertion_events WHERE id = NEW.id) BEGIN SELECT RAISE(ABORT, 'append-only'); END;
```

- `status.schema_version`은 3(기존 단언 4곳 갱신: `test_e2e.py` 157, `test_network_boundary.py` 935, `test_store_schema.py` 328, `test_tools.py` 128 **[사실]**).
- `evidence`는 열 추가 없음. `recorded_from/to`는 `store.now()` 형식 유지(로컬 오프셋 ISO); 비교는 SQL `julianday()`(`document_events_query`가 이미 그렇게 한다 **[사실]** `store.py` 759~762행). v1 트리거의 `recorded_to < recorded_from` 문자열 비교는 같은 오프셋에서만 정확하다 — 한계로 §14.

## 3. 출처 결속 (완료 조건 ③)

### 3.1 입력

```json
"sources": [{"chunk_id": 139, "quote": "…"}, {"locator": {…M0 §3.3 전체 형식…}, "quote": "…"}]   // 1~5개
"my_note": true                                                                                  // 또는
```

- **[결정]** `sources`와 `my_note` 중 **정확히 하나**. 둘 다/둘 다 아님 → `evidence_required`. `sources`가 빈 목록이면 같은 오류. 항목마다 `chunk_id`·`locator` 중 정확히 하나(둘 다/둘 다 아님 → `argument_invalid`). `quote`는 문자열, 정규화 뒤 2~1,000자(`quote_empty`/`argument_invalid`).
- 같은 쓰기에 같은 단위·같은 범위가 두 번 오면 하나로 합친다(notice 없이).

### 3.2 재도출 절차 (`knowledge.bind_sources(db, sources) -> list[Bound]`)

각 항목에 대해, 순서대로:

1. **대상 단위 찾기**
   - `chunk_id`: `chunks` 행 → `version_id`, `unit_first..unit_last` → 그 범위의 `units(ordinal, locator_json, text)`. 행이 없으면 **`chunk_not_found`**(메시지에 `tools.CHUNK_GONE_HINT`와 같은 안내 "다시 검색하거나 hit의 locator로 주세요" — M2 부록 C 항목 처리). 청크 범위(`char_start/end`)가 아니라 **그 단위들의 전체 텍스트**를 대상으로 한다(locator는 단위 기준이므로 범위 밖도 정확한 출처다).
   - `locator`: `locator.check_shape` → `versions(document_id=doc, sha256)` 최신 행 → `units(version_id, locator_json = parsers.unit_json(unit))`(= `binding.validate_locator`의 조회 **[사실]** 256~267행). 모양 오류 `locator_invalid`, 버전·단위 없음 `not_found`. 대상은 **그 단위 하나**.
2. **인용 정규화**: `q = unicodedata.normalize('NFC', quote).strip()`. 단위 텍스트는 저장된 그대로(파서 출력; 정규화하지 않는다 — 오프셋이 원문 좌표여야 한다).
3. **위치 찾기** (단위마다):
   - (a) 정확 일치: `text.find(q)`의 **모든** 위치(겹치지 않게 반복).
   - (b) (a)가 0건이면 공백 유연 일치: `pattern = r'\s+'.join(re.escape(part) for part in q.split())`로 `re.finditer(pattern, text)` — 줄바꿈·연속 공백·탭 차이만 흡수한다. 문자 자체(따옴표 종류·전각/반각·하이픈)는 바꾸지 않는다.
   - (c) 그래도 0건이면 NFC 안 한 원래 `quote.strip()`으로 (a)·(b) 한 번 더(원문이 NFD인 드문 경우).
   - 후보가 **정확히 1개**: 채택. **0개**: `evidence_quote_not_found`(메시지: 단위 라벨·인용 글자 수만, 본문 없음). **2개 이상**: 클라이언트의 `locator.chars`가 후보 중 하나와 정확히 같으면 그것을 채택, 아니면 `evidence_quote_ambiguous`(메시지에 후보 수와 "chars로 한 곳을 지정하세요" — M0 L-11). `chunk_id` 입력에서 여러 단위에 걸쳐 후보가 1개씩 있어도 모호.
4. **저장 locator**: `locator.make(doc_id, path, sha256, unit, unit_text, [start, end])` — `text_sha256`은 여기서 계산되고 `check_text`가 통과한다. **클라이언트가 보낸 `chars`·`text_sha256`은 저장되지 않는다.**
5. **저장 quote** = `unit_text[start:end]`(서버가 자른 원문; 공백 유연 일치면 클라이언트 문자열과 공백이 다를 수 있다), `quote_sha256 = sha256(quote)`, `version_id`, `chunk_id`(힌트, 외래 키 없음 **[사실]**).
6. 단위가 두 개에 걸친 인용(문단 경계)은 1단계 대상 밖이라 (0건)으로 거부된다 → notice 문구에 "단위(문단·줄·셀) 하나 안의 인용만 결속됩니다; 두 단위면 sources 두 개로".

- **[결정]** 옛 버전(`versions.superseded_at IS NOT NULL`)이나 삭제 문서의 단위도 **허용**(그 시점의 근거, M0 §4.3) — 응답 notice "출처 n건이 옛 버전(seq k) 또는 삭제 문서의 것입니다"와 `evidence[].source_state`로 보인다.
- 결속의 정확성은 `binding.verify`가 이미 `evidence`를 검사한다 **[사실]**(`evidence:evidence_quote_mismatch` 등). M4 뒤 `workmcp verify`의 `evidence N`이 0이 아니게 된다 — ⑥ 증거.

### 3.3 출처 없는 쓰기

- `my_note: true` → `source_kind='my_note'`, `evidence` 0행. 모든 조회·쓰기 응답의 assertion에 `source_kind`와 사람이 읽는 `source_label`("내 메모" / "근거 n건")이 함께 간다. `list_knowledge`·`get_entity`에 `source_kind` 필터(`evidence|my_note|all`).
- 저장 뒤에 출처를 "붙이는" 도구는 없다: 출처를 더하려면 `supersede`(같은 내용 + `sources`)로 새 행을 만든다(이력이 남는다).

### 3.4 저장된 출처의 상태(원문이 바뀌거나 삭제됐을 때)

- `evidence` 행은 불변이고 특정 **버전**을 가리킨다. 조회 때 계산:

| `source_state` | 조건(SQL 조인) | 뜻 |
|---|---|---|
| `current` | `versions.superseded_at IS NULL AND documents.status = 'active'` | 인용한 버전이 지금 파일 |
| `changed` | `versions.superseded_at IS NOT NULL AND documents.status <> 'deleted'` | 파일이 그 뒤 바뀜(옛 버전 인용) |
| `deleted` | `documents.status = 'deleted'` | 파일이 사라짐 |
| `skipped` | `documents.status = 'skipped'` | 클라우드 자리표시자 등으로 건너뜀(M1) |

- `get_history`·`get_entity`(상세)에서는 `changed`인 항목에 **`requote`**를 더한다: 최신 버전(`superseded_at IS NULL`)에 같은 `locator_json`의 단위가 있고 그 텍스트에 `quote`가 정확히 1곳 있으면 `{"found": true, "locator": <최신 버전 locator>}`, 아니면 `{"found": false}`. 단위 조회 1회·`find` 1회라 싸다. `requote.locator`는 **제안**일 뿐 저장되지 않는다 — 클라이언트가 그 locator로 `supersede`하면 새 근거가 된다.
- `list_knowledge`는 assertion마다 `source_state`의 **최악값**만(`deleted > changed > skipped > current`) 준다(조인 1회, 인용 없음).
- 서버 재확인 명령: `workmcp verify`가 현재 파일과 같은 버전의 evidence를 재검사(`evidence_checked`); 옛 버전 근거는 `stale`로 센다 **[사실]** `binding.py` 86~95행.

## 4. 철회·대체·충돌 (완료 조건 ④)

### 4.1 공통

- 모든 쓰기 도구는 **한 트랜잭션**(`BEGIN IMMEDIATE … COMMIT`, §8.2). 중간 실패(트리거 거부·결속 실패·제약 위반)는 ROLLBACK → 아무것도 안 남는다. 결속(§3.2)은 트랜잭션 **안**에서 한다(단위 읽기와 evidence INSERT 사이에 scan이 끼어들어도 같은 스냅샷).
- 쓰기 순서(사실 기록의 예): `INSERT assertions` → `INSERT evidence×n` → 충돌 탐지(§4.4) → `UPDATE status='conflict'`(해당 시) → `INSERT links` → `INSERT assertion_events('recorded', related_id=supersedes_id)` → COMMIT.
- 시각: `recorded_from = store.now()` 한 번 받아 같은 트랜잭션의 모든 행(`recorded_to`, `links.recorded_at`, `assertion_events.at`)에 같은 값을 쓴다(한 사건 = 한 시각; 시점 질의에서 같은 순간에 닫힘과 열림이 일관됨).

### 4.2 철회 `retract(assertion_id, reason)`

1. 행이 없으면 `assertion_not_found`; `status IN ('withdrawn','superseded')`면 `already_closed`(메시지에 `recorded_to`·닫힌 이유의 종류).
2. `UPDATE assertions SET status='withdrawn', recorded_to=:now, change_reason=:reason WHERE id=:id AND recorded_to IS NULL`(v1 트리거 허용 경로; `change_reason`은 여기서 **처음** 설정된다 — 충돌 표시는 이 열을 쓰지 않으므로 N-L11 해결).
3. `INSERT assertion_events(kind='retracted', reason, recorded_by, call_id)`.
4. 충돌 해소(§4.5): 이 행의 열린 `conflicts` 링크에 `resolved_at=:now, resolved_by_id=:id`; 상대 행이 다른 열린 충돌이 없으면 `conflict→active` + `assertion_events('conflict_cleared', related_id=이 행)`.
5. 응답: 닫힌 행 요약 + `cleared_conflicts: [ids]`.

### 4.3 대체 `supersede(assertion_id, 새 내용…, reason, sources|my_note, old_valid_to?)`

- 새 내용 인자는 kind별 `record_*` 인자의 **부분집합**(모두 선택; 주지 않은 것은 옛 행에서 복사). `kind`는 바꿀 수 없다(옛 행의 kind와 맞지 않는 인자, 예: todo에 `predicate` → `kind_mismatch`). `entity_id`는 바꿀 수 있다(잘못 붙인 주어 교정).
- 절차(한 트랜잭션):
  1. 옛 행 확인(§4.2 1과 같은 오류).
  2. `old_valid_to`가 있으면(L-13 "유효 기간 끊기"): **중간 행 C** = 옛 행 내용 그대로 + `valid_to=old_valid_to`(옛 `valid_from < old_valid_to` 검사), `supersedes_id=old`, `source_kind`·`evidence`는 옛 행의 것을 **복사**(같은 locator·quote; 서버가 `binding.validate_locator`로 다시 검사 — 저장된 단위 기준이므로 항상 통과), `recorded_by`는 이번 호출. 새 행 N의 `valid_from` 기본값은 `old_valid_to`.
  3. 새 행 N: `INSERT assertions(kind=old.kind, supersedes_id = C.id 또는 old, …)` + `evidence`(§3.2 결속) — `sources|my_note`는 **항상 필요**(옛 근거를 물려받지 않는다; 체인에서 보인다).
  4. 옛 행(그리고 C는 N이 바로 대체하므로 같은 시각에 열고 닫힘: `recorded_from = recorded_to = now` — v1 트리거는 `recorded_to >= recorded_from`을 허용 **[사실]** 테스트 208~219행): `UPDATE … status='superseded', recorded_to=:now, change_reason=:reason`.
  5. `links(from=N, to=old, relation='supersedes')`(C가 있으면 `C→old`, `N→C` 두 개), `assertion_events`: old `superseded(related=N, reason)`, (C `recorded`+`superseded`), N `recorded(related=supersedes_id)`.
  6. 충돌: old(및 C)의 열린 충돌 링크 해소(§4.5) → N에 대해 충돌 탐지(§4.4; old·C는 닫혔으므로 대상 아님).
- 응답: `old`, `cut`(C 또는 null), `new`(evidence 포함), `conflicts[]`, `cleared_conflicts[]`.
- **[결정]** `supersede`의 의미는 **기록 교정**이다: 옛 행은 모든 유효 시점에서 현재 지식에서 빠진다(`as_of_recorded`를 과거로 주면 보인다). "값이 D부터 바뀌었다(그 전엔 옛 값이 맞다)"는 `old_valid_to=D`로 적는다. 이 구분을 도구 docstring에 한 문장으로 넣는다.
- 할 일 상태 변경 = `supersede(id, state='done', done_at='…', reason='완료', my_note=true)`. `complete_todo` 같은 전용 도구는 두지 않는다.

### 4.4 충돌 정의와 탐지

- **[결정]** 두 행 a·b가 **충돌**: `a.kind = b.kind = 'fact'`, `a.entity_id = b.entity_id`, `a.predicate = b.predicate`, 둘 다 열림(`recorded_to IS NULL`), 유효 기간이 겹치고(`COALESCE(a.valid_from,'0000-00-00') < COALESCE(b.valid_to,'9999-12-31') AND COALESCE(b.valid_from,'0000-00-00') < COALESCE(a.valid_to,'9999-12-31')`), 값이 다름(`value_key`가 다름). `value_key = (NFC+strip한 value 또는 '', unit 또는 '', object_entity_id 또는 0)`의 정확 비교.
- 값이 **같고** 기간이 겹치면 충돌이 아니라 **중복**: 저장은 하되 응답 `duplicates: [ids]` + notice "같은 사실이 이미 있습니다(id …) — 출처를 더하려는 것이면 괜찮습니다".
- 결정·할 일·`predicate`가 다른 사실은 충돌 탐지 대상이 아니다. `"담당"`과 `"담당자"`는 다른 predicate다(동의어 처리 없음 — `get_entity.predicates_in_use`로 클라이언트가 맞춘다; 한계 §14).
- 탐지 SQL(새 행 N 삽입 뒤, 같은 트랜잭션):

```sql
SELECT id FROM assertions WHERE kind='fact' AND entity_id=:e AND predicate=:p AND recorded_to IS NULL AND id<>:new
  AND COALESCE(valid_from,'0000-00-00') < :new_to AND :new_from < COALESCE(valid_to,'9999-12-31')
```
  결과를 Python에서 `value_key`로 나눈다(같음 → duplicates, 다름 → conflicts). 충돌마다: `UPDATE assertions SET status='conflict' WHERE id IN (:new, :other) AND status='active'`(이미 `conflict`면 그대로), `INSERT links(from=:new, to=:other, 'conflicts')`, `assertion_events('conflict_marked', related_id=상대)` 두 행.
- G0 §8 **[사실]** "상충하는 주장에 대해 단순 최신 우선으로 한쪽을 삭제하지 않는다" — 자동 해소 없음. 사람이 `retract`/`supersede`로 푼다.

### 4.5 충돌 해소 규칙

- 행 X가 닫힐 때(철회·대체): `UPDATE links SET resolved_at=:now, resolved_by_id=:closer WHERE relation='conflicts' AND resolved_at IS NULL AND (from_id=X OR to_id=X)`(`closer` = 철회면 X, 대체면 새 행 N). 상대 행 Y마다: `Y`에 다른 열린 `conflicts` 링크가 없으면 `UPDATE assertions SET status='active' WHERE id=Y AND status='conflict'` + `assertion_events(Y, 'conflict_cleared', related_id=X)`.
- 조회 표시: assertion마다 `conflicts: [{id, value, valid_from, valid_to, recorded_from}]`(열린 링크의 상대). `as_of_recorded`가 과거면 그 시점에 열려 있던 링크(`recorded_at <= R AND (resolved_at IS NULL OR R < resolved_at)`)로 계산한다.

## 5. 시점 질의

### 5.1 두 축의 SQL 의미 (`knowledge_query.visible_sql(valid_at, recorded_at, include_closed)`)

| 축 | 인자 | 기본 | WHERE 조각 | 뜻 |
|---|---|---|---|---|
| 기록 시점 | `as_of_recorded` (ISO 8601 시각; `search._instant`와 같은 검사·정규화 **[사실]**) | **지금** | `julianday(recorded_from) <= julianday(:R) AND (recorded_to IS NULL OR julianday(:R) < julianday(recorded_to))` | 그때 기록이 알고 있던 것(철회·대체되기 전 행이 보인다; 그 뒤 기록된 행은 안 보인다) |
| 유효 시점 | `as_of_valid` (`YYYY-MM-DD`) | **없음**(모든 기간) | `(valid_from IS NULL OR valid_from <= :T) AND (valid_to IS NULL OR :T < valid_to)` | 그때 사실이었던 것(기간이 없는 행은 항상 해당) |

- **[결정]** 기본값: 기록 축은 지금(현재 지식), 유효 축은 **거르지 않음** — 엔티티 상세에서 과거·미래 기간의 사실도 각자의 날짜와 함께 보이는 쪽이 덜 놀랍고, "지금 유효한 것만"은 `as_of_valid=오늘`을 주면 된다(M0 §3.2의 "기본 valid_at=now"를 바꿈 — 이유: 기간이 끝난 사실이 조용히 사라지면 클라이언트가 "정보 없음"으로 오해한다).
- `include_closed=true`면 기록 축 조건을 `julianday(recorded_from) <= julianday(:R)`로 바꾼다(R까지 기록된 모든 행, 닫힌 것 포함; `status_as_of`로 구분).
- `status_as_of`(응답 필드): R에 열려 있었으면 `open`(그 시점 충돌 여부는 §4.5 링크로 `conflicts_as_of`), R 전에 닫혔으면 저장된 `status`(`withdrawn`/`superseded`).
- 두 축을 함께 주면 AND. 예: "9월 10일에 우리가 알던 바로, 9월 1일 기준 계약 금액" = `as_of_recorded='2026-09-10T23:59:59+09:00', as_of_valid='2026-09-01'`(G0 §8의 예 **[사실]**).
- `supersede(old_valid_to=D)` 뒤: 현재 지식(`R=지금`)에서 `T<D`는 C(옛 값), `T>=D`는 N(새 값); `R`을 대체 전으로 주면 옛 행 하나.

### 5.2 이력 `get_history(assertion_id)`

- 체인: `supersedes_id`를 거슬러 뿌리까지, `assertions_supersedes` 색인으로 앞으로(대체한 행)까지 — 분기는 없다(한 행을 두 번 대체할 수 없음: 두 번째 `supersede`는 `already_closed`). 최대 50행(넘으면 `truncated: true`, 최신 쪽 50).
- 행마다: 요약 + `evidence[] {id, locator, quote, source_state, requote?}` + `events[]`(그 행의 `assertion_events`) + `links[]`(대체·충돌, 해소 포함).
- 시점 인자 없음(이력은 전부).

## 7. `delivered_sources`·호출 기록·기록자

### 7.1 조각 규칙 확장

- **[결정]** `tools.pieces_of(envelope)`를 **재귀 탐색**으로 바꾼다: 결과 트리의 어떤 dict가 `locator` 키와 함께 `snippet`·`text`·`quote` 중 **정확히 하나**를 문자열로 가지면 조각이다(순서는 JSON 순서: dict 키 순 → 리스트 순). 기존 `search`·`get_snippet` 결과는 같은 결과를 낸다(테스트로 고정: 옛 구현과 새 구현의 출력이 M3 응답 전부에서 같음). `units[]`(`unit, chars, text_sha256`)는 `locator` 키가 없어 조각이 아니다; `requote.locator`는 `quote` 없이 locator만이라 조각이 아니다.
- `delivered_sources`·`deliveries` 행·`tool_calls.pieces/chars`는 이 함수에서 나온다 — 쓰기 도구도 **같은 경로**(`server.handle` 공통)라 별도 규칙이 없다.
- 쓰기 응답이 인용을 되돌려 주는 이유: 서버가 재도출한 **저장된** 인용(공백이 다를 수 있음)을 클라이언트가 확인하고, 규칙 1("본문이 실리면 목록에")을 예외 없이 지킨다. 대가: `deliveries`에 쓰기 호출의 조각도 행으로 남는다(사실상 클라이언트가 방금 보낸 텍스트 — 허용; 투명성 쪽이 낫다).

## 8. 안전

### 8.1 원본 파일

- 쓰기 도구는 파일 시스템을 **전혀** 열지 않는다: 결속은 `units.text`(저장된 원문)로만 한다. `knowledge.py`·`knowledge_query.py`를 `tests/test_readonly.py::READONLY_MODULES`에 추가(`open()`·쓰기 API 정적 검사 0건 **[사실]** 현재 목록 `collect.py, binding.py, parsers`).
- serve 감사(§10)가 `ROOT`를 받아 쓰기 도구 호출 중 `source_opens == 0`과 쓰기 모드 open 0을 잰다(기존 hook이 `open`의 mode/flags를 판정 **[사실]** `_audited_server.py` 153~176행).

### 8.2 DB 쓰기와 잠금

- **[사실]** M3: 호출 기록 연결 `write_db`는 `busy_timeout` 200 ms, 못 쓰면 메모리 대기열(잃을 수 있음). 지식 쓰기는 잃으면 안 된다.
- **[결정]** `ServerState.know_db`: 프로세스당 **두 번째 쓰기 연결**(`store.connect(db_path)` — 마이그레이션은 이미 `write_db`가 했으므로 읽기 판정으로 바로 통과 **[사실]** `migrate` 290행), `PRAGMA busy_timeout=5000`(`server.KNOWLEDGE_BUSY_MS`). 호출 기록 연결과 분리한 이유: busy 정책이 다르고(200 ms vs 5 s), 한 연결에서 PRAGMA를 호출마다 바꾸지 않기 위해. 도구는 직렬(`async def`)이라 두 연결이 같은 프로세스에서 동시에 트랜잭션을 열 일은 없다.
- 트랜잭션: `know_db.execute('BEGIN IMMEDIATE')` → 모든 읽기(단위·옛 행)와 쓰기 → `COMMIT`. `BEGIN IMMEDIATE`가 `sqlite3.OperationalError`('locked'/'busy', 5초 뒤)면 **아무것도 쓰지 않은 상태**로 `store_busy`(`retryable: true`); `tool_calls`에는 오류 코드로 남는다. COMMIT 단계의 busy(드묾)는 같은 오류이고 SQLite가 롤백한다 — 결과 불확실 재시도 금지 원칙(G0 `outcome_unknown` 개념, M0 §6 #13)은 여기선 필요 없다: COMMIT 실패 = 미기록이 확정이다(SQLite는 COMMIT이 busy면 트랜잭션을 유지하고 오류를 돌려주므로 우리는 즉시 ROLLBACK한다).
- 두 serve 프로세스: `BEGIN IMMEDIATE`가 RESERVED 잠금을 잡으므로 충돌 탐지 SELECT와 INSERT 사이에 다른 프로세스가 끼어들 수 없다(충돌을 놓치는 경합 없음). 두 프로세스가 같은 `(kind, name)` 엔티티를 동시에 만들면 둘째는 UNIQUE 위반 대신 `entities_no_replace_name` 트리거/제약 오류 → `knowledge.py`가 잡아 **다시 조회**해 `created:false`로 돌려준다(한 트랜잭션 안에서 "SELECT 없으면 INSERT"를 하므로 실제로는 둘째가 SELECT에서 찾는다).
- `scan`/`index`와의 경합: 그쪽은 `scan.lock`·`index.lock`을 잡지만 serve는 잡지 않는다(M3 §7). scan의 긴 트랜잭션(200파일 단위 commit, M0 §5) 동안 지식 쓰기는 ≤ 5 s 대기 후 `store_busy`. `data_generation`은 건드리지 않는다(청크가 바뀌지 않음).
- 읽기 도구는 `store.open_read`(`mode=ro`, 마이그레이션 없음 **[사실]**).

### 8.3 입력 위생

- 모든 문자열 NFC + strip, 제어 문자 거부, 상한(§2.2). 숫자는 `StrictInt`(SDK 층)와 `_int_in`(우리 층) 둘 다. 날짜는 `date.fromisoformat` + 길이 10. `sources`는 리스트·각 항목 dict·키 집합 검사. `data_json`의 모르는 키 없음(서버가 만든다).
- 오류 메시지에 클라이언트가 보낸 **본문**(문장·값·인용)은 넣지 않는다(길이·번호·라벨만) — M3 §8.2 유지.

- **승인이 필요한 항목: 없음.** 새 의존성·외부 호출·전역 설정 변경·지출·회사 자료 사용이 없다. 범위는 PLAN §4 M4 완료 조건 안이다.
- **정보 공유(답 불필요)**: ① ⑥ 확인을 위해 Code 탭 세션을 새로 열거나 `/mcp`에서 workmcp를 재연결해야 한다(서버 코드가 바뀌면 떠 있는 서버는 옛 코드). ② 시험 홈 DB에 합성 지식 행(엔티티·사실·이벤트)이 남는다 — 합성 자료뿐이며 M5 전 정리는 피터 판단.
- **총괄 결정 요청(설계 안에서 고를 수 있는 것, 기본값 제시)**: (a) `as_of_valid` 기본 "거르지 않음"(§5.1) — M0의 "오늘"에서 바꿨다; (b) 쓰기 응답이 저장된 인용을 되돌려 주고 `delivered_sources`·`deliveries`에 넣는다(§7.1); (c) `supersede`의 `old_valid_to` 중간 행(§4.3). 셋 다 기본대로 가면 질문 없이 진행.

## 부록 A. `knowledge.record` 의사코드 (A 구현 기준)

```python
def record(db, kind, *, recorded_by, call_id, sources=None, my_note=False, **fields):
    spec = normalise(kind, fields)                     # NFC·strip·상한·날짜·data_json (argument_invalid)
    if bool(sources) == bool(my_note): raise KnowledgeError('evidence_required', ...)
    try:
        db.execute('BEGIN IMMEDIATE')                  # OperationalError(locked/busy) -> store_busy, retryable
    except sqlite3.OperationalError as exc: raise KnowledgeError('store_busy', ..., retryable=True) from exc
    try:
        now = store.now()
        require_entities(db, spec)                     # entity_id / object_entity_id / owner_entity_id (entity_not_found)
        bound = bind_sources(db, sources) if sources else []   # §3.2 (quote_not_found/ambiguous/chunk_not_found/...)
        new_id = insert_assertion(db, kind, spec, now, recorded_by, source_kind='evidence' if bound else 'my_note')
        insert_evidence(db, new_id, bound)
        conflicts, duplicates = detect_conflicts(db, new_id, spec, now, recorded_by, call_id) if kind == 'fact' else ([], [])
        add_event(db, new_id, now, 'recorded', None, spec.get('supersedes_id'), recorded_by, call_id)
        db.execute('COMMIT')
    except BaseException:
        db.execute('ROLLBACK'); raise
    return {'assertion': knowledge_query.assertion_row(db, new_id, with_evidence=True),
            'conflicts': conflicts, 'duplicates': duplicates, 'notice': notices(bound, conflicts, duplicates)}
```
