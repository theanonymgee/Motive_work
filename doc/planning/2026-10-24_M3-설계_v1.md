## 2. 도구 목록과 입출력

### 2.1 공통 규칙

- 봉투: `{"ok": true, "result": {...}, "delivered_sources": ["<display>", ...], "notice": ["...", ...]}` 또는 `{"ok": false, "error": {"code", "message", "retryable"}}`(`tools.ok/error` 그대로 **[사실]**).
- **[결정]** 도구 함수의 반환형은 `str`(봉투의 compact JSON, `ensure_ascii=False`), 등록은 `@server.tool(structured_output=False)`. 근거 **[사실]**: SDK `_convert_to_content`는 `str`이 아닌 결과를 `pydantic_core.to_json(result, indent=2)`로 다시 직렬화하고(`func_metadata.py` 652~655행), `dict[str, Any]` 반환은 자동 감지에서 구조화 출력(`structuredContent`)까지 만들어 같은 내용이 두 번 실린다. 문자열을 돌려주면 `TextContent(text=그대로)` 하나만 나간다. 기존 serve 테스트의 `json.loads(content[0].text)`는 그대로 맞는다.
- 모든 시각은 `store.now()` 형식(로컬 오프셋 ISO 8601, 초). 모든 경로는 `documents.path` 원문(수집 때의 절대 경로).
- 인자 검사 순서: 형·범위(우리 코드, `argument_invalid`류) → 저장소 열기(`store_missing`) → 실행. 인자 오류는 모델을 건드리기 전에 난다(M2 `Engine.search`와 같음).
- `notice`는 사람이 읽는 한국어 문장 목록. 기존 문구(`NO_RESULTS_NOTICE`, `OBSERVED_NOTICE`, `SHORT_QUERY_NOTICE`) 유지.
- 서버 `instructions`(SDK `MCPServer(instructions=...)` **[사실]** 인자 있음): 두 문장 — "응답의 delivered_sources가 이번에 PC를 떠난 원문 조각의 출처 전부다", "검색 결과 없음 ≠ 회사에 그 정보가 없음". 도구 설명(docstring)에도 본문 유무를 적는다.

### 2.2 `search`

입력(JSON Schema는 SDK가 타입 힌트에서 생성):

| 인자 | 형 | 기본 | 상한 | 오류 |
|---|---|---|---|---|
| `query` | str | 필수 | strip 뒤 비어 있지 않음, ≤ 1,000자 | `empty_query`, `query_too_long` |
| `mode` | str | `"hybrid"` | `hybrid|lexical|semantic` | `mode_invalid` |
| `limit` | int | 10 | 1~50 | `limit_out_of_range` |
| `path_prefix` | str? | null | ≤ 1,024 | `filter_invalid` |
| `ext` | list[str]? | null | ≤ 20개, `SUPPORTED_EXTENSIONS` | `filter_invalid` |
| `since`, `until` | str? | null | ISO 8601(`versions.observed_at` 기준) | `filter_invalid` |
| `collapse_by_document` | bool | false | — | — |

출력 `result` = M2 §5.7 그대로(`hits[]`, `meta`) **[사실]** `search.RESULT_KEYS/HIT_KEYS/META_KEYS`, 여기에 더하는 것:

```json
{"hits": [...M2 §5.7 hit...],
 "meta": {..., "collapsed": 0, "truncated_hits": 0,
          "signals": {"lexical_candidates": 143, "exact_phrase_hits": 2, "cosine_top1": 0.71, "cosine_top10": 0.52, "cosine_gap": 0.19, "low": false},
          "engine": {"model_loaded_now": false, "load_ms": 0}},
 "notice": ["..."]}
```

- **[결정]** `collapse_by_document=true`: 융합 순서대로 훑으며 **문서(`doc.id`)당 첫 hit만** 남기고 `limit`개가 차면 멈춘다. `rank`는 1부터 다시 매긴다. `meta.collapsed` = 건너뛴 hit 수. 구현: `search()`가 `_hits`에 `ranked` 전체(후보 합집합 ≤ 400)를 넘기고 `_hits(limit, collapse)`가 멈출 때까지만 locator를 만든다(기존 `ranked[:limit]` 호출은 `collapse=False`일 때의 특수 경우). 점수·`hit` 이유는 바뀌지 않는다.
- `meta.signals`·`LOW_SIGNAL`은 §9.3. `meta.engine`은 §6.3(준비 notice).
- `notice`: 결과 0건 → `NO_RESULTS_NOTICE`; 필터 since/until 사용 → `OBSERVED_NOTICE`; LIKE 경로 → `SHORT_QUERY_NOTICE` 또는 N1 문구; 크기 상한 → §4; 모델 첫 로드 → §6.3; `semantic_note`가 있으면 "의미 검색 사용 불가: <code>"(코드만, 메시지 본문 아님).
- `delivered_sources` = `[locator.display(hit['locator']) for hit in hits]`(스니펫 본문이 나간 출처; `units[]`는 본문이 없으므로 제외 — M2 §5.7).
- 오류 코드: `search.ERROR_CODES` 5개 + `store_missing` + `internal_error`.

### 2.3 `get_snippet`

| 인자 | 형 | 기본 | 규칙 | 오류 |
|---|---|---|---|---|
| `chunk_id` | int? | null | `chunk_id` **또는** `locator` 중 정확히 하나 | `argument_invalid` |
| `locator` | object? | null | `locator.check_shape` 통과(`v`,`doc`,`path`,`sha256`,`unit`,`chars`,`text_sha256`) | `locator_invalid` |
| `context_units` | int | 0 | 0~5 | `argument_invalid` |
| `max_chars` | int | 4,000 | 200~4,000, 조각 하나의 본문 상한 | `argument_invalid` |

출력:

```json
{"doc": {"id": 12, "path": "...", "ext": ".docx"},
 "version": {"id": 61, "seq": 3, "sha256": "...", "observed_at": "...", "latest": true, "latest_version_id": 61},
 "chunk": {"id": 8812, "ordinal": 4, "unit_first": 10, "unit_last": 12, "chunk_version": "units-700-900-140-v1"} | null,
 "pieces": [{"locator": {...}, "text": "...", "truncated": false}, ...],
 "context_before": [{"locator": {...}, "text": "...", "truncated": false}, ...],
 "context_after": [...]}
```

- **[결정]** `chunk_id` 경로: `chunks` 행을 읽고(없으면 `not_found`) 그 버전의 `units[unit_first..unit_last]`에서 M2 `search._hits`와 같은 계산으로 단위별 `[cs, ce)`를 내어 조각마다 `locator.make(doc, path, sha256, unit, unit_text, [cs, ce])` + `text = unit_text[cs:ce]`. 청크 본문을 이어 붙인 문자열은 주지 않는다(M2 §2.5). 공통 계산은 `search._hits`에서 `snippet.cover(units_rows, char_start, char_end) -> list[(ordinal, unit, text, (cs, ce))]`로 빼서 둘이 같은 함수를 쓴다(B가 `search.py`와 `snippet.py`를 함께 소유하므로 충돌 없음).
- **[결정]** `locator` 경로: `binding.validate_locator`와 같은 조회(`versions(document_id, sha256)` 최신 행 → `units(version_id, locator_json)`) 뒤 `locator.check_text`로 `text_sha256` 대조. 모양 오류 → `locator_invalid`, 버전·단위 없음 → `not_found`, 해시 불일치 → `locator_invalid`(메시지 `text_sha256 mismatch`). `pieces` = 그 범위 하나(조각 1개). `chunk`는 null.
- **[결정]** 문맥: 같은 `version_id`에서 `ordinal` 기준 앞 `context_units`개·뒤 `context_units`개의 **전체 단위**(그룹 경계·쪽 경계를 넘어도 됨 — 단위 locator가 쪽·시트를 그대로 말한다). 각각 `chars=[0, len]`. 버전 시작·끝에서는 있는 만큼만.
- **[결정]** 옛 버전: `versions.superseded_at IS NOT NULL` 또는 문서 `status != 'active'`여도 **돌려준다**(단위는 M1대로 보존됨, M2 §4.1). `version.latest=false`, `latest_version_id`는 그 문서의 `superseded_at IS NULL`인 버전(삭제 문서면 null), notice "이 조각은 옛 버전(seq n)의 것입니다; 현재 버전 id …" 또는 "이 문서는 삭제됨". M0의 `version_superseded` 오류는 쓰지 않는다(오류가 아니라 정보).
- **[결정]** 조각 상한: 조각 하나 `text`가 `max_chars`를 넘으면 앞에서 `max_chars` 안의 마지막 낱말 경계(`chunks._pull_to_words` 재사용)까지 자르고 `truncated: true`, **locator의 `chars`도 잘린 범위로** 만든다(전달한 글자와 출처가 정확히 같음). 같은 단위 안에서 더 읽으려면 클라이언트가 `locator`의 `chars`를 바꿔 다시 부른다 — 이를 notice로 안내.
- `delivered_sources` = `context_before` → `pieces` → `context_after` 순서의 모든 조각 locator display.
- 오류: `argument_invalid`, `locator_invalid`, `not_found`, `store_missing`, `internal_error`.

## 3. `delivered_sources`와 로컬 기록

### 3.1 불변 규칙 (테스트 §13 D-1~D-4로 고정)

1. `delivered_sources[i]` ↔ 응답 안에서 본문이 실린 i번째 조각. 길이가 같고 순서가 같다. 조각 = `hits[*].snippet`, `pieces[*].text`, `context_*[*].text`. 그 밖의 문자열(경로·`notice`·`meta`·`units[]`)은 본문이 아니다.
2. 표시 문자열은 `locator.display(조각의 locator)`이며, 그 locator로 `binding.validate_locator`를 통과하면 **정확히 그 조각의 텍스트**가 나온다(§5).
3. 크기 상한으로 뺀 조각은 응답에도, 목록에도, `deliveries`에도 없다. 잘린 조각(`get_snippet` `truncated`)은 잘린 범위의 locator로 들어간다.
4. `ok:false` 응답은 본문이 없다 → 목록·`deliveries` 행 없음(`tool_calls` 행은 있음).

### 3.2 클라이언트 이름

- **[사실]** 도구 함수는 `Context` 형 매개변수를 받을 수 있고(`mcp.server.mcpserver.Context`, `mcp/server/mcpserver/__init__.py`에서 export), `ctx.session.client_params`가 `InitializeRequestParams(protocol_version, capabilities, client_info: Implementation)`을 준다. 새 프로토콜(2026-07-28+)에서는 `initialize`가 없지만 요청 봉투의 `client_info`로 `client_params`를 **합성**한다(`connection.py` 262~290행 docstring). 클라이언트가 정보를 안 보내면 None.
- **[결정]** `client = f"{info.name}/{info.version}"`에서 이름은 `client_info.name`(없으면 `"unknown"`), 버전은 `client_info.version`(없으면 `""`). 이름은 ≤ 64자로 자르고 제어 문자는 뺀다(기록용). M0 §4.1의 대안(`serve --client`)은 쓰지 않는다 — 읽는 방법이 확인됐다.
- 실제 값(⑤에서 기록): Claude Code·Codex가 보내는 `clientInfo.name`은 **[추정]** `claude-code`·`codex-cli`(또는 `codex`) — 연결 확인 때 `tool_calls.client`를 그대로 증거 문서에 적는다.

### 3.3 기록 내용

- `tool_calls` 1행/호출: `at`, `client`, `client_version`, `tool`, `call_id`(`os.urandom(8).hex()` — `uuid`는 허용 목록에 없고 필요도 없다), `args_json`(인자 **요약**: `search` → `{"mode","limit","filters":["path_prefix","ext"],"query_chars":n,"query_sha12":"…","collapse":bool}` — 질의 본문은 넣지 않는다; `get_snippet` → `{"by":"chunk_id"|"locator","chunk_id":n|null,"doc":id|null,"context_units":k,"max_chars":m}`; `list_documents`/`recent_changes` → 필터 키와 limit/offset; `status` → `{}`), `pieces`(조각 수), `chars`(조각 글자 합), `ok`(0/1), `error_code`, `elapsed_ms`, `pid`.
- `deliveries` 1행/조각: 기존 열(`at, client, tool, locator_json, chars`) + `call_id`.
- 본문(질의·스니펫·조각)은 **어느 표에도, stderr에도** 쓰지 않는다(테스트 D-5: 합성 `SENTINEL`이 DB의 `tool_calls`·`deliveries`와 stderr에 없음 — `units`·`chunks`에는 당연히 있음).
- 기록 시점: 응답 문자열을 만든 **뒤**, 돌려주기 **전**. 기록이 실패(`sqlite3.OperationalError`)하면 1회 재시도 뒤 응답 `notice`에 "로컬 전달 기록(deliveries) 실패: <예외 클래스>"를 붙이고 stderr에 적는다(응답은 나간다 — 클라이언트에 이미 보일 `delivered_sources`가 1차 가시성이고 로컬 기록은 2차). 이 notice 추가는 크기 상한 뒤에 일어나므로 상한을 넘길 수 있다 → 상한 계산에 notice 여유 200자를 둔다(§4).

### 3.4 스키마 마이그레이션 v2 (`store.MIGRATIONS`에 **추가**, v1 불변)

- **[사실]** `store.migrate`는 `BEGIN IMMEDIATE` 안에서 `MIGRATIONS`를 순서대로 적용하고 체크섬을 기록하며, 적용된 항목의 체크섬이 바뀌면 거부한다. 이 PC에는 앱 가상화 홈에 `models/bge-m3`가 있고 `db/`는 **비어 있다**(2026-10-24 실측) — 그래도 M1 §10.1의 "v1 직접 수정"은 이번에 쓰지 않는다: 두 serve 프로세스가 각각 `open_home`으로 마이그레이션을 시도하므로 **추가 전용 v2**가 안전하고(`BEGIN IMMEDIATE` + `busy_timeout`으로 한 프로세스만 적용, 다른 쪽은 적용됨을 봄), 회사 PC 첫 설치 뒤의 절차와도 같다.

```sql
-- (2, 'tool_calls_events_v2', SCHEMA_V2)
CREATE TABLE tool_calls(id INTEGER PRIMARY KEY, at TEXT NOT NULL, client TEXT NOT NULL,
  client_version TEXT NOT NULL DEFAULT '', tool TEXT NOT NULL, call_id TEXT NOT NULL UNIQUE,
  args_json TEXT NOT NULL DEFAULT '{}', pieces INTEGER NOT NULL DEFAULT 0, chars INTEGER NOT NULL DEFAULT 0,
  ok INTEGER NOT NULL, error_code TEXT, elapsed_ms REAL, pid INTEGER);
CREATE INDEX tool_calls_at ON tool_calls(at, id);
ALTER TABLE deliveries ADD COLUMN call_id TEXT NOT NULL DEFAULT '';
CREATE INDEX deliveries_call ON deliveries(call_id);
CREATE TABLE document_events(id INTEGER PRIMARY KEY, at TEXT NOT NULL,
  scan_id INTEGER REFERENCES scans(id), document_id INTEGER NOT NULL REFERENCES documents(id),
  version_id INTEGER REFERENCES versions(id),
  kind TEXT NOT NULL CHECK(kind IN ('added','changed','restored','deleted','reparsed')));
CREATE INDEX document_events_at ON document_events(at, id);
CREATE INDEX document_events_doc ON document_events(document_id, id);
```

- `tool_calls`·`deliveries`·`document_events`는 **추가 전용**(append-only) 표다. `versions`와 같은 보호 트리거(`*_no_delete`·`*_update_guard`)를 둘지는 [제안]: 두면 `tests/test_store_schema.py`의 기존 트리거 테스트 양식을 재사용. 기본은 **둔다**(UPDATE·DELETE 거부; REPLACE 우회는 `id` 재사용 INSERT 거부 트리거로) — 전달 기록은 사후 감사 자료라 고치지 못해야 의미가 있다.
- `status.schema_version`은 2가 된다(기존 serve 테스트의 `schema_version == 1` 단언 갱신).
- `doctor`의 `DEV_SCHEMA_HINT`(v1 체크섬 불일치 안내)는 그대로. v2 적용은 `open_home`에서 자동.
- 이관: 기존 `deliveries` 행(현재 0행)은 `call_id=''`로 남는다.

### 3.5 쓰기 연결

- **[결정]** `server.main`은 지금처럼 `store.open_home(home)`을 열되 **닫지 않고** `ServerState.write_db`로 보관한다(마이그레이션은 이 한 번). 기록 INSERT는 autocommit(`isolation_level=None` **[사실]**) 단문 2개(`tool_calls` 1행, `deliveries` executemany) — 트랜잭션 묶음은 `BEGIN IMMEDIATE … COMMIT`으로 한 번에(조각 수십 행). 읽기는 도구마다 `store.open_read`(기존 `Engine`과 같음). lifespan 종료에서 `write_db.close()`.
- `scan`·`index` CLI와의 경합: 그쪽 트랜잭션은 짧다(M2 §4.6). `busy_timeout` 5초 안에 풀린다 [추정]. 넘으면 §3.3의 실패 경로.

- 측정 단위: **직렬화 결과 문자열의 `len`**(`json.dumps(envelope, ensure_ascii=False, separators=(',', ':'))`). 바이트가 아니라 문자(클라이언트 한도가 문자·토큰 기준).

- 도구별 빼는 단위와 notice:
  - `search`: 마지막 hit부터. `meta.truncated_hits += 1`, notice "응답 크기 상한(40,000자)으로 hit n개를 뺐습니다 — limit을 줄이거나 필터를 쓰세요". 뺀 hit는 `delivered_sources`에 없다.

### 6.2 결정

- **도구 함수는 `async def`**(본문에 `await` 없음). 효과: 이벤트 루프 스레드에서 호출마다 끝까지 실행 → 도구 호출끼리 **직렬**(`Engine`의 "잠금 없음" 전제가 그대로 성립), `threading`을 허용 목록에 넣지 않아도 된다. 대가: 모델 첫 로드(≈3.4 s)·행렬 로드 동안 루프가 멈춘다 — ping·다른 요청이 그만큼 늦는다. 수용(단일 사용자, Claude Code stdio 도구 유휴 한도 30분·Codex `tool_timeout_sec` 기본 60초 **[사실]** 안).
- **`Engine` 하나**를 `build_server`가 만든다(`ServerState.engine`, 테스트는 `engine=` 인자로 `HashEmbedder` 팩토리 Engine을 주입). 서버 시작 시 모델·행렬을 **미리 로드하지 않는다**(M2 부록 C).
- **유휴 해제**: SDK에 훅이 없으므로 lifespan 안에서 ticker를 돈다.

```python
@contextlib.asynccontextmanager
async def _lifespan(server):              # server.py; state는 클로저
    async with anyio.create_task_group() as tg:
        tg.start_soon(_ticker, state)      # while True: await anyio.sleep(state.tick); state.engine.maybe_unload()
        try:
            yield {}
        finally:
            tg.cancel_scope.cancel()
            state.write_db.close()
```

  `anyio.sleep`·`create_task_group`만 쓴다(소켓·프로세스 없음; 감사 테스트가 확인). 또한 **모든 도구 호출의 시작**에서 `maybe_unload()`를 한 번 더 부른다(ticker가 어떤 이유로 멈춰도 다음 호출이 해제). `tick = config [server].unload_tick_seconds`(기본 30, 1~300). `maybe_unload`가 True를 돌려주면 `unloads += 1`과 stderr 한 줄(`unloaded model after idle`). 해제 뒤 다음 의미 질의가 다시 로드한다(≈3.4 s, 준비 notice 다시).
- 허용 목록 변경(`tests/test_network_boundary.py`): `MODULE_IMPORTS['server.py'] = {'mcp.server.MCPServer', 'mcp.server.mcpserver.Context', 'anyio', 'contextlib', 'time', 'logging'}`(부록 C); `test_server_may_use_mcp_but_not_other_transports`의 `import anyio` 위반 단언은 `anyio.run(server.run_sse_async)` 위반 단언으로 바꾼다(전송 규칙이 잡음). 새 양성 대조군: `import anyio` **in `tools.py`**(위반), `from anyio import to_thread`(server.py에서도 위반 — 스레드로 도구를 돌리지 않는다는 결정을 정적으로 고정), `anyio.open_tcp_stream`(호출 이름 금지 목록에 추가). `contextlib`는 server.py에만(다른 모듈에서 쓰지 않으므로 공통 목록에 넣지 않음).

### 6.3 첫 질의 "준비" notice

- `handle`이 호출 전후로 `engine.status()['loaded']`와 `engine.loads`를 비교: 이번 호출에서 로드가 일어났으면 `meta.engine = {"model_loaded_now": true, "load_ms": …}`(로드 구간은 `Engine.embedder()` 안에서 재는 `last_load_ms`를 `Engine`에 추가) + notice "의미 검색 모델을 이 호출에서 처음 로드했습니다(+N ms); 다음 질의부터 빠릅니다". 로드 실패면 `semantic_note` 코드 + notice "의미 검색 사용 불가(<code>) — 어휘 결과만".
- `status`도 `engine.loaded`를 보이므로 클라이언트가 미리 알 수 있다. 사전 로드 도구(`warm_up`)는 두지 않는다(메모리 보장과 충돌).

### 6.4 다른 프로세스의 scan/index와의 일관성

- **[사실]** M2 §14: `Engine.vectors`는 `index_generation`이 바뀌면 행렬을, `data_generation`만 바뀌면 청크 매핑을 다시 만들고, `_hits`는 지금 대상(최신 활성·현재 청크 규칙)이고 점수 낸 텍스트와 같은 청크만 낸다. `get_snippet`·`list_documents`·`recent_changes`는 호출마다 `open_read`로 현재 상태를 읽는다 → 캐시 없음.
- **[결정]** 추가 없음. 테스트는 서버 경로에서 재현: `scan` 변경 → 같은 `Engine`으로 `search` → 옛 버전 없음; `index` 완료 → 새 텍스트 의미 hit(§13 E-2). N2(§9.2)가 이 보장의 구별력을 맡는다.

### 8.2 경로

- 우리 코드의 오류는 **예외가 아니라 봉투**로 돌아온다(`server.handle`이 `search.SearchError`·`locator.LocatorError`·`snippet.NotFound`를 코드로 바꿈). SDK가 `is_error=True`를 만드는 경우는 **인자 스키마 검증 실패**(예: `limit`에 문자열)뿐 — 그 텍스트는 SDK가 만든다(필드 이름만 로그 **[사실]** 436~441행). 문서화하고 테스트 §13 X-2가 그 형태를 고정한다.
- `handle`의 마지막 보호: `except Exception as exc: envelope = tools.error('internal_error', type(exc).__name__); traceback → stderr`. `BaseException`(KeyboardInterrupt)은 통과시킨다.
- stdout 순수성: 우리 코드는 `print`를 쓰지 않는다(`server.main`의 홈 오류 1줄도 stderr **[사실]**). `logging.basicConfig(stream=sys.stderr, level=logging.WARNING, format='%(asctime)s %(name)s %(levelname)s %(message)s')`를 `server.main`에서 한 번 — SDK의 `logger.exception`이 stderr로 가게 하고(루트 핸들러 없음 → Python `lastResort`도 stderr이지만 명시), **네트워크 핸들러 금지 규칙**(`test_logging_allowlist_does_not_open_network_handlers`)은 그대로. SDK의 fd 1 전환은 **보조**: 테스트는 우리 코드가 stdout에 아무것도 쓰지 않음을 serve 감사(stdout 전 줄 JSON-RPC)로 본다.
- 메시지 언어: 코드 영문, 메시지는 짧은 한국어 또는 영문 고정 문구. 클라이언트가 보낸 값(경로 접두·확장자)을 메시지에 되돌려줄 수 있다(그 클라이언트의 것). 저장소의 **다른** 문서 경로는 오류 메시지에 넣지 않는다.

## 9. M2 §14의 M3 항목

### 9.1 N1 — `fts_dirty`면 LIKE 경로

- **[사실]** `store.fts_dirty` 규칙: FTS5 없이 청크를 바꾸면 `meta.fts_dirty='1'`, 이후 쓰기는 FTS를 건드리지 않고 다음 FTS5 `index`가 자동 rebuild. `search.fts_usable(db)`는 표 존재·읽기 가능만 본다(231~240행) → dirty 동안 어긋난 FTS로 검색.
- **[결정]** `fts_usable(db)`에 `and store.meta_get(db, 'fts_dirty') is None`을 더한다(`store.py`에 이미 같은 판정이 있음: 484행 `fts_available(db) and meta_get(db, 'fts_dirty') is None` — 그 함수를 호출). dirty면 `meta.lexical.engine='like'` + notice "전문 색인이 어긋나 있어 느린 어휘 검색을 씁니다 — `workmcp index --rebuild-fts`". 대상 청크가 `like_max_chunks`를 넘으면 `engine='none'` + 같은 notice(기존 S3 규칙).
- 테스트(§13 N-1): 색인 뒤 `store.fts5_available`을 몽키패치로 False로 만들고 문서 하나 수정·scan·index(청크만) → dirty → 원래대로 FTS5 켜고 `search(새 문장, lexical)` → `engine=='like'`이고 새 버전 hit; **옛 코드(패치 전)**에선 `engine=='fts5'`이고 못 찾음 — 테스트에 `monkeypatch.setattr(search, 'fts_usable', 기존 판정)`으로 **옛 동작을 재현해 실패함**을 함께 단언(구별력).

### 9.2 N2 — 구별력 있는 테스트

- **[사실]** `test_long_lived_engine_after_an_index_run_that_stopped`(test_search.py 730행)는 어휘 모드의 `version_id`만 보며, `_hits`가 비적격 청크를 거르므로 `VectorCache.remap`이 없어도 통과한다(검토 M2 v2 N2).

### 10.2 왜 일어나는가 (Microsoft Learn, 접근 2026-10-24)

- 가상화되는 패키지 앱에서 "All newly created files and folders in the user's `AppData` folder … are written to a private per-user, per-app location; but merged at runtime to appear in the real `AppData` location." 대상 폴더: `Local`, `Local\Microsoft`, `Roaming`, `Roaming\Microsoft`, … (Windows 10 1903+).
- "In response to a file open command, the OS will open the file from the per-user, per-package location first. If that location doesn't exist, then the OS will attempt to open the file from the real `AppData` location. If the file is opened from the real `AppData` location, then no virtualization for that file occurs."
- 패키지 제거 시 "any redirected writes to `AppData` … are removed" — **앱을 지우면 앱 가상 홈의 DB·모델이 함께 사라진다.**
- 자식 프로세스가 패키지 정체성을 물려받는지는 문서가 직접 말하지 않지만, 위 탐침(앱 → claude.exe → cmd → powershell에서 리디렉션 관찰)이 이 PC에서 **물려받음**을 보인다 [사실, 이 PC]. Codex 앱이 띄우는 서버도 같은 규칙을 따른다 [추정 — ⑤에서 확인].
- 따라서 생기는 세 가지 상황:
  1. **분리**: 앱 안 서버는 `Packages\<앱>\LocalCache\Local\Motive_work\db\work.sqlite3`를, 앱 밖 CLI(`workmcp scan`을 Windows Terminal에서 실행)는 `C:\Users\<USER>\AppData\Local\Motive_work\db\work.sqlite3`를 만든다 → 서로 다른 DB, scan한 문서가 서버에 안 보임. Claude 앱과 Codex 앱은 **각자의 패키지 폴더**를 본다 → 두 클라이언트가 다른 DB.
  2. **반쪽 가상화(위험)**: 실제 AppData에 DB가 이미 있으면 앱 안 프로세스도 그 파일을 연다(새 파일이 아니므로). 그러나 SQLite가 만드는 `work.sqlite3-wal`·`-shm`은 **새 파일**이라 패키지 위치에 생긴다. 밖의 프로세스는 실제 위치에 자기 `-wal`을 만든다 → 두 작성자가 **서로 다른 WAL**로 같은 DB 파일을 고친다. 이는 SQLite의 "한 DB에 WAL 하나" 전제를 깨며 손상 가능성이 있다 [추정 — 재현 실험은 하지 않는다; 설계상 **피한다**].
  3. **삭제 위험**: 앱 제거·초기화가 데이터 홈을 지운다.

### 10.3 대처 (결정)

1. **홈은 AppData 밖에 명시한다.** 두 클라이언트의 MCP 설정 `env`에 `WORKMCP_HOME`을 같은 절대 경로로 적는다. 기본 후보 **`%USERPROFILE%\Motive_work`**(= `C:\Users\<USER>\Motive_work`). `paths.validate_home` 규칙 대조 **[사실]**: 절대·로컬·저장소 밖(`C:\Users\<USER>\Project\Motive_work`와 겹치지 않음)·동기화 이름 없음·UNC 아님 → 통과. 사용자 프로필 루트는 OneDrive 리디렉션 대상(문서·바탕화면·사진)이 아니다 [사실, 일반 Windows]. 대안: `D:\Motive_work`(다른 드라이브면 `drive_warning`만). 회사 PC는 M5에서 같은 규칙으로 고른다.

- "You can also add project-scoped overrides in `.codex/config.toml` files." "Codex loads project-scoped config files only when you trust the project." 신뢰는 `projects.<path>.trust_level`. 프로젝트 설정이 덮을 수 없는 키(`model_provider` 등)가 있으나 `mcp_servers`는 그 목록에 없다.

### 11.2 결정

1. **파일 위치**: Claude Code → 프로젝트 루트 `.mcp.json`; Codex → 프로젝트 루트 `.codex/config.toml`. **전역 파일(`~/.claude.json`, `~/.codex/config.toml`)은 건드리지 않는다.**
2. **커밋하지 않는다**: 두 파일 모두 `.gitignore`에 추가(`/.mcp.json`, `/.codex/`). 이유: Codex 파일은 절대 경로가 필요하고(`env`에 변수 확장이 문서에 없음), 두 파일 다 PC별 값(사용자 이름·venv 경로·데이터 홈)을 담으며, ⑤에서는 합성 홈으로 잠시 바꾼다. 대신 `doc/examples/mcp.json.example`·`doc/examples/codex-config.toml.example`을 커밋하고 자리표시자 `<REPO>`·`<HOME>`을 쓴다. 비밀값은 어느 파일에도 없다(서버가 비밀을 쓰지 않음; `.env`는 git-ignored).
3. **명령은 venv 파이썬 직접 호출**(`uv run` 아님 — 추가 프로세스·네트워크 가능성 없음, 감사 경로와 같음): `<REPO>\.venv\Scripts\python.exe -I -m workmcp serve`(`-I` 격리 모드: 앱 프로세스가 물려준 `PYTHONPATH`·사용자 site·작업 폴더 모듈을 무시 — 검토 v1 M3-4, §18). Claude 쪽은 `${CLAUDE_PROJECT_DIR:-.}` 확장으로 상대화할 수 있으나 **[추정]** 서버의 작업 디렉터리가 프로젝트 루트인지 문서가 확인해 주지 않으므로 예시는 **절대 경로**로 적고, 확장 변형은 ⑤에서 시험해 되면 템플릿에 반영한다.
4. **`env`에 항상 `WORKMCP_HOME`**(§10). 평상시 `%USERPROFILE%\Motive_work`(Claude 쪽은 `${USERPROFILE}\\Motive_work`로 확장 가능 — ⑤에서 확인), ⑤ 동안은 합성 홈.
5. 이름은 두 클라이언트 모두 `workmcp`.
6. `timeout`(Claude, ms)과 `tool_timeout_sec`(Codex)은 첫 의미 질의(모델 로드 ≤ 10 s)를 넘도록 **120 s**로 적는다. `startup_timeout_sec`는 기본(10 s; serve 시작은 마이그레이션 포함 < 1 s **[추정]**).

```python
                 ext: list[str] | None = None, since: str | None = None, until: str | None = None,
                 collapse_by_document: bool = False, ctx: Context = None) -> str:
    """Hybrid search; returns snippets (<=600 chars) with exact sources. delivered_sources = one per hit."""
    return handle(state, 'search', dict(query=query, mode=mode, ...), client_of(ctx))

def handle(state, tool, args, client) -> str:
    began = time.perf_counter(); call_id = os.urandom(8).hex()
    released = state.engine.maybe_unload()                       # 유휴 해제 (ticker 보조)
    loaded_before = state.engine.status()['loaded']
    try:
        envelope = TOOLS[tool](state, **args)                    # tools.search(state.home, state.engine, ...) 등
        envelope = tools.fit(envelope, SHRINK[tool], state.budget)
        annotate_engine(envelope, state.engine, loaded_before)   # §6.3
    except search.SearchError as exc:   envelope = tools.error(exc.code, exc.message)
    except locator.LocatorError as exc: envelope = tools.error('locator_invalid', exc.code)
    except snippet.NotFound as exc:     envelope = tools.error('not_found', str(exc))
    except FileNotFoundError as exc:    envelope = tools.error('store_missing', str(exc))
    except sqlite3.OperationalError as exc: envelope = tools.error('store_busy' if 'locked' in str(exc) else 'internal_error', type(exc).__name__, retryable=...)
    except Exception as exc:            log_exception(exc); envelope = tools.error('internal_error', type(exc).__name__)
    text = json.dumps(envelope, ensure_ascii=False, separators=(',', ':'))
    record(state, call_id, client, tool, args, envelope, began)   # tool_calls + deliveries; 실패 시 notice 추가 후 재직렬화
    return text
```
