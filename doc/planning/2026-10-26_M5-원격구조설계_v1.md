## 0. 요약 (결정 한 장)

| 항목 | 결정·추천 |
|---|---|
| 구조 | **같은 패키지 `workmcp`의 두 역할.** 수집기(회사 PC): 기존 `scan`·`index`·`verify` 그대로 + 새 `push`. 운영 서버(VPS): 기존 15개 도구 그대로 + 새 `serve --http`(Streamable HTTP, 토큰) + 업로드 수신 + 토큰 관리. 저장소 스키마는 양쪽 같고(v1~v4 + **v5 추가**), 서버 쪽 표에는 수집기 id가 붙는다(§1·§2) |
| 동기화 | **서버가 기준, 수집기는 상태 없음.** `push` = ① 서버 상태 요약 2개 해시 비교(같으면 **배치 0·전송 0**) → ② 문서·버전 행(단위 없음) → 서버가 버전마다 `have/copied/need` 답 → ③ `need`인 버전의 **단위 텍스트**(분할 가능) → 서버가 같은 청크 규칙으로 청크·FTS를 **스스로 재생성**(청크 텍스트는 보내지 않음) → ④ 서버가 없는 벡터(`text_sha256`)만 fp32로 → ⑤ 문서 이벤트 → ⑥ 종료. 배치마다 `batch_id`(본문 해시) 멱등, 서버 트랜잭션 1배치, 중단 재개는 ①부터 다시(§3) |
| 서버 전송·인증 | mcp 2.2.0 `run(transport="streamable-http")` **[사실]**: stateful 세션(클라이언트 이름 기록 유지), `json_response=True`, 경로 `/workmcp/mcp`, `127.0.0.1:8765`에만 바인드. 인증은 SDK `TokenVerifier`(Bearer) — **MCP 토큰**과 **업로드 토큰**을 종류로 나눠 SHA-256만 저장, `workmcp token issue|list|revoke`. `AuthSettings.resource_server_url=None`으로 **인증 없는 경로 0**(메타데이터 경로가 생기지 않음 **[사실]**). 업로드 경로는 `custom_route`(인증 없음 **[사실]**)라 **직접** Bearer 검사(§4) |
| TLS·공존 | **리버스 프록시**(VPS에 이미 있는 nginx/caddy/apache 중 하나 또는 새 caddy)가 `srv1782254.hstgr.cloud`의 Let's Encrypt 인증서로 443을 받고 `/workmcp/` 아래만 `127.0.0.1:8765`로 넘긴다. 앱 직접 TLS는 하지 않는다. 기존 서비스 포트·설정은 건드리지 않고 **location 블록 1개만 추가**. 조사(§9.1) 전에는 어느 웹서버인지 모른다 **[사실]** |
| 프로세스 | 전용 리눅스 사용자 `workmcp`(로그인 셸 없음), **systemd 시스템 유닛** `workmcp.service`(`User=workmcp`, `MemoryMax`, `Restart=on-failure`, `ProtectSystem=strict`), 데이터 홈 `/home/workmcp/Motive_work`(`WORKMCP_HOME` 필수 — 리눅스에는 `USERPROFILE`이 없다 **[사실]**) |
| 질의 임베딩 | 서버에 같은 매니페스트 모델(bge-m3, SHA-256 고정)을 `workmcp setup --model download`로 Hugging Face에서 1회 받음(서버 egress 예외 = 모델 다운로드 모듈만, 피터 승인). 유휴 해제 유지(기본 600 s → VPS는 **[제안] 1800 s**), 메모리 상한은 cgroup `MemoryMax=3G`(§7) |

| 작업 분할 | 0단계 A(서명·와이어 스키마·스키마 v5·허용 목록) → 1단계 A `remote.py`·토큰·CLI, B `push.py`·`receive.py`(서버 수신 적용)·`sync.py` 테스트, C 배포 문서·조사 스크립트·systemd/프록시 조각·점검표·클라이언트 예시 → 2단계 A 통합·e2e·감사 → 피터 승인 → 배포(§11) |

### 0.1 전제 사실

- **[사실]** VPS(총괄 확인 2026-10-26, Hostinger API 읽기): KVM 2, 2 vCPU, 8 GB RAM, 100 GB 디스크, Ubuntu 24.04 LTS, IPv4 `<VPS_IP>`, IPv6 있음, Hostinger 방화벽 그룹 없음(`firewall_group_id: null`), 기본 호스트 이름 `srv1782254.hstgr.cloud`. **무엇이 돌고 있는지(웹서버·docker·열린 포트·디스크·메모리 여유)는 모른다** → §9.1 읽기 전용 조사가 배포 전 첫 단계.
- **[사실]** mcp 2.2.0(venv): `MCPServer.run(transport="streamable-http", host, port, streamable_http_path, json_response, stateless_http, event_store, max_request_body_size, transport_security, …)`(`server/mcpserver/server.py` 383~397·1104~1143행, 내부에서 `uvicorn.Config(app, host, port, log_level)`); `MCPServer(auth=AuthSettings, token_verifier=TokenVerifier)`(167~168행); `streamable_http_app`은 `token_verifier`가 있으면 `/mcp` 경로를 `AuthenticationMiddleware(BearerAuthBackend)` + `RequireAuthMiddleware`로 감싸 Bearer 없음/틀림에 **401 + `WWW-Authenticate`**(`lowlevel/server.py` 771~815행, `bearer_auth.py` 115~121행); `auth.resource_server_url`이 있을 때만 `/.well-known/oauth-protected-resource` 메타데이터 경로(인증 없음)가 추가된다(824~831행) → **None이면 인증 없는 경로가 없다**; `custom_route`는 인증을 거치지 않는다(docstring 1036~1038행); 요청 본문 상한 기본 4 MiB는 MCP 경로(세션 관리자)에만 적용(`streamable_http_manager.py` 114행); stateful 세션은 `Mcp-Session-Id`로 추적, 유휴 30분 뒤 종료(기본 1800 s), 세션을 만든 토큰 주체만 그 세션을 쓸 수 있다(261~325행); `app.lifespan`은 세션 관리자 `run()`에서 **프로세스당 1회** 들어간다(156~160행) → M3의 유휴 해제 ticker가 HTTP에서도 프로세스 수준으로 그대로 돈다; stateless 모드는 `initialize` 없이 "born-ready"라 `client_params`가 없다(235~243행) → 클라이언트 이름 기록(`tool_calls.client`)을 위해 **stateful**을 쓴다; `TransportSecuritySettings(allowed_hosts, allowed_origins)`로 Host/Origin 검사(DNS 리바인딩 방지).
- **[사실]** `requirements.lock.txt`에 `uvicorn 0.54.0`·`starlette 1.9.0`·`sse-starlette 3.5.0`·`httpx2 2.16.0`·`pyjwt 2.15.1`·`cryptography 50.0.2`가 mcp의 전이 의존으로 이미 있다 → **새 의존성 0**. uv export 해시는 플랫폼별 휠을 모두 담으므로 리눅스 설치도 같은 lock으로 `--require-hashes` **[추정: onnxruntime 1.31.0·tokenizers 0.23.3·numpy 2.5.4의 manylinux x86_64 휠이 lock에 포함 — 실행자가 `grep manylinux requirements.lock.txt`로 확인]**.
- **[사실]** 현재 코드: `snippet.by_chunk`/`by_locator`·`search._hits`·지식 결속(`knowledge.bind_sources`)·`knowledge_query.source_state`는 모두 **저장된 `units`·`versions`·`documents`만** 읽는다(원본 파일 접근 0) → 서버에서 그대로 동작. 원본을 여는 코드는 `collect.read_source`·`stream_sha256`(scan)과 `binding._read`(verify)뿐. `index.run_index(embedder=None)`은 단위에서 청크·FTS만 만든다(벡터는 `chunk_vectors`에 `(model_key, text_sha256)`로 내용 주소형) → 서버가 청크를 **재생성**하고 벡터만 받는 설계가 코드 변경 없이 성립한다. `paths.validate_home`은 `WORKMCP_HOME` 없이는 `USERPROFILE`을 요구(리눅스에서 `home_unresolvable`) → 서버는 환경변수 필수.
- **[사실]** M2 실측(이 PC): 모델 로드 +1.4 GiB, 질의 임베딩 ≈ 0.3 s(16 논리 CPU), 115청크 혼합 p50 55 ms, 24만 행 0.56 s. M1 `Limits`: 버전 하나 ≤ 50 M자·20만 단위 → 단위 전송은 **분할**이 필요하다(§3.4).

## 1. 전체 구조와 역할 분담

### 1.1 구성요소

```
회사 PC (수집기)                         Hostinger VPS (운영 서버)                  클라이언트
┌──────────────────────────┐   HTTPS    ┌─────────────────────────────────┐  HTTPS   ┌──────────────┐
│ 원본 파일 (읽기 전용)      │  push만    │ 리버스 프록시 :443 (LE 인증서)    │  MCP     │ Claude Code  │
│ workmcp scan → units      │ ────────▶ │  /workmcp/*  → 127.0.0.1:8765    │ ◀──────▶ │ (이 PC·회사PC)│
│ workmcp index → vectors   │           │ workmcp serve --http              │  토큰    │ Codex (M6)   │
│ workmcp verify (원본 재도출)│           │  /workmcp/mcp   도구 15개 (MCP 토큰) │          └──────────────┘
│ workmcp push  (업로드 토큰) │           │  /workmcp/push/* 수신 (업로드 토큰)  │
│ 데이터 홈 %USERPROFILE%\…  │           │ SQLite WAL: units·chunks·vectors·  │
│  (단위·청크·벡터·로그)      │           │   knowledge·tool_calls·deliveries   │
└──────────────────────────┘           │ bge-m3 (질의 임베딩, 유휴 해제)      │
                                       │ 데이터 홈 /home/workmcp/Motive_work │
                                       └─────────────────────────────────┘
```

- 원본 파일은 회사 PC에만 있고 어떤 경로로도 서버에 가지 않는다(와이어 스키마에 파일 바이트 필드가 없고, 테스트가 고정 — §6.4).
- 서버가 가진 것: 단위 텍스트·locator·버전 해시·청크(재생성)·벡터·지식(M4)·호출 기록. 서버가 내보내는 것: MCP 클라이언트가 요청한 조각만(`delivered_sources`).
- 수집기가 내보내는 것: 단위 텍스트·메타·벡터(push 보고서에 건수·글자 수·바이트). 그 밖 egress 0.

### 1.2 한 패키지, 두 역할 — **[결정]**

분리(두 패키지)하지 않는다. 이유: 스키마·locator·청크 규칙·결속 검사가 양쪽에 **같은 코드**여야 결속이 성립하고(서버가 청크를 같은 `CHUNK_VERSION`으로 재생성), `requirements.lock.txt` 하나로 두 설치를 같게 유지하며, 네트워크 경계 테스트 하나가 두 역할을 함께 본다. 역할은 **하위 명령과 설정**으로 갈린다.

| 역할 | 명령 | 설정(`config.toml`) | 쓰는 모듈 |
|---|---|---|---|
| 수집기(회사 PC·이 PC 개발) | `scan`·`index`·`verify`·`sources`·`doctor`·`fetch-model`/`setup --model`·**`push`** | `[[sources]]`·`[scan]`·`[index]`·**`[push] url`**(토큰은 환경변수/파일) | 기존 전부 + `push.py`·`sync.py` |
| 운영 서버(VPS) | **`serve --http HOST:PORT`**·**`token issue|list|revoke`**·**`collectors`**·`verify --stored`·`doctor`·`setup --model download` | `[server]`(기존 + `http_path`·`allowed_hosts`·`push_max_mb`)·`[search]` | 기존 `server`·`tools`·`search`·`snippet`·`knowledge*`·`store` + `remote.py`·`receive.py`·`sync.py` |
| 로컬 stdio 서버(개발·M3/M4 호환) | `serve`(stdio) | 기존 | 기존 |

## 2. 데이터 모델 (서버·수집기 공통 스키마 v5)

### 2.1 원칙

- **[결정]** 서버는 수집기 저장소의 **미러 + 서버 전용 표**다. `documents`·`versions`·`units`의 **내용**은 수집기와 같고(단위 텍스트·locator_json·text_sha256·sha256·seq·status), **id는 서버가 새로 매긴다**. 수집기 id ↔ 서버 id 대응은 `collector_documents`·`collector_versions`가 가진다. 이유: 두 수집기가 올릴 수 있고(이 PC + 회사 PC), SQLite rowid를 외부에서 지정하면 충돌·재사용 문제가 생긴다.
- **[결정]** `documents.path_key UNIQUE`(v1)는 바꾸지 않는다. 두 수집기가 **같은 절대 경로의 루트**를 올리면 서버가 `root_owned_by_other_collector`로 거부한다(`source_roots.collector_id`). 같은 사람의 두 PC는 사용자 이름이 달라 겹치지 않는다 **[추정]**; 겹치면 한쪽 수집기를 `collectors retire`(§4.6) 뒤에만 넘길 수 있다. 한계로 문서화.
- **[결정]** 청크는 서버가 재생성한다(`chunks.build_chunks`, 같은 `CHUNK_VERSION`). 수집기는 청크 텍스트를 보내지 않고 벡터만 `(model_key, text_sha256)`로 보낸다. 양쪽 `CHUNK_VERSION`이 다르면 push를 거부(`chunk_version_mismatch`: 서버를 먼저 업데이트).
- **[결정]** 지식(`entities`·`assertions`·`evidence`·`links`·`assertion_events`)은 **서버에만** 쓰인다(MCP 쓰기 도구). 수집기는 그 표를 보내지도 받지도 않는다. 근거 `evidence.version_id`는 서버 버전 id.
- **[결정]** 서버의 `scans` 표는 **push 실행 1회 = 1행**(`note='push:<collector>'`, `roots_json`=수집기 루트)으로 재사용해 `status.last_scan`·`recent_changes`(`document_events.scan_id`)가 그대로 동작한다. 수집기 쪽 scan id는 보내지 않는다.

### 2.2 마이그레이션 v5 (`store.MIGRATIONS`에 **추가**, v1~v4 불변; 설명용 DDL)

```sql
-- 수집기(업로드 주체). name은 토큰 발급 때 정함. retired_at: 더 올리지 못함(데이터는 남음).
CREATE TABLE collectors(id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL, last_push_at TEXT, retired_at TEXT, note TEXT);
-- 토큰: 평문 없음. kind 'mcp'(클라이언트) | 'push'(수집기, collector_id 필수). prefix: 식별용 앞 6자.
CREATE TABLE tokens(id INTEGER PRIMARY KEY, kind TEXT NOT NULL CHECK(kind IN ('mcp','push')),
  name TEXT NOT NULL, token_sha256 TEXT NOT NULL UNIQUE, prefix TEXT NOT NULL,
  collector_id INTEGER REFERENCES collectors(id),
  created_at TEXT NOT NULL, revoked_at TEXT, last_used_at TEXT,
  CHECK((kind = 'push') = (collector_id IS NOT NULL)));
CREATE TRIGGER tokens_update_guard BEFORE UPDATE ON tokens
  WHEN NEW.id <> OLD.id OR NEW.kind <> OLD.kind OR NEW.name <> OLD.name OR NEW.token_sha256 <> OLD.token_sha256
    OR NEW.prefix <> OLD.prefix OR NEW.collector_id IS NOT OLD.collector_id OR NEW.created_at <> OLD.created_at
    OR (OLD.revoked_at IS NOT NULL AND NEW.revoked_at IS NOT OLD.revoked_at)
  BEGIN SELECT RAISE(ABORT, 'token is append-only (revoke once, last_used_at only)'); END;
CREATE TRIGGER tokens_no_delete BEFORE DELETE ON tokens BEGIN SELECT RAISE(ABORT, 'append-only'); END;

ALTER TABLE source_roots ADD COLUMN collector_id INTEGER REFERENCES collectors(id);   -- 서버에서만 채움

-- push 실행(서버 scans 행과 1:1), 배치 멱등 기록, 분할 단위 임시 보관.
CREATE TABLE pushes(id INTEGER PRIMARY KEY, collector_id INTEGER NOT NULL REFERENCES collectors(id),
  scan_id INTEGER REFERENCES scans(id), started_at TEXT NOT NULL, finished_at TEXT,
  status TEXT NOT NULL CHECK(status IN ('running','done','aborted')),
  batches INTEGER NOT NULL DEFAULT 0, bytes_in INTEGER NOT NULL DEFAULT 0,
  counts_json TEXT NOT NULL DEFAULT '{}', client_version TEXT, note TEXT);
CREATE TABLE push_batches(batch_id TEXT PRIMARY KEY, push_id INTEGER NOT NULL REFERENCES pushes(id),
  kind TEXT NOT NULL, applied_at TEXT NOT NULL, bytes_in INTEGER NOT NULL, response_json TEXT NOT NULL);
CREATE TABLE push_parts(push_id INTEGER NOT NULL REFERENCES pushes(id), local_version_id INTEGER NOT NULL,
  part INTEGER NOT NULL, parts INTEGER NOT NULL, body_json TEXT NOT NULL, received_at TEXT NOT NULL,
  PRIMARY KEY(push_id, local_version_id, part));

-- 수집기 id ↔ 서버 id. local_*는 그 수집기 저장소의 rowid.
CREATE TABLE collector_documents(collector_id INTEGER NOT NULL REFERENCES collectors(id),
  local_document_id INTEGER NOT NULL, document_id INTEGER NOT NULL UNIQUE REFERENCES documents(id),
  PRIMARY KEY(collector_id, local_document_id));
CREATE TABLE collector_versions(collector_id INTEGER NOT NULL REFERENCES collectors(id),
  local_version_id INTEGER NOT NULL, version_id INTEGER NOT NULL UNIQUE REFERENCES versions(id),
  units_sha256 TEXT,             -- 수집기가 보낸 단위 집합 해시(§3.2); NULL = 단위 미수신
  PRIMARY KEY(collector_id, local_version_id));
```

- 수집기 홈에도 같은 v5가 적용되지만 표는 비어 있다(한 코드, 한 스키마). 수집기는 **상태 표를 두지 않는다**(§3.1).
- `tokens.token_sha256`은 `sha256(token_bytes)` hex. 평문은 발급 명령 출력 1회뿐이며 DB·로그·`tool_calls`에 없다(§6.5 테스트).

### 2.3 locator와 id

- 서버 응답의 locator `doc`는 **서버 document id**다. `path`·`sha256`·`unit`·`chars`·`text_sha256`은 수집기와 **같다**(`locator.display`는 `doc`를 인쇄하지 않는다 **[사실]** `locator.py` 222~226행). 수집기 `verify`와 맞추는 테스트는 `collector_documents`로 `doc`를 되돌린다(§5.3).
- **[제안]** M6에서 두 수집기가 실제로 공존하면 hit `doc`에 `collector` 이름을 넣는 것을 검토(결과 모양 변경 → 그때 결정). 이번에는 `status.collectors`와 `list_documents`의 `root_id`로 구분.

## 3. 동기화 프로토콜 (`workmcp push`)

### 3.1 원칙 — **[결정]**

1. **서버가 기준(authoritative state), 수집기는 상태 없음.** 수집기 쪽에 "무엇을 보냈나" 표를 두지 않는다. 매 push는 서버 상태를 읽어 차이만 보낸다. 중단·재시작·재설치·DB 복원 어느 경우에도 같은 절차로 수렴한다.
2. **멱등.** 배치 본문의 정규화 JSON SHA-256이 `batch_id`. 서버는 `push_batches`에 기록하고, 같은 `batch_id`가 다시 오면 저장된 응답을 그대로 돌려준다(적용 0). 재시도는 항상 안전하다.
3. **배치 1개 = 서버 트랜잭션 1개**(`BEGIN IMMEDIATE` … `COMMIT`). 부분 적용 없음. 실패한 배치는 응답 코드와 함께 거부되고 수집기는 보고서에 적는다(조용한 복구 없음).
4. **전송량 상한.** 배치 본문 ≤ `[server] push_max_mb`(기본 **8 MiB**, gzip 해제 후 기준, 수집기도 같은 값으로 자른다), 단위 배치는 단위 ≤ 2,000개·텍스트 ≤ 2 Mi자, 벡터 배치 ≤ 1,024개(fp32 1024차원 = 4 MiB). 실행 1회 상한 `push --max-mb N`(선택)·`--limit-docs N`.
5. **원본 파일은 보내지 않는다.** 와이어 스키마(§3.3)에는 파일 바이트·경로 밖의 파일 내용 필드가 없다. `push.py`는 `collect`·`parsers`·`binding`을 import하지 않고 원본 경로를 열지 않는다(정적·런타임 테스트, §6.4).

### 3.2 서버 상태 요약 (증분 기준)

서버와 수집기가 **같은 함수**(`sync.summary`)로 두 해시를 만든다. 입력은 저장소의 공개된 값만.

| 해시 | 입력(정렬된 줄의 SHA-256) | 뜻 |
|---|---|---|
| `documents_sha256` | 문서마다 `f"{local_doc_id}|{status}|{latest.seq}|{latest.sha256}|{latest.parse_status}|{latest.parser_version}|{units_sha256(latest)}|{superseded_count}"` | 문서·최신 버전·단위 내용이 같은가 |
| `vectors_sha256` | 대상 청크(`store.latest_chunks_sql()` + `CHUNK_VERSION`)의 `text_sha256` 중 `chunk_vectors(model_key)`에 행이 **있는** 것의 정렬 목록 | 서버가 수집기와 같은 벡터를 갖는가 |

- `units_sha256(version)` = `sha256('\n'.join(f"{ordinal}|{kind}|{locator_json}|{text_sha256}"))`. 단위 **텍스트**는 해시로만 들어간다.
- 수집기는 `GET /push/state` 한 번(응답 ≤ 1 KB)으로 두 해시·`schema_version`·`chunk_version`·`model_keys`·`collector`를 받는다. **둘 다 같으면 push 종료: 배치 0, 데이터 전송 0 바이트**(완료 조건 ③ "두 번째 push 전송 0"의 측정값: `batches == 0 and bytes_sent == 0`; GET 상태 요청 1건은 데이터 전송이 아님 — 보고서에 `state_requests 1`로 따로 센다).
- 다르면 `GET /push/state?full=1&after=<local_doc_id>`(페이지 500문서)로 문서별 요약 `{local_doc_id, status, seq, sha256, parse_status, parser_version, units_sha256, deleted_at, skip_reason, superseded_seqs:[…]}`을 받고 수집기 저장소와 비교해 차이를 만든다. 벡터는 `GET /push/state/vectors?model_key=…&after=<text_sha256>`로 **서버에 없는** `text_sha256` 목록(서버 대상 청크 중 벡터 없는 것, 정렬·페이지 5,000)을 받는다.

### 3.3 와이어 스키마 (`sync.py`; JSON, UTF-8, `Content-Encoding: gzip`)

공통 봉투: `{"protocol": 1, "collector": "<name>", "push_id": <int|null>, "batch_id": "<sha256>", "kind": "<kind>", "chunk_version": "...", "schema_version": 5, "client_version": "0.0.1", "items": [...]}`. 응답: `{"ok": true, "result": {...}} | {"ok": false, "error": {"code", "message", "retryable"}}`(도구 봉투와 같은 모양).

| `kind` | `items[]` 한 항목 | 서버 적용(트랜잭션 1개) | 응답 `result` |
|---|---|---|---|
| `begin` | `{roots: [{local_root_id, path, enabled}], counts_expected: {...}}` | `collectors.last_push_at`, `pushes`·`scans('running', note='push:<name>')` 행, 루트 소유 검사(§2.1) → `source_roots` 동기(`collector_id` 채움) | `{push_id, root_ids: {local_root_id: server_root_id}}` |
| `documents` | `{local_document_id, local_root_id, path, ext, status, skip_reason, first_seen_at, last_seen_at, deleted_at, versions: [{local_version_id, seq, sha256, size, mtime_ns, observed_at, superseded_at, parser, parser_version, encoding, parse_status, parse_error, unit_count, text_chars}]}` (단위 없음; ≤ 200문서/배치) | 문서 upsert(상태·시각·skip_reason·deleted_at·path 철자·root), 버전 행 insert 또는 허용된 열만 update(mtime_ns·parser 열·`superseded_at` NULL→값·locked→실제 sha). v1 트리거가 막는 변경(관측값 불일치)은 `version_identity_conflict`로 **그 문서만** 거부·보고. 버전마다 단위 상태 판정: 서버가 그 버전의 단위를 이미 받았고 `units_sha256`이 같음 → `have`; 같은 `sha256+parser_version`의 다른 버전이 단위를 가짐 → **서버 안에서 복사**(`collect.record`의 reuse와 같은 규칙) → `copied` + 청크 재생성; 그 밖 → `need`. `parse_status<>'ok'`·`unit_count==0`은 `none` | `{documents: {local_document_id: server_document_id}, versions: {local_version_id: {id, units: "have|copied|need|none"}}, refused: [{local_document_id, code}]}` |
| `units` | `{local_version_id, units_sha256, part, parts, units: [{ordinal, kind, locator_json, text, text_sha256}]}` (한 버전의 단위를 `parts`개로 분할; 각 ≤ 2 Mi자) | `parts==1`이면 바로, 아니면 `push_parts`에 보관 후 마지막 part에서 조립. 검사: `text_sha256 == sha256(text)` 전부, ordinal 1..n 연속, 조립 해시 == `units_sha256`, 버전이 `need` 상태. 적용: 기존 단위·청크 삭제(reparse 미러) → `units` insert → `index._chunk_version`으로 청크 생성(FTS 동기) → `collector_versions.units_sha256` 갱신 → 없는 벡터 집계 | `{version_id, units: n, chunks: n, vectors_missing: [text_sha256…]}` (`parts` 미완이면 `{received: k, of: n}`) |
| `vectors` | `{model_key, dims, items: [{text_sha256, vector_b64}]}` (`vector_b64` = fp32 LE dims×4 바이트의 base64; ≤ 1,024개) | `dims == 1024 == len/4`, 유한·단위 노름(`index.validate_vectors`) 검사 → `INSERT OR IGNORE chunk_vectors`; 배치 끝에 `meta.index_generation += 1` | `{stored: n, ignored: n, invalid: n}` |
| `events` | `{local_document_id, local_version_id|null, kind, at}` (수집기 `document_events` 중 서버에 없는 것; 수집기는 마지막 push 이후 것을 `events_after`로 서버가 알려 준 시각 뒤부터 보냄) | `document_events(scan_id=push.scan_id)` insert(서버 id로 치환; 같은 (document, version, kind, at)이 있으면 무시) | `{stored: n, ignored: n}` |
| `end` | `{counts: {...}, bytes_sent}` | `pushes`·`scans` 행 `done`·`counts_json`; `data_generation` bump; 응답에 새 요약 해시 | `{documents_sha256, vectors_sha256, vectors_missing_total}` |

- 삭제: `documents` 항목의 `status:'deleted', deleted_at` + `events`의 `deleted`. 복원: 새 버전(seq+1) + `restored`. 되돌림(A→B→A): 새 버전 행, 단위는 서버가 `copied`(전송 0). 재파싱(`scan --reparse`, 같은 seq에 새 단위): `documents` 항목의 버전 `parser_version`이 바뀌고 `units_sha256`이 달라 `need` → `units` 재전송 → 서버가 단위·청크를 **제자리에서 교체**하고 `events`의 `reparsed`로 근거 상태(`evidence_stale_after_reparse`, `source_state: changed`+`requote`)가 M4 규칙대로 동작한다.
- 지식 결속과의 맞물림: 근거는 서버 버전 id를 가리키고 `source_state`는 `documents.status`·`versions.superseded_at`을 보므로(**[사실]** `knowledge_query.source_state`), 문서 변경·삭제가 미러되면 자동으로 `changed`·`deleted`가 된다. 추가 규칙 없음. **[결정]** 서버는 수집기가 삭제한 문서의 단위·버전을 **지우지 않는다**(수집기와 같음: 옛 버전 조회·근거 보존).

### 3.4 수집기 절차 (`push.run(home, settings, token) -> report`, 의사코드)

```
state = GET /push/state                          # 토큰 → collector 확정; 스키마·chunk_version 불일치면 exit 4
mine  = sync.summary(local_db, model_key)        # 같은 함수
if state.documents_sha256 == mine.documents_sha256 and state.vectors_sha256 == mine.vectors_sha256:
    return report(batches=0, bytes_sent=0, up_to_date=True)
push_id = POST begin(roots)
remote = {} ; for page in GET /push/state?full=1: remote.update(page)      # 문서별 요약
changed = [doc for doc in local docs if remote.get(doc.id) != summary_row(doc)]   # 새·바뀐·삭제·복원·재파싱
for batch in chunks(changed, 200):   r = POST documents(batch)  → need_versions += r.versions where units == 'need'
for v in need_versions:              for part in split_units(v, 2 Mi chars): r = POST units(part)
                                     missing_vectors += r.vectors_missing
missing_vectors += GET /push/state/vectors?model_key=…        # 지난 push에서 못 보낸 것
have = [sha for sha in missing_vectors if local chunk_vectors has (model_key, sha)]
for batch in chunks(have, 1024):     POST vectors(batch)
POST events(local events after state.events_after)
final = POST end(counts, bytes_sent)
return report(…, server_summary=final, remaining_vectors=final.vectors_missing_total)
```

- 재시도: 연결 오류·5xx·`retryable` 오류는 같은 배치를 지수 백오프(1·2·4·8·16 s, 최대 5회)로 재전송(멱등). 4xx(인증·검증)는 즉시 중단, exit 1. 중단된 push(`end` 없음)는 서버에서 `running`으로 남고 다음 `begin`이 `aborted`로 닫는다(`collect.scan`의 stale running 처리와 같음).
- 로그: `<home>/logs/push-YYYYMMDD.log`에 `pushed | <path> | sha12 | units n | chars n`, `vectors | n`, `refused | <path> | code` — **텍스트 없음**(scan 로그 형식). 보고서(stdout): 아래 §3.6.
- 벡터가 없는 청크(수집기 `index`가 아직 안 돈 경우): 서버는 어휘 검색으로 답하고(`search`가 그 청크를 의미 후보에서 못 볼 뿐 **[사실]** 설계 M2), 다음 push가 보낸다. `push --require-vectors`면 벡터 없는 대상 청크가 있을 때 exit 1로 알려 준다 **[제안]**.

### 3.5 여러 수집기

- 토큰이 수집기를 정한다(`tokens.collector_id`). 각 수집기는 자기 `local_*` id 공간만 쓰며 서버 표에서 `collector_id`로 분리된다. 요약 해시는 **수집기별**로 계산한다(`GET /push/state`는 그 토큰의 수집기 범위).
- 충돌은 루트 경로 소유(§2.1)뿐. 서로 다른 수집기가 **같은 내용**(같은 sha256)을 올리면 단위는 복사(`copied`), 벡터는 `(model_key, text_sha256)` 공유 — 전송이 줄어든다.
- 수집기 폐기(`workmcp collectors retire NAME`): 토큰 폐기 + `retired_at`. 데이터는 남고 `list_documents`에 그대로 보인다(삭제는 피터가 DB를 지우는 결정).

### 4.2 인증 — **[결정]**

- **두 종류 토큰, 한 표**(`tokens`, §2.2). `mcp` 토큰은 MCP 경로만, `push` 토큰은 업로드 경로만 통한다. 교차 사용은 401(`invalid_token`).
- 토큰 = `secrets.token_urlsafe(32)`(43자, 256비트). 발급 명령이 **평문을 한 번** 인쇄하고 DB에는 `sha256`·`prefix`(앞 6자)만 둔다. 검증: 받은 토큰의 sha256으로 조회 → 행이 있고 `revoked_at IS NULL`이고 `kind`가 맞으면 통과; `hmac.compare_digest`로 hex 비교(조회가 해시 기반이라 시간 측 공격 여지가 적지만 습관으로). `last_used_at`은 분 단위로만 갱신(쓰기 폭주 방지).
- MCP 경로: SDK `TokenVerifier.verify_token(token) -> AccessToken(token='', client_id=<token name>, scopes=['mcp'])|None`. `AuthSettings(issuer_url=<서버 URL>, resource_server_url=None, required_scopes=['mcp'])` → 메타데이터 경로 없음, OAuth 서버 없음(`auth_server_provider=None`), 등록·폐기 엔드포인트 없음 **[사실]** §0.1. 세션은 만든 토큰에 묶인다(SDK).
- 업로드 경로: `remote.py`의 핸들러가 `Authorization: Bearer` 직접 검사(`kind='push'`) → `receive.apply(...)`. 실패는 401(`WWW-Authenticate: Bearer`), 종류 불일치 401, 폐기 401, 수집기 retired 403.
- 명령(서버에서, `workmcp` 사용자로):

```
workmcp token issue --kind mcp  --name claude-code-thispc      # 평문 1회 출력: "workmcp token (shown once): <43자>"
workmcp token issue --kind push --name company-pc              # 수집기 collectors 행도 만든다
workmcp token list                                             # id kind name prefix created revoked last_used (평문 없음)
workmcp token revoke <id>                                      # revoked_at 설정; 즉시 효력(캐시 없음)
workmcp token rotate <id>                                      # = issue(같은 kind/name/collector) + 옛 것 revoke; 새 평문 1회 출력
```

- 토큰 전달(서버 → 피터 → 클라이언트/수집기)은 피터가 손으로 한다(Q8). 클라이언트 쪽 보관: Claude Code 설정 파일(`~/.claude.json`)에 헤더로 들어간다 **[추정]** → 그 파일은 피터의 PC 사용자 폴더(권한은 OS에 맡김). 수집기 쪽: 환경변수 `WORKMCP_PUSH_TOKEN` 또는 `--token-file <path>`(기본 `<home>\push.token`, 홈은 저장소·동기화 폴더 밖). 토큰은 `config.toml`에 넣지 않는다(설정은 비밀 아님).
- 인증 실패 기록: 서버 stderr에 `auth refused kind=<mcp|push> reason=<missing|unknown|revoked|wrong_kind> ip=<proxy가 준 X-Forwarded-For 또는 -> 없음>` 한 줄(토큰·prefix 없음). 5분에 20회 넘으면 같은 줄을 1회만(폭주 방지). 차단(fail2ban류)은 두지 않는다(단일 사용자; 토큰 256비트).

### 4.3 TLS와 기존 서비스 공존 — **[결정] 리버스 프록시**

| 안 | 내용 | 채택 |
|---|---|---|
| (A) 기존 웹서버에 location 추가 | VPS에 nginx/caddy/apache가 이미 443을 쓰면 그 설정에 `location /workmcp/ { proxy_pass http://127.0.0.1:8765; }` 블록 1개(nginx) 또는 `handle /workmcp/* { reverse_proxy 127.0.0.1:8765 }`(caddy) 추가. 인증서: 이미 `srv1782254.hstgr.cloud`용이 있으면 재사용, 없으면 certbot/caddy로 발급(80 포트 HTTP-01) | **1순위**(조사 결과 웹서버가 있을 때) |
| (B) 새 caddy | 80/443이 비어 있으면 caddy 설치(자동 Let's Encrypt). 다른 서비스가 80/443을 쓰는데 웹서버가 아니면(예: docker가 직접 바인드) → 그 서비스 앞에 caddy를 두는 것은 **기존 서비스 변경**이라 피터 결정(Q3) | 2순위 |
| (C) 앱 직접 TLS(uvicorn ssl) | `run()` 편의 함수에 TLS 인자가 없다 **[사실]** → 직접 uvicorn 호출 + 인증서 갱신 훅 + 443 바인드 권한(또는 비표준 포트) | 하지 않음 |
| (D) 서브도메인 | `workmcp.<피터 도메인>`이 있으면 host 분리가 깔끔 — 기본 호스트 이름만 쓰기로 했으므로 경로 분리 | 피터가 원하면(Q2) |

- 프록시 설정 요지(nginx; `tools/deploy/nginx-workmcp.conf`):

```
location /workmcp/ {
    proxy_pass http://127.0.0.1:8765;          # URI 그대로(접두사 유지)
    proxy_http_version 1.1;
    proxy_set_header Host $host;               # TransportSecurity allowed_hosts 검사와 일치
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto https;
    proxy_buffering off;                       # SSE(GET 스트림)가 열려도 지연 없음
    proxy_read_timeout 300s;                   # 첫 질의 모델 로드(≤ 30 s 추정)보다 넉넉히
    client_max_body_size 16m;                  # push 배치(gzip 전) 상한보다 크게
}
```

- 평문 HTTP(80)는 프록시가 443으로 리디렉션하거나(기존 설정 따름) `/workmcp/`를 열지 않는다. 앱은 127.0.0.1에만 있으므로 80으로 앱에 닿는 길은 없다.
- TLS 버전·암호군은 프록시 기본(Let's Encrypt 권장 설정). 점검표 #2가 `openssl s_client`로 확인.

### 4.7 `get_snippet`·결과의 출처 표시

- 서버의 `get_snippet`은 이미 저장 단위로 답한다(§0.1). 원본에 접근하지 않는다는 점은 `INSTRUCTIONS`(서버 역할 문구)와 `status.role = "server"`로 알린다: **[결정]** `build_server(..., instructions=REMOTE_INSTRUCTIONS)`, 문구 "이 서버는 회사 PC 수집기가 올린 저장 텍스트(단위)로 답한다; 원본 파일은 회사 PC에만 있다. 응답의 delivered_sources가 이번 응답으로 서버를 떠난 조각의 출처 전부다. 검색 결과 없음 ≠ 회사에 그 정보가 없음."
- locator의 `path`는 회사 PC 경로 그대로(출처의 일부). `status`에 `collectors: [{name, roots: n, documents: n, last_push_at}]`, `last_push: {collector, at, documents, units, vectors}`.

### 4.8 질의 임베딩·모델 수명

- 같은 매니페스트(`models.MANIFEST['bge-m3']`, 리비전 `5617a9f6…`, SHA-256 4개) → `model_key`가 수집기와 같다(**[사실]** `index.model_key(identity)`는 매니페스트 값만의 함수) → 수집기가 보낸 벡터를 서버 질의 벡터와 비교할 수 있다.

- 수명: 기존 `Engine` 유휴 해제 + ticker(프로세스당 1회 **[사실]** §0.1). **[제안]** VPS `config.toml [search] model_idle_seconds = 1800`(첫 질의 재로드가 2 vCPU에서 길다, §7.2), `threads = 2`(`effective_threads`가 `cpu_count//2 = 1`을 주므로 명시). **[제안]** `[server] model_preload = false` 기본; 측정 뒤 메모리 여유가 있으면 true(시작 시 로드, 해제 없음).

### 5.2 `binding.verify_version(..., stored_only=True)` — **[결정]**

- 파일 읽기(`_read`)·`parsers.parse`를 건너뛰고 `derived = 저장 단위 자체`로 §5.1 ②·③을 수행, ①을 추가. 결과 `result ∈ {ok, failed}`; `unverifiable`은 없음(파일이 없으므로). 실패 코드는 기존 이름 재사용(`unit_text_sha256_mismatch`, `chunk_text_mismatch`, `chunk_set_mismatch`, `evidence:*`) + `units_sha256_mismatch`(`collector_versions.units_sha256`과 재계산 불일치). `REPARSE_STALE_CODES` 규칙(재파싱 뒤 근거는 경고)도 그대로 — 서버 `document_events`에 `reparsed`가 미러되므로 성립.
- CLI 출력은 기존 `verify_lines` + 첫 줄 `verify (stored text only; originals stay on the collector)`.

### 5.3 테스트가 보이는 일치(완료 조건 ③)

`test_remote.py::test_server_hits_bind_to_collector_originals`: 합성 묶음 → 수집기 홈 scan·index(HashEmbedder) → 로컬 HTTP 서버로 push → MCP `search` 10 hit + `get_snippet` 3건 → 각 조각 (a) 서버 `validate_locator` 일치, (b) `doc` 매핑 뒤 수집기 `validate_locator` 일치, (c) `path/sha256/unit/chars/text_sha256`가 양쪽 동일; 그리고 수집기 `binding.verify(...)['ok']`, 서버 `verify --stored` ok. 두 번째 push `batches 0`.

### 7.3 처리량·용량

- push: 배치 8 MiB·직렬 적용 → **≥ 5 MiB/s** 적용(네트워크가 병목: 회사 PC 업로드 10 Mbit/s면 1.2 MB/s). 첫 push 1만 청크 ≈ 단위 텍스트 20~30 MB + 벡터 40 MB(b64 55 MB, gzip 효과 거의 없음) ≈ **90 MB ≈ 1.5분(10 Mbit/s)** [추정]. 이후는 변경분만.
- 저장 용량(서버): 청크 1만당 단위·청크 텍스트 ≈ 30 MB, 벡터 40 MB, FTS trigram ≈ 텍스트 3배 90 MB → **≈ 160 MB/1만 청크** [추정] → 10만 청크 1.6 GB + 백업 7개. 100 GB 디스크에서 문제 없음; 조사에서 여유 확인.
- 동시 클라이언트: stateful 세션 ≤ 16(`max_sessions`); 두 클라이언트(Claude Code 이 PC + 회사 PC)와 push 1개가 동시여도 루프 직렬로 정합성 유지(SQLite 쓰기 연결 3개는 같은 스레드).
- **한계(기록)**: 루프 정지(모델 로드·큰 배치) 동안 다른 요청이 기다린다. M5 v1 §8 #37(스레드 로드)은 그대로 **다음**; VPS 실측에서 V-L4가 30 s를 넘으면 `model_preload=true`를 기본으로.

- 설계와 다르게 한 것은 이 문서 끝 "반영 기록"에 적는다.

class TokenVerifier:                       # mcp.server.auth.provider.TokenVerifier 프로토콜
    async def verify_token(self, token):   # await 없음
        row = lookup_token(self.db, sha256(token))                 # kind='mcp', revoked_at IS NULL

def build_remote(home, state, settings) -> MCPServer:
    server = build_server(home, state=state, instructions=REMOTE_INSTRUCTIONS,
                          auth=AuthSettings(issuer_url=settings.public_url, resource_server_url=None, required_scopes=['mcp']),
                          token_verifier=TokenVerifier(state.know_db_ro))
    @server.custom_route(f'{prefix}/push/{{action:path}}', methods=['GET','POST'])
    async def push_route(request):          # Bearer 직접 검사(kind='push') → receive.apply / state 조회; 413·401·403
    @server.custom_route(f'{prefix}/healthz', methods=['GET'])   # 인증 필요(Bearer 어느 종류든 유효) → {"ok":true}
    return server

def main(host, port):                       # cli serve --http
    server.run(transport="streamable-http", host="127.0.0.1", port=port, streamable_http_path=f'{prefix}/mcp',
               json_response=True, stateless_http=False, max_sessions=16,
