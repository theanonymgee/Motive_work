### 1.2 CLI (`cli.py`; 0단계에서 서명 고정)

| 명령 | 동작 | 종료 코드 |
|---|---|---|
| `workmcp index [--model bge-m3\|none] [--doc ID ...] [--limit N] [--rebuild-fts] [--gc] [--keep-history]` | 홈 검증·`ensure_home`·`open_home`·`index.lock`(scan.lock과 같은 방식, 이름만 다름) → `index.run(db, home, options, on_event)` → 요약 출력. `--model none`은 청크·FTS만(모델 없이). `--limit N`은 이번 실행에서 임베딩할 청크 수 상한(시간 묶기, 재실행으로 이어감). `--doc`은 그 문서만 | 0 완료, 2 홈, 3 잠금, 4 모델 이름 오류 |
| `workmcp search "질의" [--mode hybrid\|lexical\|semantic] [--limit 10] [--path-prefix P] [--ext .docx ...] [--since ISO] [--until ISO] [--json]` | `search.Engine(home).search(...)` → 사람용 표(순위·점수·출처 한 줄·스니펫) 또는 `--json`(M3 계약 그대로) | 0, 2, 4(빈 질의·범위 밖) |
| `workmcp fetch-model NAME --from FOLDER` | `models.import_from(NAME, FOLDER, home)` → 파일별 상태 출력. `--from` 없으면 종료 4 + "M2에서는 네트워크 다운로드를 켜지 않음; `python -m workmcp.models fetch`는 명시적 다운로드 모듈(미사용)" | 0 전부 ok, 1 아니면 |
| `workmcp verify-model [NAME]` | `models.verify(NAME, home)` 표 출력 | 0/1 |
| `workmcp doctor` | 기존 + `index: chunks N (chunk_version …), vectors M (model …), fts rows K (synced …)` 한 줄, 불일치면 경고 | 0 |

- **[결정]** `cli.py`는 `models.import_from`·`models.verify`·`models.quick_status`만 쓴다. `models.fetch`·`download_file`·`main`은 어떤 형태로도 참조하지 않는다(정적 검사 `network_functions` 유지). `import_from`은 네트워크 함수를 부르지 않으므로 오염되지 않아야 한다(테스트 §10 N-2).
- **[결정]** `search` CLI의 사람용 출력에는 스니펫이 찍힌다(사용자가 직접 보는 로컬 출력, 원문 조각이 stdout으로 나가는 것은 의도). 로그 파일에는 질의·스니펫을 쓰지 않는다(건수·시간만).
- **[결정]** `search`는 결과가 없을 때 M0 §4.2 문구("검색 결과 없음 ≠ 회사에 그 정보가 없음")를 `notice`로 낸다.

### 1.3 `config.toml` 추가 절 (모두 선택, 기본값 있음)

```toml
[index]
model = "bge-m3"          # 또는 "none"(어휘만)
embed_batch = 8           # fp32 배치. int8 모델이면 코드가 1로 강제
commit_every = 64         # 벡터 커밋 간격(청크 수)
threads = 0               # 0 = onnxruntime 기본(물리 코어). 색인 CLI용

[search]
lexical_candidates = 200
semantic_candidates = 200
max_vectors_in_memory = 250000   # 초과 시 스트리밍(§6)
threads = 0               # 0 = max(1, cpu_count//2) — 서버 두 프로세스 전제
model_idle_seconds = 600  # 유휴 해제
```

## 2. 청크 규칙 (`chunks.py`)

### 2.1 상수와 근거

| 상수 | 값 | 근거 |
|---|---|---|
| `CHUNK_TARGET` | 700자 | **[사실]**(이 PC, BGE-M3 `tokenizer.json`, Motive_vari venv `tokenizers`로 측정) 합성 한국어 업무 문장 1,008자 → 563토큰(**1.79자/토큰**), 영문 880자 → 251토큰(3.51자/토큰). 700자 한국어 ≈ 391토큰, 숫자·기호가 많아도 512 안 |
| `CHUNK_MAX` | 900자 | 900자 ≈ 503토큰 ≤ 512(`max_tokens`). 초과 분은 `OnnxEmbedder`가 잘라 임베딩하고(`enable_truncation`) `index`가 `truncated` 수를 센다 — 오류 아님 |
| `CHUNK_OVERLAP` | ≤ 140자 | 앞 청크의 **마지막 단위들**(전체 단위만, 합 ≤ 140자, 앞 청크의 전부는 아님)을 다음 청크 머리에 다시 넣는다. 문장 분할 조각은 마지막 문장 하나(≤ 140자) |
| `SNIPPET_MAX` | 600자 | M0 §4.2 |
| `CHUNK_VERSION` | `'units-700-900-140-v1'` | 상수 셋이나 알고리즘(§2.2~2.3)이 바뀌면 `v2` — 색인 키에 들어가 자동 재청크 |

- **[결정]** 글자 수는 `len(str)`(코드 포인트). 토큰 수가 아니라 글자 수로 자르는 이유: 청크 규칙이 **토크나이저(모델)와 독립**이어야 모델이 바뀌어도 청크·FTS가 그대로다. 토큰 상한 초과는 색인 보고 항목(`truncated`)으로만 보인다(§4.4).

### 2.2 알고리즘 (의사코드)

```python
@dataclass(frozen=True, slots=True)
class ChunkSpec:
    ordinal: int            # 1-based, 버전 안 순서
    unit_first: int         # units.ordinal (1-based, 포함)
    unit_last: int
    char_start: int         # "단위 텍스트들을 '\n'으로 이은 문자열" 기준 [start, end)  (M0 §3.2 chunks 주석과 같음)
    char_end: int
    text: str               # joined[char_start:char_end]  — 저장 전 단언
    def text_sha256(self): ...

def group_key(unit) -> tuple:      # 이 경계를 넘는 청크는 없다
    k = unit['kind']
    if k == 'page':        return ('page', unit['page'])
    if k == 'sheet_cell':  return ('sheet', unit['sheet'])
    if k in ('slide', 'slide_cell'): return ('slide', unit['slide'])
    if k == 'mail':        return ('part', unit['part'])
    if k == 'mail_header': return ('header',)
    if k == 'section_para': return ('section', unit['section'])
    return ('body',)                # paragraph(표 포함)·line·cell

def build_chunks(units: Sequence[tuple[int, dict, str]]) -> list[ChunkSpec]:
    """units = (ordinal, unit_dict, text) in ordinal order. 순수 함수, 결정적."""
    out, current = [], []           # current: [(ordinal, text)]
    def flush():
        if current:
            joined = '\n'.join(t for _, t in current)
            out.append(ChunkSpec(len(out)+1, current[0][0], current[-1][0], 0, len(joined), joined))
    for ordinal, unit, text in units:
        if len(text) > CHUNK_MAX:                       # 큰 단위: 혼자, 문장 분할
            flush(); current = []
            out += split_large_unit(ordinal, text, start_ordinal=len(out)+1)
            continue
        if current and (group_key(unit) != group_key(prev_unit)
                        or sum(len(t)+1 for _, t in current) + len(text) > CHUNK_TARGET):
            flush()
            current = carry(current)                    # 겹침: 끝에서부터 전체 단위만, 합 ≤ CHUNK_OVERLAP, 전부는 아님
            if group_key(unit) != group_key(prev_unit): current = []   # 그룹이 바뀌면 겹침 없음
        current.append((ordinal, text)); prev_unit = unit
    flush()
    return out
```

- `carry(current)`: 뒤에서부터 단위를 모아 `합 ≤ CHUNK_OVERLAP`이고 `len(carried) < len(current)`인 최대 접미. 단위 하나가 140자를 넘으면 겹침 없음.
- **[결정]** 겹친 청크는 전체 단위만 포함하므로 `char_start = 0`, `char_end = len(joined)`. `char_start > 0`인 청크는 문장 분할 조각(§2.3)뿐이다. 그래서 M0 §3.2의 문자 범위 정의와 `binding.verify_version` 7단계(`'\n'.join(units[first-1:last])[start:end] == text`)가 그대로 맞는다.
- **[결정]** 청크 텍스트에 `strip`·정규화를 하지 않는다(결속 재도출의 단순성). 빈 단위는 M1에서 이미 없다.
- 결과 수 상한 **[추정]**: 청크 수 ≤ 단위 수 + `text_chars / (CHUNK_TARGET − CHUNK_OVERLAP)` ≈ `max_units`(20만) + 50M/560 ≈ **29만**(버전 하나 최대, 기본 `Limits`). 저장 글자 수 ≤ `text_chars × (1 + 140/700)` = **1.2배**.

### 2.3 큰 단위의 문장 분할 (`split_large_unit`)

1. `spans = [locator.anchor(text, s) for s in locator.sentences(text)]` → 문장별 `[start, end)`(단위 텍스트 기준, 낱말 경계). 문장 사이 공백·줄바꿈은 **앞 문장의 끝에 붙인다**(`end = 다음 문장 start`, 마지막은 `len(text)`) → 조각들이 단위 텍스트를 **빈틈없이 덮는다**.
2. 문장을 순서대로 모아 합 ≤ `CHUNK_TARGET`이면 한 조각. 문장 하나가 `CHUNK_MAX`를 넘으면 그 문장을 `CHUNK_TARGET`마다 끊되, 끊는 자리는 `[TARGET−100, TARGET]` 구간의 마지막 공백(`locator._WORD` 경계), 없으면 정확히 `TARGET`.
3. 겹침: 앞 조각의 마지막 문장이 ≤ `CHUNK_OVERLAP`이면 다음 조각 머리에 포함(`char_start`를 그 문장 시작으로).
4. 각 조각 = `ChunkSpec(ordinal, u, u, start, end, text[start:end])`.

- **[사실]** `locator.sentences`·`anchor`·`_WORD`·`_LINE_BREAK`는 이미 `locator.py`에 있다(`COORD_VERSION='unit-words-sentences-v1'`). 규칙이 바뀌면 `COORD_VERSION`과 함께 `CHUNK_VERSION`도 올린다.
- 적용 대상 **[추정]**: PDF 쪽(보통 2~5천자), 긴 DOCX 문단, TXT 한 줄 JSON(M1 §13 #18이 미룬 "줄 쪼개기"가 여기서 일어난다 — 8 Mi자 한 줄도 조각 ≤ 900자로 나뉜다).

### 2.5 L-7 — hit의 출처 표현 (결정)

- **[결정]** 검색 hit는 `locator`(하나)와 `units[]`(목록)를 **둘 다** 가진다.
  - `units[]`: 청크가 덮는 단위마다 locator 하나. `chars` = 그 단위 안에서 **청크가 차지하는 범위**(전체 단위면 `[0, len]`, 문장 조각이면 `[start, end]`). 본문은 싣지 않는다(크기 상한 때문). 모두 정확한 locator라 `locator.validate`가 통과한다.
  - `locator`: **스니펫**의 locator. 스니펫은 항상 **단위 하나 안**에서 자른다(§2.6). 그래서 "모든 조각에 정확한 출처"가 스니펫 글자 단위로 성립한다.
- **[결정]** M3 `get_snippet(chunk_id)`는 청크 전체를 **단위 조각 목록**(`pieces[]: {locator, text}`)으로 돌려준다(청크 하나의 본문을 이어 붙인 문자열 하나로 주지 않음). `delivered_sources`에는 조각마다 들어간다. (M3 계약에 반영할 메모, 부록 C.)

### 2.6 스니펫 규칙 (`chunks.snippet_in_unit`) — 결정적

입력: 청크의 단위 목록(각 `(ordinal, unit, text, [cs, ce])`), 질의 토큰 목록(§5.2의 `terms`), `SNIPPET_MAX`.
1. **대상 단위 선택**: 토큰(긴 것부터, 대소문자 무시)이 처음 나타나는 단위(청크 범위 안)를 고른다. 어떤 토큰도 없으면(의미 전용 hit) 청크의 **첫 단위**.
2. **창**: 일치 위치 `m`을 중심으로 `[m − 200, m + 400)`을 단위 텍스트와 청크 범위의 교집합으로 자르고, 길이가 600을 넘으면 뒤를 자른다. 일치가 없으면 범위 앞 600자.
3. 앞뒤를 **낱말 경계**(`locator._WORD`)로 당겨 자른다(글자 중간에서 끊지 않음, 단위 길이가 600 이하면 전체).
4. `locator.make(doc, path, sha256, unit, unit_text, [start, end])` → 검증된 locator. 스니펫 = `unit_text[start:end]`.

- **[결정]** 하이라이트 표시는 하지 않는다(텍스트 원형 유지).

### 2.7 결속 검사가 청크를 재도출하는 방법 (`binding.verify_version` 7단계 강화)

- 현행 **[사실]**: 저장 청크마다 `'\n'.join(units[first-1:last])[start:end] == text`와 해시만 본다(텍스트 일관성).
- **[결정]** 추가: 그 버전의 청크 중 `chunk_version == chunks.CHUNK_VERSION`인 행 집합을 `chunks.build_chunks(재도출 단위)`의 결과와 **(ordinal, unit_first, unit_last, char_start, char_end, text_sha256) 전체 일치**로 비교한다. 차이 → `chunk_set_mismatch`(실패). 다른 `chunk_version`의 행은 현행 텍스트 검사만 하고 `chunks_other_version` 카운트에 넣는다(`index`가 지워야 할 잔재 — §4.3).
- `verify` 요약 줄의 `chunks N`은 검사한 청크 수. 완료 조건 ④ 테스트는 `index` 뒤 `verify`가 `chunks_checked == COUNT(chunks)`·`ok`임과, 모든 hit의 `locator`·`units[]`가 `binding.validate_locator`를 통과하고 스니펫 == 돌려받은 텍스트임을 함께 보인다(§10).

- **[결정]** 벡터 = 텍스트의 함수. fp32 배치에서 패딩·배치 동료가 결과를 바꾸지 않아야 내용 주소형 저장(§4.2)이 옳다. **테스트로 고정**(§10 E-4, 실모델 있을 때만): 같은 텍스트를 (a) 혼자, (b) 길이가 다른 7개와 함께 임베딩 → 코사인 ≥ 0.9999. 실패하면 `batch_size=1`로 내리고 기록한다(kakao가 int8에 한 규칙을 fp32에도 적용).
- **[결정]** 질의 임베딩은 `query=True`(BGE-M3는 접두어 없음 — 매니페스트 `query_prefix=''`). 질의는 ≤ 1,000자(§6).

### 3.2 `HashEmbedder` (테스트 전용)

- kakao 그대로(글자 2/3-gram blake2b 해시, `dims=256`, `identity.real_model=False`, `name='hash-ngram-test-only'`). 반환은 ndarray. 결정적이고 모델 파일이 없어도 돈다. **색인·검색의 모든 기능 테스트와 감사 모드(`index`·`search`)가 이것으로 돈다.** 품질 지표는 실모델로만 기록한다(§8).
- **[결정]** 실 코드 경로에서 `HashEmbedder`를 쓸 수 있는 곳은 `index.run(embedder=...)`·`search.Engine(embedder_factory=...)`의 **주입 인자**만. CLI·설정으로는 선택 불가(`--model hash` 없음).

- **[결정]** `import_from(name, source: Path, home: Path, *, log) -> dict[str, str]`:
  1. `source`는 절대 경로의 폴더. 매니페스트 파일마다 `source/<local_name>`(평면) 또는 `source/<spec.path>`(HF 트리 모양 `onnx/…`) 중 **있는 쪽**을 읽는다. 없으면 `missing_in_source`.
  2. 크기 불일치 → `size_mismatch_in_source`(복사 안 함).
  3. 대상이 이미 `ok`(크기 일치·해시 일치)면 `already_verified`(복사 안 함).
  4. `home/tmp/<name>-<file>.partial`에 1 MiB 블록으로 복사하며 **같은 블록으로 SHA-256 누적** → 끝에 해시 비교 → 일치면 `os.replace(partial, target)` → `ok`; 불일치면 `.partial` 삭제 → `sha256_mismatch_in_source`.
  5. 원본 폴더는 **읽기만**(`open(src, 'rb')`). 쓰기는 `home` 아래만.
  6. 반환 `{filename: 상태}`; CLI는 전부 `ok`일 때 종료 0.
- **[결정]** `import_from`은 `download_file`·`fetch`를 호출하지 않는다 → `network_functions(models.py)`에 들지 않음(테스트 N-2). `main`은 `fetch`를 부르므로 오염 상태 유지(쓰지 않음).
- **[결정]** 디스크: 데이터 홈에 **복사**(2.3 GB). 하드링크·원본 참조는 하지 않는다(데이터 홈 규칙 §2는 "우리 데이터는 홈 안"이고, Motive_vari 폴더는 저장소 밖이지만 다른 프로젝트의 작업 트리라 삭제·이동될 수 있다).
- **[결정]** 매니페스트는 **bge-m3 하나 유지**(M0 §6 #3 결정). `multilingual-e5-base-int8`(이미 받은 폴더 있음, kakao 매니페스트에 핀 있음 — [사실] 279 MB)은 **§6 M1 보장이 측정에서 깨질 때만** 항목을 추가해 비교 측정한다(승인 대장 "이미 받은 모델 재사용" 안, 새 다운로드 아님). 기본값 변경은 그때 총괄 결정.
- **[결정]** `models.quick_status`는 유지(크기만). `tools.status.model`과 `doctor`가 쓴다. 로드 실패 사유 코드 고정: `model_missing`, `model_unverified(<file>: <status>)`, `runtime_import_failed:<ClassName>`(ORT·tokenizers import 실패 — DLL 차단 등), `runtime_error:<ClassName>`.

### 3.4 모델 없을 때 (어휘 검색만)

- `search.Engine.embedder()`가 `models.quick_status` → `available` 거짓이면 로드 시도 없이 `None` + `semantic_note='model_missing: …'`. 있으면 `OnnxEmbedder` 로드 시도; 실패하면 위 코드 + `None`. **한 프로세스에서 실패는 한 번만 시도**하고 다음 요청부터 `semantic_note`만 낸다(재시도는 `Engine.reset()`; 서버는 재시작).
- `index --model bge-m3`에서 모델이 없으면 종료 4가 아니라 **청크·FTS만 만들고** 요약에 `vectors: skipped (model_missing)`을 적는다(종료 0). `--model none`과 결과가 같다. 이유: 어휘 검색이 모델 없이도 동작해야 한다는 완료 조건 ③.

## 4. 색인 (`index.py`, `store.py`)

### 4.1 대상·증분 규칙

- **대상 버전** = `documents.status='active'` AND `versions.superseded_at IS NULL` AND `parse_status='ok'` AND `unit_count > 0`. (= "최신 활성 버전만", §0.1)
- **[결정]** 대체(superseded)·삭제 문서의 버전은 색인에서 **빠진다**: 그 청크는 `index`가 지운다(`--keep-history`면 남김). `units`는 M1대로 보존되므로 근거(`evidence`)·`get_snippet(locator)`는 과거 버전도 읽을 수 있다. 과거 버전 **검색**은 M2 범위 밖(M3 이후 필요하면 `--keep-history` + `include_history` 필터).
- 한 버전의 처리(모두 **한 트랜잭션**, 버전마다 커밋):
  1. `EXISTS(chunks WHERE version_id=? AND chunk_version=CHUNK_VERSION)` → 청크 단계 건너뜀.
  2. 아니면 **복사 후보**: `SELECT c.version_id FROM chunks c JOIN versions s ON s.id=c.version_id WHERE s.sha256=:sha AND s.parser_version=:pv AND c.chunk_version=:cv LIMIT 1` → 있으면 `INSERT INTO chunks(...) SELECT :new, chunk_version, ordinal, unit_first, unit_last, char_start, char_end, text, text_sha256 FROM chunks WHERE version_id=:src AND chunk_version=:cv`(M1 §3.3의 단위 복사와 같은 모양, `reused_chunks`로 셈). 없으면 `units`를 읽어 `chunks.build_chunks` → `store.insert_chunks(db, version_id, specs)`(1,000행 `executemany` 배치, FTS 동시 삽입). 저장 전 `text == joined[start:end]` 단언(실패는 버그 → `index` 중단, `aborted`).
  3. 그 버전의 **다른 `chunk_version`** 행은 `store.drop_chunks(db, version_id, keep=CHUNK_VERSION)`로 지운다(규칙 변경 뒤 잔재).
- **벡터 단계**(임베더가 있을 때): 모든 대상 버전의 청크를 돈 뒤 `SELECT DISTINCT c.text_sha256, c.text FROM chunks c JOIN <대상 버전> WHERE NOT EXISTS(SELECT 1 FROM chunk_vectors v WHERE v.model_key=:mk AND v.text_sha256=c.text_sha256) ORDER BY c.version_id, c.ordinal` → 배치(`embed_batch`)로 임베딩 → `INSERT OR IGNORE INTO chunk_vectors` → **64행마다 COMMIT**(`commit_every`). `--limit N`은 이 단계의 청크 수 상한. `truncated` = `token_counts > max_tokens`인 청크 수(배치마다 토크나이저로 셈 — **[추정]** 토큰화 비용은 임베딩의 1% 미만).
- **정리 단계**: `store.drop_chunks`로 대상이 아닌 버전의 청크 전부(`--keep-history` 아니면). `--gc`: `DELETE FROM chunk_vectors WHERE text_sha256 NOT IN (SELECT text_sha256 FROM chunks)`(모든 model_key). 기본 실행에서 `--gc`는 하지 않는다(A→B→A 재사용 보존).
- 끝에 `meta`: `chunk_version`, `index_generation += 1`, `fts_synced_at = now`, `fts_rows = COUNT(chunks_fts)`(FTS 있을 때); `index_runs` 행 `done` + counts.
- **재실행**: 바뀐 것만 — 새 버전만 청크(1), 새 텍스트만 임베딩(벡터 단계의 `NOT EXISTS`), 나머지는 SQL `EXISTS`로 건너뜀. 두 번째 실행의 요약은 `chunked 0 embedded 0`이어야 한다(완료 조건 ②의 테스트).

### 4.2 내용 주소형 벡터 저장 — 왜

- **[사실]** kakao `index.py`는 `(file_sha256, chunk_version, model_key, chunk_id)`로 저장하고 `text_sha256`으로 재사용했다(`reuse_from`).
- **[결정]** 키를 `(model_key, text_sha256)`로 바꾼다. 결과: (1) 같은 문단이 여러 문서·버전에 있어도 벡터 1개, (2) 문서 편집 시 바뀐 청크만 임베딩되고 **옛 버전 청크를 지워도 벡터는 남아** A→B→A·복원에서 재임베딩 없음, (3) 청크 삭제와 벡터가 독립이라 `--reparse`·FK 충돌 없음, (4) `index_chunks`의 복잡한 existing/reused 분기가 `NOT EXISTS` 하나로 준다. 전제는 §3.1 "벡터 = 텍스트의 함수"(테스트 E-4).
- 저장 형식: `float32 little-endian` BLOB(4,096 B/벡터), 노름 1(저장 전 `l2_normalize`, 읽을 때 `from_blob` 검사: 길이·유한·노름 허용 1e-3 — kakao 그대로). float16 저장은 **채택하지 않음**: 디스크 절약(2 KB/벡터)보다 저장값의 정확·검증 단순성이 중요하고, 10만 벡터 ≈ 400 MB는 로컬 디스크에서 문제 없다. 메모리는 §6에서 fp16로 줄인다.
- 용량 **[추정]**: 청크 1개당 DB ≈ 텍스트 1.2× + 벡터 4 KB + FTS trigram(텍스트의 3~5배) → 10만 청크 ≈ 400 MB(벡터) + 70 MB(텍스트) + 200~350 MB(FTS).

### 4.3 FTS5 동기화·재생성 (L-8, `store.py`)

- **[사실]** `chunks_fts`는 외부 콘텐츠 FTS5(`content='chunks', content_rowid='id'`, trigram). 외부 콘텐츠 표는 `chunks`의 변경을 **자동으로 따라가지 않는다**; 삭제는 옛 값을 함께 주는 `'delete'` 명령이 필요하다.
- **[결정]** 트리거를 두지 않는다(대량 DELETE에서 트리거는 행마다 FTS 삭제를 돌려 느리고, FTS5가 없는 Python에서는 트리거 자체가 깨진다). 대신 청크를 쓰고 지우는 함수를 **두 개로 고정**하고 그 안에서 FTS를 함께 다룬다:
  - `store.insert_chunks(db, version_id, rows)`: `INSERT INTO chunks …` 뒤 `fts_available(db)`이면 `INSERT INTO chunks_fts(rowid, text) SELECT id, text FROM chunks WHERE version_id=? AND chunk_version=?`.
  - `store.drop_chunks(db, version_id, keep: str | None = None)`: FTS 있으면 먼저 `INSERT INTO chunks_fts(chunks_fts, rowid, text) SELECT 'delete', id, text FROM chunks WHERE version_id=? [AND chunk_version<>?]`, 그 다음 `DELETE FROM chunks …`. (벡터는 건드리지 않음.)
  - `collect.py`(`--reparse`·locked 채움)는 이제 `store.drop_chunks(db, fill)`만 부른다(직접 DELETE 삭제).
- **정적 테스트**(§10 X-3): `src/workmcp/**`에서 `chunks`·`chunks_fts`에 대한 `INSERT`/`DELETE` SQL 문자열은 `store.py`의 이 두 함수 안에만 있다.
- **재생성**: `index --rebuild-fts` → `INSERT INTO chunks_fts(chunks_fts) VALUES('rebuild')` + `meta` 갱신. 자동 조건: `index` 시작 시 `fts_available`인데 `meta.fts_rows`가 없거나(FTS 없는 Python으로 만든 DB를 FTS 있는 Python이 처음 연 경우) `COUNT(chunks_fts) != COUNT(chunks)`면 **자동 rebuild** 후 로그에 적는다.
- **상태**: `store.fts_status(db) -> {available, rows, chunks, synced_at, consistent}`. `status`·`doctor`가 보여 주고 불일치면 notice/경고 `run workmcp index --rebuild-fts`. `COUNT(*) FROM chunks_fts`는 **[추정]** 10만 행에서 수십 ms(외부 콘텐츠라 `chunks`를 세는 것과 같음) — 실측해 느리면 `meta.fts_rows`만 쓴다.
- **FTS5가 없는 Python**: `insert/drop_chunks`가 FTS 부분을 건너뛰고, 검색은 `LIKE` 대체 경로(§5.3)에 `meta.fts='none'`을 표시한다. 이 PC는 FTS5 trigram 사용 가능 **[사실]**(SQLite 3.53.1).

### 4.6 트랜잭션·잠금·재개

- `index.lock`(`store.acquire_lock(home, 'index.lock')` — 기존 `acquire_scan_lock`을 이름 매개변수화). `scan`과 `index`는 동시에 돌 수 있다(다른 표를 쓰고 WAL·`busy_timeout`). 다만 `scan`이 `--reparse`로 지우는 버전과 `index`가 청크 중인 버전이 겹치면 한쪽이 `BEGIN IMMEDIATE` 대기 → 5초 뒤 `OperationalError` → `index`는 그 버전을 건너뛰고 `skipped_locked`로 세고 계속(다음 실행에서 처리).
- 청크 단계는 버전마다 COMMIT, 벡터 단계는 64행마다 COMMIT → Ctrl-C·종료 뒤 다시 실행하면 이어 간다(`index_runs`의 `running` 행은 다음 시작 때 `aborted`로 정리, scan과 같은 규칙).
- 서버(M3)에서 `index`를 도구로 노출하는 것은 범위 밖(`refresh_sources`와 같이 M3 결정).

### 5.2 질의 변환 (trigram 어휘 검색)

- **[사실]**(이 PC 실측, SQLite 3.53.1) trigram 토크나이저는 **3자 미만 토큰을 전혀 매치하지 않는다**: `"회의록"` 매치, `"회의"`·`"계약"`·`"A사"` → 0행. 공백 포함 구는 매치한다: `"a사 계약"`(5자, 대소문자 무시) → 매치. `bm25()`·`highlight()` 동작.
- **[결정]** `search.lexical_terms(query) -> Terms`:
  1. `tokens = TOKEN.findall(query)`(kakao `TOKEN = r'[\w가-힣]+'`, 최대 64개).
  2. `long = [t for t in tokens if len(t) >= 3]`, `short = [t for t in tokens if len(t) < 3]`.
  3. MATCH 식 = **OR**로 이은 구 목록(각 구는 큰따옴표로 감싸고 안의 `"`는 `""`로 이스케이프 — FTS 구문 주입 차단):
     - 전체 질의 정규화 구(공백 하나로 접음) — 길이 ≥ 3일 때;
     - 인접 토큰 쌍 `"tok_i tok_{i+1}"` — 길이 ≥ 3일 때(짧은 토큰 둘도 `"A사 계약"`처럼 붙으면 매치됨);
     - `long`의 각 토큰.
  4. `short`는 MATCH에 넣지 않고 **보조 점수**로 쓴다: 후보 안에서 `token in text.casefold()`(포함 수 / 전체 토큰 수)를 `lexical_bonus`로 더해 **어휘 순위의 동점 정렬**에만 쓴다(점수 자체는 bm25).
- **후보 질의**: `SELECT c.id, bm25(chunks_fts) AS score FROM chunks_fts JOIN chunks c ON c.id = chunks_fts.rowid JOIN versions v … JOIN documents d … WHERE chunks_fts MATCH :expr AND <최신 활성 조건> AND <필터> ORDER BY score LIMIT :N`(N = `lexical_candidates` 200). bm25는 작을수록 좋다(음수).
- **[결정]** 띄어쓰기 변형("견적서발송" vs "견적서 발송")은 trigram이 부분적으로 흡수한다(공백을 포함한 3-gram만 어긋남). 약어·동의어(MOU↔업무협약)는 어휘로는 못 잡고 **의미 검색이 맡는다** — §8 질의 세트가 이것을 모드별로 보인다. 사전 기반 확장(kakao `category_terms`)은 하지 않는다(M0 §6 #5의 [제안] "엔티티 별칭 보너스"는 M4에 엔티티가 생기면).

### 5.3 LIKE 대체 경로

- 조건: (a) FTS5가 없는 Python(`meta.fts='none'`), 또는 (b) `long`이 비어 있고 전체 질의 구·쌍 구도 모두 3자 미만(즉 MATCH 식이 빈 경우 — 예: 질의 `"QA"`), 또는 (c) MATCH 결과가 0건이고 `short`가 있는 경우.
- `SELECT c.id FROM chunks c JOIN … WHERE <최신 활성·필터> AND (instr(lower(c.text), :t1) > 0 OR …) LIMIT 200`(토큰별 `casefold`한 값; `lower()`는 ASCII만 접지만 한글은 대소문자가 없고 질의 쪽도 같은 함수로 접는다). 점수 = 포함된 토큰 수(동점은 청크 id).
- **[결정]** 상한: 대상 청크 수 > `like_max_chunks`(200,000)이면 LIKE 경로를 **쓰지 않고** `notice`("질의가 짧아 어휘 검색을 할 수 없음 — 3자 이상 낱말을 포함해 주세요")만 낸다. 비용 **[추정]**: 20만 청크 × 700자 ≈ 140 M자 스캔 ≈ 0.5~1초(§6 S2에 포함).

### 5.4 의미 검색

- `Engine.vectors()`가 현재 `index_generation`의 행렬을 준비한다(§6.2 캐시 규칙):
  - `SELECT DISTINCT c.text_sha256, v.vector FROM chunks c JOIN chunk_vectors v ON v.model_key=:mk AND v.text_sha256=c.text_sha256 JOIN <최신 활성>` → `keys: list[str]`, `matrix: np.ndarray(float16, (n, dims))`(블록 4,096행씩 읽어 변환, `from_blob` 검사 실패 행은 건너뛰고 `invalid_vectors`에 셈).
  - 청크→행 매핑은 질의 시 SQL(`SELECT c.id, c.text_sha256 … WHERE <필터>`)로 만든다(필터가 없으면 캐시한 `chunk_rows` 사용).
- 점수: `scores = matrix.astype(float32) @ q`(블록 65,536행씩 변환해 일시 메모리 ≤ 256 MiB — fp32 임시 행렬을 한 번에 만들지 않음). 코사인 **> 0인 것만** 상위 `semantic_candidates`(200) — `np.argpartition`. 텍스트가 같은 청크들은 같은 점수(동점은 평균 순위로 흡수).
- 스트리밍 모드(행렬이 캡을 넘을 때): 캐시하지 않고 질의마다 SQL로 8,192행씩 읽어 `np.frombuffer` → 점수 → 힙(상위 200) 유지. 작업 메모리 ≤ 8,192 × 4 KB = 32 MiB + 힙. `meta.semantic.streamed = true`.
- 의미 전용 모드(`mode='semantic'`)에서도 결과 hit의 스니펫은 §2.6 규칙(토큰 없으면 첫 단위).

### 5.5 융합·정렬 (kakao `search.py` 이식)

- 어휘 순위 = 후보의 bm25 오름차순(동점은 `lexical_bonus` 내림차순 뒤 **평균 순위** `average_ranks` — [사실] kakao 함수 그대로), 의미 순위 = 코사인 내림차순(평균 순위).
- `fusion[k] = Σ 1/(60 + rank)` (RRF k=60), 두 목록의 합집합. 최종 정렬 키: `(-fusion, bm25 오름(없으면 +inf), -cosine(없으면 -inf), chunk_id)`. `hit ∈ {'both','lexical','semantic'}`.
- `mode='lexical'`은 어휘 순위만(융합 없음, 정렬 `(bm25, -bonus, id)`), `semantic`은 코사인만.
- **[결정]** 같은 문서의 인접 청크가 상위를 독식하는 문제(겹침 때문)는 M2에서 **다루지 않는다**(결과는 청크 단위, `units[]`가 범위를 보인다). M3에서 "문서별 상위 1개 접기" 옵션을 검토(부록 C).
- `SEARCH_VERSION = 'fts5-trigram-bm25+cos-rrf60-tieavg-v1'` → `meta.search_version`.

### 5.6 `Engine` (프로세스 캐시)

```python
class Engine:
    def __init__(self, home, settings: SearchSettings, *, embedder_factory=None, clock=time.monotonic): ...
    def search(self, query, *, mode='hybrid', limit=10, path_prefix=None, ext=None, since=None, until=None) -> tuple[list[dict], dict]
    def embedder(self) -> Embedder | None        # 지연 로드, 실패 사유 1회 기록(§3.4), last_used 갱신
    def vectors(self, db) -> VectorCache | None  # meta.index_generation이 바뀌면 다시 읽음
    def maybe_unload(self, now=None) -> bool     # last_used + model_idle_seconds < now → 세션·행렬 해제(gc.collect())
    def unload(self) -> None
    def status(self) -> dict                     # 모델 로드 여부·행렬 행 수·세대·메모리 추정(rows × dims × 2)
```
- 연결: `search`마다 `store.open_read(home)`(읽기 전용, 마이그레이션 없음 — M0 §3.1)를 열고 닫는다. 캐시 유효성은 `meta.index_generation`(정수) 비교 — `index` CLI가 끝날 때 +1 하므로 다른 프로세스의 변경이 다음 질의에 반영된다.
- **[결정]** 스레드 잠금은 두지 않는다. MCP stdio 서버는 asyncio 단일 스레드에서 도구를 부르고, CLI는 단일 호출. `threading`은 허용 목록에 넣지 않는다. 유휴 해제의 **주기적 호출**(타이머)은 M3 서버가 SDK의 lifespan/주기 작업으로 붙인다(부록 C); M2에서는 `maybe_unload(now)`가 순수 함수로 테스트된다.

| P3 | `unload()` 뒤 | M1·M2 | ≤ base + 200 MiB |
| P4 | 코퍼스(§8) 색인 전체 | I1·I2 | 피크 ≤ R_model + 1.5 GiB, s/청크 기록, `truncated` 수 기록 |
| P5 | 색인 중단(k번째 배치 KeyboardInterrupt 흉내) → 재실행 | I2 | `embedded` = 남은 수, 결과 벡터 집합 동일 |
| P6 | 두 번째 `index` 실행 | ②·I2 | `chunked 0 embedded 0`, 2초 이내 |
| P7 | 행렬 로드(코퍼스 ~1,000벡터)와 합성 **대량 벡터**(HashEmbedder 1024차원 30만 행을 DB에 직접 넣음) | S1 | 25만 캡 → 스트리밍 전환, 메모리 ≤ 상한 |
| P8 | 질의 세트 모드별 지연 p50/p95 | S2 | 기록(상한은 [추정] 2 s 따뜻한 혼합) |
| P9 | 적대 질의 12종 | S3 | 오류 코드 또는 정상, 예외 0 |
| P10 | 두 프로세스가 같은 DB에 동시 질의(subprocess 2개는 **테스트 코드**에서만 생성 — 패키지 코드 아님) | S5·M2 | 둘 다 정상, 각자 로드, 합 ≤ 2×M1 |

- 회귀 테스트(HashEmbedder, 작은 설정, 수 초)는 §10 표에 이름을 고정했다. 보장 문장 ↔ 테스트의 1:1 대응이 검토 기준이다(M1 교훈: "표에 없는 지점"이 없게).

### 6.4 "표 밖 지점" 금지 (정적, §10 X-3·X-4)

- 벡터를 메모리에 올리는 코드는 `search.VectorCache.load`·`stream` 두 곳만(`np.frombuffer`·`from_blob` 호출 위치를 AST로 검사: `search.py`·`index.py`의 그 함수 안에만).
- 청크 텍스트를 목록으로 모으는 코드는 `chunks.build_chunks`·`index._chunk_version`(버전 하나 범위)·`search._hits`(limit 개)만 — `fetchall()` 호출을 `index.py`·`search.py`에서 AST로 세어 허용 함수 밖에 없음을 단언(블록 읽기는 `fetchmany(n)`).

## 8. 합성 질의 세트와 실측 (완료 조건 ⑤)

### 8.1 왜 확장 묶음이 필요한가

- **[사실]** M1 합성 묶음(51개 파일)은 `LINES_KO`(5문장)·`LINES_EN`(5문장)을 모든 형식이 되풀이한다(`tests/fixtures/__init__.py`). 거의 모든 문서가 같은 문장을 담고 있어 "어느 문서가 정답인가"를 가릴 수 없다 → 기능 테스트(결속·증분)에는 쓰되 **검색 품질 지표에는 쓸 수 없다**.
- **[결정]** 검색 평가용 **확장 합성 코퍼스** `tests/fixtures/corpus.py`를 만든다. 기존 생성기(`make_text`·`make_eml`·`make_ooxml`·`make_pdf`·`make_hwp`)의 **저수준 작성 함수**를 재사용해(새 형식 코드 없음) 내용만 주제 카드에서 뽑는다. 합성 규칙은 `fixtures/__init__.py` 1~4번을 그대로 따른다(실명·실제 회사·실제 주소 없음, 예약 도메인만, `SENTINEL` 포함).

### 8.2 코퍼스 구성 (`corpus.build(seed=7) -> Corpus`)

- **주제 카드 60장**(`Topic`): `project`(합성 프로젝트 N호 / 영문 코드 `PRJ-0NN`), `customer`(가상 거래처 A~L), `person`(담당자 갑~사), `date`(2029~2032년 임의 날짜, 한글·ISO 두 표기), `amount`(원 단위 숫자, "1,234,000원"·"123만 4천원"·"1234000" 세 표기 중 문서에는 하나), `acronym`(MOU·NDA·PoC·QA·RFP·SLA·KPI·BOM 중 하나와 그 **한국어 풀이**: 업무협약·비밀유지계약·개념검증·품질보증·제안요청·서비스수준·핵심지표·자재명세), `synonym_pair`(일정↔스케줄, 거래처↔고객사, 견적↔가격제안, 회의록↔미팅노트, 지연↔연기, 검수↔인수검사 중 하나; 문서에는 한쪽만), `topic_sentinel`(그 문서에만 있는 합성 식별 구 `주제표지-NNN`), `body_sentences`(주제 전용 문장 6~12개 — 템플릿 20종에 카드 값을 채움, 한국어 80% / 영문 20%).
- **문서 60개**(카드 1장 = 문서 1개), 형식 분포: TXT 10·MD 6·DOCX 12·XLSX 6·PPTX 6·EML 8·PDF 6(영문+숫자, WinAnsi 제약)·HWPX 4·HWP 2. **방해 문서(distractor)**: 각 카드의 문장 1~2개는 다른 카드 2장의 문서에 "참고" 문장으로 섞여 들어간다(같은 어휘가 여러 문서에 — 정답을 어렵게). 단위 수 합 **[추정]** 1,500~2,500, 청크 ≈ 1,000.
- `Gold`: 질의마다 정답 `(rel_path, unit)` 목록(단위 locator의 `unit` dict) — 생성 시 "이 문장을 어느 단위에 썼는지"를 생성기가 기록한다(각 생성기의 `Expected.units_sample`과 같은 원리이지만 **모든 단위**를 돌려주는 `units_all`을 코퍼스 생성기가 받는다 — 기존 생성기에 `return_units=True` 인자를 더하는 소수정이 필요하면 C가 B(없음)·A와 조율 없이 **`corpus.py` 안에서 자체 계산**한다: 각 형식의 단위 규칙(M1 §5.8)이 결정적이므로 코퍼스가 쓴 문장 순서로 `unit`을 계산할 수 있다).

### 8.3 질의 세트 (`corpus.queries() -> list[Query]`, 약 120개)

| 범주 | 수 | 만드는 규칙 | 기대(어휘/의미) |
|---|---|---|---|
| Q1 원문 구절 | 20 | 정답 문장에서 연속 5~12자 발췌 | 어휘 강함 |
| Q2 띄어쓰기 변형 | 15 | 정답 문장의 어절 경계를 붙이거나(견적서 발송→견적서발송) 쪼갬 | 어휘 부분, 의미 보강 |

### 8.4 측정 절차 (`tests/probes/measure_search.py`, 수동 1회 + 재현 가능)

1. 임시 데이터 홈(`WORKMCP_HOME=<tmp>`, 저장소 밖) + `fetch-model bge-m3 --from <Motive_vari 폴더>`(1회).

- Windows 휠 **[사실 Motive_vari 설치본]**: 세 패키지 모두 `win_amd64` 바이너리 휠. onnxruntime은 DLL(회사 PC 앱 제어 위험 — M0 §9 #1·#6), tokenizers는 Rust 확장(`.pyd`), numpy는 C 확장. 모두 사용자 레벨 설치.
- **[결정]** 선택 의존성(`extras`)으로 빼지 않는다(단일 lock, 단순). 대신 **런타임 지연 import + 실패 격리**(§3.4 `runtime_import_failed`)로 "DLL이 막힌 회사 PC에서도 어휘 검색은 동작"을 보장한다. 회귀: `test_search_survives_runtime_import_failure`(임베더 팩토리가 `ImportError`를 내도 lexical 결과 + `semantic_note`).
- M5 오프라인 묶음: 세 휠 + 전이 휠을 `uv export` 해시 lock으로 받아 두는 절차는 M0 §9 #2 그대로. 모델은 `fetch-model --from <USB 폴더>`로 반입(이번 설계의 반입 경로가 그대로 M5 오프라인 묶음 경로다).
- 첫 `uv sync`가 앱 제어에 막히면 재시도(M0에서 관찰). numpy 2.5.4가 Python 3.12 휠을 제공함은 Motive_vari 설치로 확인됨 **[사실]**.
