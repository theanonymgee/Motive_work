## 2. 설치 명령

### 2.1 두 단계로 나누는 이유

- `workmcp setup`은 패키지 안의 명령이라 **패키지가 설치된 뒤에만** 실행된다. 그 전 단계(Python 확인·venv 생성·휠 설치)는 패키지 밖의 부트스트랩이 맡는다.
- **[결정]** 부트스트랩은 **Python 스크립트 `tools/install.py`**(표준 라이브러리만). `.ps1`은 회사 PC의 PowerShell 실행 정책(기본 `Restricted`)에 막힐 수 있고 `.cmd`는 인용·한글 경로 처리가 약하다. Python은 어차피 필요하다. `tools/`는 `src/workmcp` 밖이라 네트워크 경계 정적 검사(`src/workmcp` 대상) 범위 밖이며, 온라인 모드에서는 pip가 네트워크를 쓴다(부트스트랩은 서버가 아니다). `tools/install.py`는 `workmcp`를 import하지 않는다.
- **[결정]** 묶음 zip의 루트에도 같은 `tools/install.py`가 들어가므로 "묶음 폴더에서 더블클릭 없이 한 줄"로 시작한다.

### 2.2 `tools/install.py` (부트스트랩, 의사 명령)

```
python -I tools\install.py [--bundle DIR] [--python EXE] [--venv DIR] [--dev]
```

1. **Python 판정**: `sys.version_info[:2] == (3, 12)`인지 본다. 아니면 ① `--python EXE`, ② `--bundle DIR\python\python.exe`, ③ `py -3.12`(런처가 있을 때), ④ `%APPDATA%\uv\python\cpython-3.12*\python.exe` 순으로 찾아 **그 인터프리터로 자기 자신을 다시 실행**(`os.execv`가 아니라 `subprocess.run([exe, '-I', __file__, …])` — 부트스트랩은 패키지 밖이라 허용). 없으면 멈추고 "Python 3.12가 필요합니다: 묶음의 `python\` 폴더를 쓰거나 python.org 3.12를 사용자 설치" 안내(exit 4).
2. **venv**: `<repo>\.venv`(또는 `--venv`)가 없으면 `python -I -m venv .venv`(stdlib `venv`, pip 포함 — uv 관리 Python도 `ensurepip` 번들 있음 **[사실]**). 있으면 `pyvenv.cfg`의 `home`이 같은 Python인지 확인하고 다르면 "지우고 다시"를 안내(멱등: 같으면 그대로).
3. **설치**(venv Python 절대 경로로 실행, 환경변수 `PYTHONPATH`·`VIRTUAL_ENV`·`PIP_*`를 **비운 환경**을 명시 전달 — §2.7):
   - 오프라인(`--bundle`): `.venv\Scripts\python.exe -I -m pip install --no-index --find-links <bundle>\wheels --require-hashes -r requirements.lock.txt`, 이어서 `… -m pip install --no-index --find-links <bundle>\wheels --no-build-isolation --no-deps -e .`(또는 묶음에 든 `workmcp-<ver>-py3-none-any.whl`을 `--no-deps`로 — §3.1 결정). `setuptools==84.2.1` 휠이 `wheels\`에 있어 `--no-build-isolation` 전에 `pip install --no-index --find-links … setuptools==84.2.1`을 먼저 한다(M0 §9 #2·#17).
   - 온라인(묶음 없음): `… -m pip install --require-hashes -r requirements.lock.txt` → `… -m pip install --no-deps -e .`(격리 빌드가 setuptools를 받으려 PyPI에 간다; 막히면 `--no-build-isolation` + `pip install setuptools==84.2.1`로 재시도). `HTTPS_PROXY`는 pip가 존중한다.
   - `--dev`가 없으면 `pytest`는 설치하지 않는다 … **[결정] 아니다, 설치한다.** `requirements.lock.txt`가 pytest를 일부러 포함(CLAUDE.md: 회사 PC에서 같은 테스트를 진단으로 돌림). `--require-hashes` 파일 하나로 단순하게 간다.
4. **확인 출력**: `.venv\Scripts\python.exe -I -m workmcp --help`가 뜨면 성공, 마지막 줄에 다음 명령(`workmcp setup …`)을 **절대 경로로** 인쇄한다. 표준 출력은 사람용(서버가 아니다).
5. **종료 코드**: 0 성공, 2 Python 없음, 3 venv 불일치, 4 pip 실패(pip 출력 그대로 — 해시 불일치는 여기서 보인다).

### 2.3 `workmcp setup` (패키지 안, `src/workmcp/setup.py` + `cli.py` 하위 명령)

```
workmcp setup --home PATH [--source PATH ...] [--model-from DIR | --no-model]
              [--clients claude,codex] [--scope user|project] [--project DIR]
              [--scan] [--index] [--upgrade] [--yes]
```

실행은 항상 `<repo>\.venv\Scripts\python.exe -I -m workmcp setup …`(README·install.py 출력이 이 형태를 쓴다).

| 단계 | 동작 | 멱등성 | 출력(사람용 stdout) |
|---|---|---|---|
| 1 홈 | `--home`(필수 — 기본값 논쟁을 피함; §11 Q4)을 `paths.validate_home` 규칙으로 검증(저장소 밖·동기화 아님·UNC 아님·절대 경로·AppData 권고 밖). AppData 안이면 **경고 + 계속하지 않음**(`--yes`로만 강행). 통과 시 `ensure_home` | 있으면 그대로 | `data home: C:\Users\<user>\Motive_work (rules ok; created)` |
| 2 설정 | `<home>\config.toml`이 **없으면** 고정 템플릿으로 생성(`[[sources]]`마다 `path = "…"`(기본 문자열, `\`·`"` 이스케이프), `[index] model = "bge-m3"` 또는 `"none"`, `[search] model_idle_seconds` 기본). **있으면 고치지 않고** 누락된 `--source`를 "이 줄을 추가하세요"로 출력(M1 §2.1 "TOML 쓰기 코드 없음" 결정은 **새 파일 템플릿 1종**으로만 완화 — **[결정]**, 일반 TOML 작성기는 만들지 않음). 각 source는 `config.validate_root`로 검증(존재·절대·네트워크 여부·동기화 경고) | 파일 있으면 변경 0 | `config: written <home>\config.toml (2 sources)` / `config: exists, not changed; add: [[sources]] path = "…"` |
| 3 모델 | `--model-from DIR` → `models.import_from`(1 MiB 블록·SHA-256·원자 교체, 네트워크 함수 없음 **[사실]**) → `verify-model`과 같은 상태표. `--no-model` → `[index] model = "none"` 템플릿, 어휘 검색만 안내. 둘 다 없으면 묻지 않고 exit 4("--model-from 또는 --no-model") | 이미 검증된 파일은 `already_verified` | `model bge-m3: ok (4 files, 2,284,694,904 bytes, SHA-256 verified)` |
| 4 클라이언트 | `--scope user`(기본 **[제안]**): **등록 명령줄을 출력만** 한다(아래). 전역 파일(`~/.claude.json`, `~/.codex/config.toml`)은 **키 이름만 읽어** 같은 이름 `workmcp`가 이미 있는지 알리고(있으면 "이미 등록됨 — 명령은 `…`로 바뀜"), 쓰지 않는다. `--scope project --project DIR` → `DIR\.mcp.json`·`DIR\.codex\config.toml`을 템플릿(`doc/examples/*`와 같은 본문, 절대 경로·`-I`·`WORKMCP_HOME`)으로 **없을 때만** 생성, 있으면 내용이 같은지 비교해 다르면 diff 요약 + "`--yes`로 덮어쓰기" | 같은 내용이면 변경 0 | 아래 명령줄 2개 |
| 5 점검 | `doctor` 본문을 그대로 실행(홈·가상화·store·model·sources 줄) | — | doctor 출력 |
| 6 수집·색인 | `--scan` → `scan`(설정 sources, `scan.lock`), `--index` → `index`(모델 지연 로드, 없으면 청크·FTS만). 기본은 **하지 않음**(실제 회사 폴더 수집은 피터가 명시적으로 켜는 단계) | 증분 | scan/index 요약 줄 |
| 7 업그레이드 | `--upgrade`: §5 절차(백업 → `store.open_home`로 마이그레이션 → `doctor`). 다른 단계는 건너뜀 | — | `backup: <home>\db\backup-YYYYMMDD-vN.sqlite3` / `schema: v4 → v4 (no migration needed)` |

클라이언트 등록 명령(4단계 출력; `<PY>` = venv Python 절대 경로, `<HOME>` = 데이터 홈):

```
# Claude Code (사용자 범위) — 피터가 실행(또는 피터 승인 후 에이전트)
claude mcp add --scope user --transport stdio -e WORKMCP_HOME=<HOME> workmcp -- <PY> -I -m workmcp serve
# Codex — 피터가 실행
codex mcp add workmcp --env WORKMCP_HOME=<HOME> -- <PY> -I -m workmcp serve
# 확인
claude mcp list        # workmcp … ✔ Connected
codex mcp list
```

- **[사실]** 두 명령은 M3 §11.1에서 읽은 공식 문서 형태다(`claude mcp add` 옵션 이름 `--scope`·`-e`는 **[추정]** — 실행자가 회사 PC 전 이 PC의 `claude.exe mcp add --help`로 확인; 이 PC `claude.exe` 경로는 M3 §10.1). `timeout`(Claude 120 s)·`tool_timeout_sec`(Codex 120)는 `claude mcp add`로 못 줄 수 있어 **[추정]** 첫 의미 질의 전 `doctor`에서 모델 로드 시간을 미리 보고, 필요하면 피터가 `~/.claude.json`의 `timeout`을 손으로 넣는다(전역 파일 편집은 우리가 하지 않음).
- **[결정]** `setup`은 **프로세스를 만들지 않는다**(`claude`·`codex`·`setx` 실행 금지). 네트워크 경계 정적 검사의 프로세스 생성 금지가 패키지 전체에 적용되기 때문이고, 전역 설정 변경은 피터가 누르는 승인으로 남긴다(M3 §17 원칙 유지). `tools/install.py`만 예외(패키지 밖).
- **[결정]** `setup`은 모델 반입·`doctor`·`scan`·`index`를 기존 함수로 부른다. 새 로직은 홈 생성·템플릿 2종(`config.toml`, 클라이언트 설정)·명령줄 인쇄·업그레이드 백업만.

### 2.4 데이터 홈 기본값 (총괄 결정 요청)

- **[제안] `paths.APP_DIR` 기본을 `%USERPROFILE%\Motive_work`로 바꾼다**(M3 §10.3-2). 이유: ① 앱 가상화(MSIX)가 `%LOCALAPPDATA%` 아래 새 파일을 패키지 폴더로 돌린다(M3 §10 실측) — 기본값이 AppData 밖이면 설정 없이도 앱 안팎·두 클라이언트가 같은 홈; ② CLI(`scan`·`doctor`)와 클라이언트 `env`가 어긋날 위험이 사라짐; ③ 규칙 통과 **[사실]**(절대·로컬·저장소 밖·동기화 이름 없음; 로밍 프로필이 UNC면 `home_unc`로 거부되어 안전). 영향: `tests/test_data_paths.py`의 기본값 테스트, `CLAUDE.md`·M0 §2.1 문구. `setup`은 어차피 `--home`을 명시하고 클라이언트 `env`에 `WORKMCP_HOME`을 적으므로 기본값 변경은 "안전망"이다.
- 거부되면: `setup`이 마지막 줄에 `setx WORKMCP_HOME <HOME>`(사용자 환경변수, 관리자 불필요)을 **출력**해 피터가 실행한다.

### 2.5 `-I`·`WORKMCP_HOME`·절대 경로 (클라이언트 설정 불변 규칙, M3 §11.2 유지)

- 명령은 venv Python **절대 경로**, 인자는 `-I -m workmcp serve`(`PYTHONPATH`·사용자 site·작업 폴더 무시 — 검토 M3-4 실측 **[사실]**), `env`에 `WORKMCP_HOME` 절대 경로. `uv run`은 쓰지 않는다(추가 프로세스·네트워크 가능성, 오염).
- **[제안]** 회사 PC에 Claude Code가 **데스크톱 앱(Code 탭)**으로만 있고 터미널 `claude`가 PATH에 없으면(이 PC와 같음 — M3 §10.1 **[사실]**) `claude mcp add`를 앱이 내려받은 `claude.exe` 전체 경로로 실행하거나, 사용자 범위 대신 프로젝트 범위 `.mcp.json`(`--scope project`)으로 간다. 두 길 모두 README에 적는다.

### 2.6 되돌리기(제거)

문서 절차(코드 없음 — 삭제는 사용자의 결정):

1. 클라이언트 등록 해제: `claude mcp remove --scope user workmcp`, `codex mcp remove workmcp`(**[추정]** 명령 이름; 없으면 앱 설정 UI). 프로젝트 범위면 `.mcp.json`·`.codex\config.toml` 삭제.

3. 데이터 홈 삭제(DB·모델·로그 — **회사 자료 파생물이 여기 있다**; 피터가 지운다). `setx WORKMCP_HOME ""`로 환경변수 제거(설정했을 때).
4. 흔적 확인: `%LOCALAPPDATA%\Packages\<Claude|Codex 패키지>\LocalCache\Local\Motive_work`가 생겼는지 보고 있으면 삭제(가상화 홈이 생겼다면 설정이 잘못됐던 것).

### 2.7 `PYTHONPATH`·`VIRTUAL_ENV` 오염과 앱 가상화에 강한 방식

- **[사실]** 이 PC에서 `PYTHONPATH`가 다른 Python 3.11 venv를 가리켜 `uv run pytest`가 numpy import 오류, `doctor`가 mcp 버전을 잘못 표시(PROGRESS 2026-10-26); serve는 `-I`로 안전.
- **[결정]** M5의 모든 절차·문서 명령은 `.venv\Scripts\python.exe -I -m workmcp …` 형태만 쓴다. `uv run workmcp …`는 개발 PC 편의로 CLAUDE.md에 남지만 README·설치 절차서에는 쓰지 않는다. `tools/install.py`가 pip를 부를 때 `env={**os.environ}`에서 `PYTHONPATH`·`VIRTUAL_ENV`·`PYTHONHOME`·`PIP_*`(단 `PIP_CONFIG_FILE`·프록시 변수 `HTTP_PROXY`·`HTTPS_PROXY`·`NO_PROXY`·`REQUESTS_CA_BUNDLE`·`SSL_CERT_FILE`은 **남김** — 회사 프록시·사설 CA 때문)를 지운 환경을 전달한다.
- **[결정]** `doctor`에 **환경 진단 줄 추가**: `env: PYTHONPATH set (ignored by -I)` / `env: VIRTUAL_ENV=<path> (not this venv)` 경고, `python: <sys.executable>`이 이 저장소 venv인지(`sys.prefix` 비교) 한 줄. 테스트는 환경 dict 주입으로.
- 앱 가상화: `setup` 1단계가 AppData 안 홈을 거부(기본), `doctor` 가상화 줄(M3 §10.3-4) 유지. 회사 PC 점검표 §7에서 앱 밖 Windows Terminal·Code 탭·Codex 셸 세 곳의 `doctor` 출력 비교(M3 §10.3-6 재실행).
- 묶음 Python을 쓸 때 `install.py`가 그 Python의 `python.exe -I -c "import sys; print(sys.prefix)"`로 **옮긴 뒤에도 동작하는지** 먼저 확인한다(§3.4 재배치 검증 결과에 따라).

### 3.1 내용과 레이아웃

```
Motive_work-bundle-<ver>-<yyyymmdd>\
  README-BUNDLE.md            # 3줄: 압축 해제 → python -I tools\install.py --bundle . → workmcp setup …
  SHA256SUMS                  # 아래 모든 파일의 sha256 (sha256sum 형식)
  code\                       # git archive <commit> (추적 파일만: src, tests, tools, doc, pyproject, lock 2종, README)
  tools\install.py            # code\tools\install.py 사본(루트에서 바로 실행용)
  wheels\                     # requirements.lock.txt 전부(win_amd64/py3-none-any) + setuptools-84.2.1 + (선택) workmcp-<ver>-py3-none-any.whl
  python\cpython-3.12.13-windows-x86_64-none\   # uv 관리 Python 사본 68 MB (pip·ensurepip 포함)
Motive_work-model-bge-m3-5617a9f6\              # 별도 zip (2.28 GB)
  model.onnx  model.onnx_data  Constant_7_attr__value  tokenizer.json   # 평면 레이아웃(import_from이 읽음)
  SHA256SUMS                                      # 매니페스트 4개 해시와 동일해야 함
```

- **[결정]** 묶음을 **둘로 나눈다**(코드·휠·Python 약 150~250 MB **[추정]**; 모델 2.28 GB **[사실]**). 모델은 바뀌지 않으므로 한 번만 반입하고, 코드 묶음은 업데이트마다 작게 만든다. 매체 제약(메일 첨부 상한, USB 차단 여부)은 Q2.
- **[결정]** 프로젝트 설치는 **editable(`-e .`)이 아니라 휠**로 간다: `tools/make_bundle.py`가 `python -m build`… 는 새 의존성이므로 쓰지 않고, `pip wheel --no-deps --no-build-isolation -w wheels .`(setuptools 84.2.1이 venv에 있음)로 `workmcp-0.0.1-py3-none-any.whl`을 만든다. 회사 PC에서는 `pip install --no-index --find-links wheels --no-deps workmcp==<ver>` → 코드 폴더를 지워도 동작하고 업데이트는 휠 교체. **단** `paths.find_repo_root`가 `pyproject.toml` 조상을 못 찾으면 cwd의 `.git`을 보고 둘 다 없으면 저장소 검사 생략 **[사실]** — 휠 설치에서는 "홈이 저장소 안" 검사가 사라지지만 회사 PC에서 저장소 폴더는 묶음 압축 해제 폴더이고 `setup --home`이 그 폴더 아래를 고르지 않도록 `install.py`가 묶음 폴더 경로를 `setup`에 `--not-under`로 넘겨 **[제안]** 검사한다(단순 대안: README에 "홈을 압축 해제 폴더 안에 두지 말 것" + `doctor` 경고). 개발 PC는 계속 `-e .`(uv).
- **[사실]** `tests/`가 `code\`에 들어가므로 회사 PC에서 `python -I -m pytest -q`(venv의 pytest)가 진단으로 돈다(CLAUDE.md 의도).

### 3.2 만드는 명령 (`tools/make_bundle.py`, 이 PC에서, 의사 명령)

```
.venv\Scripts\python.exe -I tools\make_bundle.py --out D:\bundles --model-from <모델 폴더> [--python <uv Python 폴더>] [--no-model]
```

1. `git status --porcelain`이 비어 있고 HEAD가 원격과 같은지 확인(아니면 경고). `git archive --format=zip HEAD -o code.zip` → `code\`로 해제(추적 파일만 → `.mcp.json`·`.codex`·`.venv`·`.env`는 구조적으로 제외 **[사실]** .gitignore).
2. 휠: `.venv\Scripts\python.exe -I -m pip download --only-binary=:all: --platform win_amd64 --python-version 3.12 --implementation cp --abi cp312 --abi none --require-hashes -r requirements.lock.txt -d wheels` **[추정]** `--platform` 지정 시 `--only-binary=:all:`이 필수이며 `--abi`를 두 번 주는 형태가 통하는지 실행자가 확인; 단순 대안은 플랫폼 옵션 없이 이 PC(같은 win_amd64·3.12)에서 `pip download --require-hashes -r requirements.lock.txt -d wheels`(이 PC가 대상과 같은 플랫폼이라 결과가 같다). 이 PC venv에 pip가 없으면(`uv venv`는 pip를 넣지 않음 **[사실]** 관례) `uv pip install pip` 1회 또는 묶음 Python의 pip 사용. 이어 `pip download --no-deps setuptools==84.2.1 -d wheels`(해시는 `SHA256SUMS`로 고정). 마커(`sys_platform == 'win32'`·`platform_python_implementation != 'PyPy'`)가 붙은 줄은 win_amd64에서 전부 해당되어 `pywin32`·`colorama`·`cffi`·`pycparser`가 받아지고 `httpx2-jsfetch ; sys_platform == 'emscripten'`은 제외된다 **[사실]** lock 마커.
3. 프로젝트 휠: `pip wheel --no-deps --no-build-isolation -w wheels .`.
4. Python: `%APPDATA%\uv\python\cpython-3.12.13-windows-x86_64-none` 폴더를 복사(`--python` 생략 시 자동 탐색). 재배치 가능성은 §3.4에서 **먼저** 검증.
5. 모델: `--model-from` 폴더에서 매니페스트 4파일을 `models.import_from`과 같은 규칙(블록 복사·SHA-256 대조)으로 모델 zip 폴더에 복사 — `make_bundle.py`는 `src/workmcp`를 import하지 않고 해시 4개를 **파일 안에 상수로 복사**(패키지 밖 도구; `tests`가 `models.MANIFEST`와 일치를 단언).
6. `SHA256SUMS` 작성(묶음별), 전체 크기 출력, zip 2개 생성(`shutil.make_archive`; 2.28 GB는 ZIP64 — Python `zipfile`이 지원 **[사실]** stdlib).
7. 출력 예: `bundle: code 1.2 MB, wheels 96 MB, python 68 MB → Motive_work-bundle-0.0.1-20261027.zip 160 MB` / `model: 4 files 2,284,694,904 B → …-model-….zip`.

### 3.3 해시 고정

- 휠: `requirements.lock.txt`의 `--hash=sha256:`(uv export) — 설치 시 pip가 **파일마다** 대조(`--require-hashes`). `setuptools==84.2.1`·`workmcp` 휠은 lock에 없으므로 `SHA256SUMS`로 묶음 수준에서 고정하고 `install.py`가 설치 전 `SHA256SUMS`를 **전수 검증**한다(stdlib `hashlib`, 1 MiB 블록; 2.28 GB 모델은 약 10~20초 **[추정]**).
- 모델: `models.MANIFEST` SHA-256 4개(코드에 고정) — `fetch-model --from`이 복사 중 대조하고, `verify-model`이 다시 본다. `SHA256SUMS`와 매니페스트는 같은 값이어야 하며 `tests/test_bundle.py`가 단언.
- Python 사본: 폴더 전체의 파일별 해시가 `SHA256SUMS`에 들어간다(수백 파일). 출처는 "이 PC의 uv가 받은 python-build-standalone"이며 상류 서명은 묶음 안에서 재검증하지 않는다(**한계**; 피터 자신이 만든 묶음이라는 사실이 신뢰 근거).
- 코드: `git archive` 커밋 해시를 `README-BUNDLE.md`에 적는다.

## 5. 업데이트·마이그레이션 절차

### 5.1 새 버전 반입

1. 이 PC: 버전 올림(`pyproject.toml version`), 테스트·검토 통과 → `tools/make_bundle.py`(코드 묶음만; 모델 묶음은 매니페스트가 바뀔 때만) → 반입.
2. 회사 PC: **클라이언트(Claude Code 세션·Codex 앱)를 모두 닫는다** — stdio 서버는 클라이언트의 자식이라 닫히면 함께 끝난다. 확인: `Get-CimInstance Win32_Process -Filter "CommandLine LIKE '%workmcp serve%'"`가 비어 있음(**[추정]** PowerShell 5.1에서 동작).
3. 새 묶음 압축 해제 → `python -I tools\install.py --bundle .`(같은 venv에 `pip install --no-index --find-links wheels --require-hashes -r requirements.lock.txt --upgrade` + `workmcp` 휠 교체; 의존성이 안 바뀌면 `Requirement already satisfied`만).
4. `…\.venv\Scripts\python.exe -I -m workmcp setup --upgrade --home <홈>`: ① `work.sqlite3`를 **`PRAGMA wal_checkpoint(TRUNCATE)` 뒤** `db\backup-YYYYMMDD-HHMM-v<옛 schema>.sqlite3`로 복사(백업은 사용자 홈 안, 동기화 폴더 아님) ② `store.open_home`이 마이그레이션(`BEGIN IMMEDIATE`, 체크섬 불일치면 거부 exit 2) ③ `doctor` 출력(`store: … schema v5`) ④ `verify-model`(모델 변경 시).
5. 클라이언트 재시작 → `status.schema_version` 확인(M4 §14 #13).

### 5.2 잠금 중 마이그레이션 (M4 L-f, M3 N1)

- **[사실]** serve는 최신 스키마면 쓰기 잠금 없이 시작(M3 검토 v2 N1), 마이그레이션이 필요한데 다른 프로세스가 쓰기 잠금 중이면 stderr 한 줄 + **exit 3**. 클라이언트에는 "서버 시작 실패"로 보인다.
- **[결정]** 대처는 **순서**로 푼다(5.1 2단계: 모두 닫고 `setup --upgrade`가 마이그레이션을 먼저 적용). stderr 메시지를 "`another process holds the store; close every MCP client and run: <PY> -I -m workmcp setup --upgrade`"로 보강. 옛 버전 서버가 떠 있는 채 새 서버가 마이그레이션하면 옛 서버의 쿼리가 새 스키마를 만나는 상황도 피한다(append-only 마이그레이션이라 깨지진 않지만 **[추정]** 확인 비용 대신 절차로 회피).
- scan/index CLI가 돌고 있는 중에도 같다(`scan.lock`·`index.lock`은 다른 잠금; `setup --upgrade`는 두 lock 파일이 있으면 "scan/index가 실행 중 — 끝난 뒤" 안내 후 exit 3).

### 5.3 롤백

- 코드: 옛 묶음으로 3단계 재실행(`pip install … workmcp==<옛 ver>`; 의존성 lock이 달라졌으면 옛 `requirements.lock.txt`로).
- DB: 스키마는 내려가지 않는다. 새 스키마가 필요한 옛 코드는 없으므로(append-only 마이그레이션; 옛 코드는 새 테이블·인덱스를 모름) **대부분 옛 코드가 새 DB를 그대로 연다** **[추정]** — `schema_migrations`에 모르는 버전 행이 있어도 `migrate`는 자기 목록만 본다 **[사실]** store.py 361~392줄. 단 체크섬 검사는 자기 목록 버전만. 확실한 롤백은 `backup-…-v<N>.sqlite3`를 `work.sqlite3`로 되돌리기(그 사이 기록한 지식은 잃는다 — 경고).
- 모델: 바뀌지 않음.

### 5.4 서버 재시작(클라이언트별)

- Claude Code: 세션 안 `/mcp` 재연결 또는 새 세션(M4 §16 ①). Codex: 앱 재시작 또는 `/mcp`. 코드가 바뀌면 떠 있는 서버는 옛 코드다 — README·절차서에 명시.
