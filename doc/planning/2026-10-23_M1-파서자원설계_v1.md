## 0. 요약 (한 장)

- **왜 세 번 막혔나.** [사실] 상한이 "경로마다 따로"였다: 텍스트는 `TextBudget`, 단위 수는 파서 끝·디스패처 끝, 시간은 `Clock`(XML 조각·HWP 조각·PDF 쪽 사이에만), 메모리는 구조 상한 6개. 메모리를 **만드는 지점**(조각 목록·셀·공유 문자열 참조·표 셀·이름공간·PDF 방문자 텍스트·디스패처 후처리)마다 어느 상한이 막는지 명시된 표가 없어, 검토자가 표에 없는 지점을 찾을 때마다 새 우회가 됐다(v3: M1-5 공유 문자열 참조, M1-6 memoryview 조각, M1-9 PDF 폼 팬아웃, L15 URI intern, L16 표 셀 누적, 그리고 디스패처가 시계 밖).

- **단일 예산** [결정]: 디스패처가 파일 하나당 `Budget` 하나를 만들어 모든 파서에 세 번째 인자로 넘긴다. 미터 다섯: `text`(단위 글자), `unit`(단위 수, 대기 중 포함), `event`(XML 이벤트·HWP 레코드·줄·PDF 방문 — 기계 무관 시간 대리), `hold`(보관 근사 바이트: 공유 문자열 표·rels 대상·이름표), `clock`(벽시계). 새 코드 `too_large/limit_events`, `too_large/limit_memory`, `too_large/unit_chars`(단위 하나 8 Mi자, `xml_text`를 대체). 디스패처 후처리도 시계 안.

## 1. 위협 모델과 보장

### 1.1 모델 [결정]

| 항목 | 내용 |
|---|---|
| 입력 | 피터 본인의 업무 파일. 악의적 공격자는 원칙상 없다. 그러나 **우연히 이상한 파일**은 반드시 온다: 거대 문서(수십만 문단·셀), 자동 생성 문서(로그·내보내기·VML 대체본·조건부 서식 `sqref`), 손상 파일(끊긴 zip·OLE·xref), 외부에서 받은 첨부(출처 불명, 변환기 산출물) |
| 적대 수준 | **저비용 적대 파일**까지 포함한다: 검토자가 합성 생성기로 수 시간 안에 만들 수 있는 파일(검토 v1~v3의 `gen*.py` 수준 — zip 폭탄, 중첩·속성·이름 폭탄, 공유 문자열 참조 폭탄, 제어 문자 문단, 폼 XObject 팬아웃, `/Kids` 중복 참조) |
| 범위 밖 | (a) pypdf·olefile·zlib·expat **내부** 결함(각 라이브러리의 공개 상한에 의존: expat 증폭 방어, pypdf 스트림 75 MB) (b) 프로세스 격리(자식 프로세스 금지 — M0 경계) (c) 커널·파일 시스템 수준(자리표시자·공유 잠금은 §13 #6·#14로 이미 한계) (d) 파싱 결과의 **품질** |

왜 "완전 적대"가 아닌가: 비용이 크게 다르다. 완전 적대는 pypdf의 모든 디코더·폰트 처리기·olefile FAT 처리기를 우리가 감싸거나 자식 프로세스로 격리해야 하고(프로세스 생성 금지와 충돌), 퍼징 캠페인이 필요하다. 저비용 적대까지는 **예산 구조 하나**로 끝난다(§2). 두 모델의 차이는 §8 질문 1에 적었다.

### 1.2 보장 (검토 기준) [결정]

기본 `Limits`에서 `parsers.parse(data, ext, limits)` 호출 하나(디스패처 후처리 포함)에 대해:

- **G1 메모리.** 프로세스 커밋 피크 증가 ≤ **M = 4·max_text_chars + max_held_bytes + 1 KiB·max_units + F**, 기본값으로 **200 + 128 + 200 + 256 = 784 MiB**. 측정은 검토자 방식 그대로: 새 프로세스, 입력 bytes를 읽고 파서 모듈을 한 번 데운 뒤를 `base`, `K32GetProcessMemoryInfo.PeakPagefileUsage − base`. 항의 뜻: 단위 텍스트(글자당 최대 4바이트), 보관 근사 바이트, 단위당 객체 비용(실측 300~650 B, 상한 1 KiB), **F = 형식별 고정 일시 사용의 최댓값**(§1.3). pypdf **메모리는 포함**한다(한 호출 안의 텍스트는 방문자로, 스트림은 pypdf 75 MB 상한으로, 쪽 수 누적은 캐시 비우기로 묶는다 — §4). 탐침 대부분은 64 MiB 아래여야 하고(§6.3 사례별 상한), M은 상한이지 목표가 아니다.
- **G2 시간.** 벽시계 ≤ **parse_seconds + 10초**(기본 70초; 10초는 후처리·마지막 조각 여유). 예외는 **끊을 수 없는 라이브러리 호출 한 번**: pypdf 파일 열기(xref 재구성 포함)·쪽 하나의 `extract_text`가 방문자를 **부르지 않는 구간**(폰트 로드·글자 없는 연산), olefile 열기·`listdir`, `zipfile` 중앙 디렉터리, `email` 파서, HTML 태그 제거 조각 하나. 이들은 입력 크기(≤ 100 MiB)에 선형이라 [추정] 이 PC에서 수십 초, 회사 PC에서 수 분을 넘지 않는다. 또한 **같은 파일은 같은 기계와 무관하게 같은 코드로 거부**되도록 `limit_events`가 `parse_time`보다 먼저 걸리게 기본값을 둔다(§2.3).
- **G3 상태.** 예외 없이 고정 코드(§5.6 집합 + 새 코드 3개)로 끝난다. `MemoryError`·`RecursionError`도 `failed/exception:<Class>`로 격리된다(현행 유지, `__init__.py:213-214`). 디스패처는 절대 예외를 내지 않는다.
- **G4 오거부 없음.** §6.4의 정상 문서 집합(합성 묶음 51개 + 검토 v3 §1.8 `normal_big` 4종 + 회귀 사례 9건)이 모두 `ok`이고 단위 수가 변하지 않는다. 특히 파트 어느 위치의 1 MiB 이하 시작 태그·주석·PI는 통과한다(M1-7).

## 2. 단일 예산 `Budget`

### 2.1 원칙 [결정]

1. **파일 하나 = 예산 하나.** 디스패처 `parsers.parse`가 `Budget(limits)`를 만들어 파서에 넘기고, 파서가 끝난 뒤 **후처리도 같은 예산의 시계 안**에서 한다. 파서는 더 이상 `Clock`·`TextBudget`을 스스로 만들지 않는다.
2. **메모리를 만드는 순간 차감.** 텍스트 조각을 목록에 넣을 때, 단위(또는 단위가 될 항목)를 목록에 넣을 때, 파싱 끝까지 보관할 표(공유 문자열·rels 대상·시트 이름)에 넣을 때, 이벤트·레코드·줄을 처리할 때. "끝나고 세기"는 없다.
3. **참조로 재사용되는 텍스트는 단위가 그것을 가리킬 때 차감**(XLSX 공유 문자열 → 셀 단위마다 `len`).
4. **대기 중인 것도 단위 수에 든다**(DOCX `found`, HWPX `found`, PPTX `frame` 셀).
5. **보관 미터는 보관 기간과 같다**: 파싱 끝까지 들고 있는 것만 `hold`, 파트가 끝나면 사라지는 것(expat 이름표)은 `release`. 그 밖의 일시 객체는 **기존 구조 상한으로 묶였음을 표에 적는다**(§3).
6. **표 밖 지점 금지.** `src/workmcp/parsers/**`에서 `list.append`·`+=`·`join`·`bytearray`·`dict[...] =`로 문서 내용을 담는 지점은 모두 §3의 어느 행이어야 한다. 정적 테스트(§6.2 S1)가 "append/extend/+= 호출이 있는 함수 ↔ 그 함수 안의 `budget.` 호출"을 대조한다.

### 2.2 API (의사코드, `parsers/_container.py`) [결정]

```python
class Budget:
    """One file's resource budget; the dispatcher makes it and every parser charges it."""
    __slots__ = ('limits', 'deadline', 'text_left', 'units_left', 'events_left', 'held_left', '_tick')

    def __init__(self, limits):
        self.limits = limits
        self.deadline = time.monotonic() + limits.parse_seconds
        self.text_left, self.units_left = limits.max_text_chars, limits.max_units
        self.events_left, self.held_left = limits.max_events, limits.max_held_bytes
        self._tick = _TICK                      # events between two clock reads (4096)

    def clock(self):                            # too_large/parse_time
        if time.monotonic() > self.deadline: raise ParseFailure('too_large', 'parse_time')

    def text(self, chars):                      # too_large/limit_chars — unit text, counted when a piece is kept
        self.text_left -= chars
        if self.text_left < 0: raise ParseFailure('too_large', 'limit_chars')

    def unit(self, count=1):                    # too_large/limit_units — units made or waiting to be made
        self.units_left -= count
        if self.units_left < 0: raise ParseFailure('too_large', 'limit_units')

    def event(self, count=1):                   # too_large/limit_events; reads the clock every _TICK events
        self.events_left -= count
        if self.events_left < 0: raise ParseFailure('too_large', 'limit_events')
        self._tick -= count
        if self._tick <= 0:
            self._tick = _TICK
            self.clock()

    def hold(self, objects=1, chars=0):         # too_large/limit_memory — kept until the parse ends
        self.held_left -= _OBJECT_BYTES * objects + 4 * chars      # 256 B per object, 4 B per character
        if self.held_left < 0: raise ParseFailure('too_large', 'limit_memory')

    def release(self, objects=1, chars=0):      # only for XmlStream's per-part name table (try/finally)
        self.held_left += _OBJECT_BYTES * objects + 4 * chars
```

- `text`·`unit`·`hold`는 단조 증가(공유 문자열 표만 `hold`, 이름표만 `release`). 잘못 차감하면 **거부가 보수적이 될 뿐** 메모리가 새지 않는다(안전한 방향). 거꾸로 `release`를 잘못 쓰면 샌다 — 그래서 `release`는 `XmlStream` 한 곳만 쓴다(정적 테스트 S2).
- 근사 바이트 모델 [추정]: 객체 256 B(memoryview 184, dict ≤ 5키 232, tuple·list·str 헤더 ≤ 64 → 상한), 글자 4 B(UCS-4 상한). 실제는 한글 2 B·ASCII 1 B이므로 모델이 2~4배 과대 — 과대는 G1 보장 쪽으로 안전하고 정상 문서에는 닿지 않는다(§6.4).
- 시계는 `event()` 4,096번마다 한 번(`time.monotonic` ≈ 50 ns, 이벤트당 0.55 µs이니 부담 < 1%). XML 조각마다는 `event(len(events))`로 자연히 포함된다. 파서가 긴 라이브러리 호출 앞뒤에는 `budget.clock()`을 직접 부른다.

### 2.3 `Limits` 필드·코드·기본값 [결정]

| 필드 | 기본값 | 근거 |
|---|---|---|
| `max_events` (새) | 50,000,000 | [사실] 이 PC 0.55 µs/이벤트 → 약 28초, 회사 PC(2배 느림) 약 55초 < 60초. 정상 대형 문서는 수백만 이벤트(`normal_big.xlsx` 15만 셀 ≈ 150만). 검토 v3 `docx_empty20M`(4천만 이벤트, 31.5초 ok)은 통과, `xlsx_empty`(빈 `<c/>` 3천만 = 6천만 이벤트)는 `parse_time` 60초 대신 **`limit_events`로 기계 무관하게** 거부 |
| `max_held_bytes` (새) | 128 MiB | 공유 문자열 표 모델 4 B/자 → 32 Mi자(실제 한글 16 Mi자 ≈ 셀 15만 개 × 100자)로 충분. rels 대상·시트 이름은 KB 단위 |

### 2.4 파서 계약 변경 [결정]

- `parse(data: bytes, limits: Limits, budget: Budget) -> tuple[list[Unit], str | None]`. `Parser.parse`의 타입도 3인자. `text.parse_csv`·`hwp.parse_hwpx`도 같다.
- 디스패처(`__init__.py:195-225`) 순서: 빈 파일·`file_bytes`·`sniff` → `budget = _container.Budget(limits)`(`_container`는 `sniff`처럼 함수 안에서 import — 순환 import 없음) → `parser.parse(data, limits, budget)` → **후처리**: 단위마다 `_unit_key` 검사하되 locator JSON 문자열을 목록에 쌓지 않고 `hashlib.sha256(unit_json).digest()`를 집합에 넣어 중복을 본다(1,000열 CSV의 locator JSON ≈ 5 KB × 20만 = 1 GB를 막음, D1), 1,024단위마다 `budget.clock()`; `len(units) > max_units`·텍스트 합 검사는 **남겨 둔다**(파서가 차감을 빠뜨린 경우의 2차 방어; 통과한 결과는 이미 예산 안이라 비용은 O(단위)).
- `TextBudget`·`Clock` 클래스 삭제. 테스트의 `fake_clock`(`tests/test_parsers_pdf_hwp.py:353`)은 `Budget.clock`을 감싸도록 바꾼다.
- 파서 버전: 거부 경계가 바뀌므로 **모두** 올린다 — `docx-4`, `pptx-4`, `xlsx-4`, `hwpx-4`, `hwp-4/olefile-0.47`, `pdf-3/pypdf-6.10.0`, `text-2`, `csv-2`, `eml-3`(`verify`가 옛 ok 버전을 새 코드로 다시 파싱해 `too_large`가 나오면 `parser_version_mismatch`로 격리돼야 하므로 버전 상향이 필수).

## 4. PDF 규칙

### 4.1 방문자 중단 [결정]

```python
class _Stop(Exception):            # module-private: carries a ParseFailure out of pypdf's swallowing
    def __init__(self, failure): self.failure = failure

def _page_text(page, budget):
    seen, stopped = 0, None                       # chars the visitor has seen on this page; first failure
    most = min(budget.limits.max_unit_chars, budget.text_left)
    def visit(text, cm, tm, font, size):
        nonlocal seen, stopped
        if stopped is not None: raise stopped     # every later form stops at once
        seen += len(text)
        try:
            budget.event()                         # events + clock (every 4096 visits)
            if seen > most:
                raise ParseFailure('too_large', 'unit_chars' if most < budget.text_left else 'limit_chars')
        except ParseFailure as failure:
            stopped = _Stop(failure); raise stopped
    try:
        text = page.extract_text(visitor_text=visit)
    except _Stop as stop:                          # raised at page level (outside pypdf's try)
        raise stop.failure from None
    if stopped is not None:                        # swallowed inside a form, then returned normally
        raise stopped.failure from None
    return text
```

- [사실] pypdf 6.10.0 `_page.py:1768-1819`: `Do` 연산마다 방문자를 try **밖**에서 부르고(`:1771`), 폼 `extract_xform_text`는 `except Exception`(`:1811`)으로 삼킨 뒤 `logger_warning`(우리 로거는 `CRITICAL`·전파 없음 `pdf.py:24-27`)만 남긴다. 그래서 폼 안에서 난 예외는 부모 폼에서 삼켜지지만, 다음 `Do`의 방문자 호출(`:1771`)이 다시 던져 **각 수준에서 형제 폼마다 한 번씩** 즉시 올라온다(폼 10개 × 7수준 = 예외 약 70번 → 검토 실측 1.0초). 쪽 수준의 방문자 호출(`:1771, 1782, 1804, 1826`, `_text_extractor.py:208, 257, 284`)은 어떤 try에도 싸이지 않아 **그대로 빠져나온다** → 두 경로 모두 처리한다(위 코드).
- 방문자가 받은 글자는 중첩 수준마다 다시 보고된다(`:1804`가 폼 결과 전체를 다시 넘김) → `seen`은 실제 텍스트의 상한이며 pypdf가 동시에 들고 있는 문자열 합과 비슷하다([추정] 수준 L 팬아웃에서 live 문자열 ≈ Σ 수준별 부분 출력). 그러므로 `seen`으로 끊으면 **메모리도** `most × 4 B` 안이다.
- 쪽 하나의 텍스트 상한 `max_unit_chars`(8 Mi): PDF 쪽은 단위 하나이므로 DOCX 문단과 같은 규칙. 정상 PDF 한 쪽 8 Mi자는 없다([추정] 빽빽한 A4 한 쪽 ≈ 5,000자). 초과는 `unit_chars`.
- 폰트 로드·`/Resources` 처리·글자 없는 연산 구간은 방문자가 없다 → 그 시간은 G2의 예외(끊을 수 없음). 메모리는 F4로 묶인다.

### 4.3 사전 순회 (열기 직후, `reader.pages` 전) [결정]

```python
def _count_pages(reader, limits, budget):
    root = reader.root_object['/Pages'].get_object(); seen_nodes = set(); count = 0
    stack = [root]
    while stack:
        node = stack.pop(); budget.event()
        ref = getattr(node, 'indirect_reference', None)
        if ref is not None:
            key = (ref.idnum, ref.generation)
            if key in seen_nodes: raise ParseFailure('failed', 'pdf_read_error')   # a cycle in /Pages
            seen_nodes.add(key)
        if node.get('/Type') == '/Pages' or '/Kids' in node:
            for kid in node['/Kids']:  stack.append(kid.get_object())   # references counted as they are met
        else:
            count += 1
            if count > limits.pdf_max_pages: raise ParseFailure('too_large', 'pdf_count')
    return count
```

- 중복 참조(`/Kids [1 0 R × N]`)도 하나씩 세므로 N > 2,000이면 `pdf_count`로 끝난다(pypdf는 `_flatten`에서 N개의 `PageObject`를 만들었을 것). `/Count`는 믿지 않는다. 노드 객체는 pypdf 캐시에 들어가지만 **서로 다른 객체 수**는 파일에 비례(≤ 2,000 + 노드).
- **`/Parent` 고리 검사**(F5): 쪽마다 `extract_text` 전에 `/Resources`가 나올 때까지 `/Parent`를 최대 64단 따라가고, 고리거나 64단 안에 없으면 그 쪽은 텍스트 없음으로 건너뛴다(pypdf `_page.py:1698-1700`은 상한 없는 `while`).
- 실행자는 `PageObject`·`root_object`·`indirect_reference`가 pypdf 6.10.0 공개 속성임을 확인한다(`_doc_common.py:1190-1197`에서 같은 속성을 쓴다). 버전이 바뀌면 `parser_version`이 바뀌어 재파싱된다.

### 4.4 쪽 사이 디코드 캐시 비우기 [결정, 2단계]

1. 쪽이 끝나면 그 쪽의 `/Contents`(스트림 또는 배열의 각 스트림)와 `/Resources/XObject`의 각 항목(한 단계)에 대해 `obj.decoded_self = None`([사실] `EncodedStreamObject` 공개 속성, `_data_structures.py:1107`).
2. §6.1 N3 실측에서 쪽 수에 비례해 피크가 계속 늘면(중첩 폼·폰트 스트림 캐시) `reader.resolved_objects.clear()`를 쪽마다 호출하고 `reader.pages[number]`를 다시 얻는다([사실] `_reader.py:130` 공개 속성; `flattened_pages`의 `PageObject`는 미해결 참조를 들고 있어 다시 해결됨). 2단계를 쓰면 고정 묶음 PDF 전부의 결과가 같음을 `test_parsers_are_deterministic`으로 확인한다.

## 5. M1-7 — 붙든 마크업을 정확히 재는 방법

### 5.1 현행의 오류 [사실]

`_container.py:248` `fed - parser.CurrentByteIndex > max_markup`. pyexpat은 `Parse` 호출이 이벤트를 하나도 내지 않으면 `CurrentByteIndex`를 `-1`로 준다(검토 v3 §1.8 `markup_dbg.py`: `held 97779713 bytes after feeding 97779712 (CurrentByteIndex -1)`). 그러면 "붙든 바이트"가 파트 앞부터 먹인 전체가 되어, 파트 1 MiB 뒤에서는 약 128 KiB(조각 두 개)부터 거부한다. `CurrentByteIndex`를 콜백 안에서 읽어 기억하는 방식은 이벤트마다 속성 접근 비용이 들고, 이벤트 **시작** 위치만 알려 주므로 마지막 토큰 길이만큼(최대 1 MiB) 과대 계산이 남는다. → `CurrentByteIndex`를 쓰지 않는다.

### 5.2 조용한 조각 세기 [결정]

- `XmlStream.__iter__`에서 64 KiB 조각을 `Parse`한 뒤 **이번 호출에서 처리기가 한 번이라도 불렸는지**를 본다(`events`가 비어 있지 않거나 `progress` 플래그). 불리지 않은 연속 조각 수 `quiet`를 세고, `quiet * 65536 > xml_max_markup_bytes`(기본 1 MiB → `quiet ≥ 17`)면 `too_large/xml_markup`. 이벤트가 하나라도 나오면 `quiet = 0`.
- 진행 신호를 내는 처리기: 기존 start/end/character 외에 `CommentHandler`, `ProcessingInstructionHandler`, `XmlDeclHandler`, `DefaultHandlerExpand`(프롤로그·에필로그 공백, 그 밖의 미처리 데이터). 이들은 `progress = True`만 두고 이벤트를 만들지 않는다. [사실](설계자 실측, 이 PC Python 3.12.13·expat 2.7.4, 64 KiB 조각) `buffer_text=True`여도 긴 텍스트 노드는 `Parse` 호출마다 TEXT 하나(65533·65536·65536·3), 루트 뒤 공백 192 KiB는 `DefaultHandlerExpand`가 조각마다(65532·65536·65536·4), 주석은 끝나는 조각에서 한 번. DTD는 그 전에 거부된다.
- **재파싱 유예를 끈다** [결정]: `parser.SetReparseDeferralEnabled(False)`(pyexpat, Python ≥ 3.12.3; 이 PC에 있음 [사실]). [사실] expat ≥ 2.6은 조각 앞이 끝나지 않은 토큰이면 "미파싱 바이트가 지난 시도의 2배가 될 때까지" 파싱 자체를 미룬다(CVE-2023-52425 완화). 그래서 유예가 켜진 채로는 토큰이 끝난 조각에서도 이벤트가 나오지 않을 수 있고(검토 v3가 본 `CurrentByteIndex -1`의 원인), 조용한 조각 수가 정렬에 따라 1개 더 나온다. 유예를 끄면 토큰이 끝나는 조각에서 바로 이벤트가 난다. 비용: 토큰 하나를 조각마다 다시 토큰화 → 1 MiB 토큰에 약 8.5 MiB 재스캔, 실측 1 MiB 토큰 32개 0.15초 → 0.27초. 우리 상한(1.125 MiB에서 끊음)이 2차 폭증을 막는다 — 128 MiB 파트가 모두 1 MiB 토큰이어도 [추정] 약 1.3 GiB 스캔 ≈ 1~2초. 속성이 없는 Python(회사 PC 포터블 묶음이 3.12.3 미만일 때)에서는 유예를 켠 채로 두되, 1 MiB가 유예 시도 격자(64 KiB × 2^k)에 놓여 있어 "L < 1 MiB 통과"는 유지되고 L = 1 MiB 정확히는 정렬에 따라 거부될 수 있다(`hasattr`로 분기, 테스트는 두 경로 모두).
- **정확성**: 토큰 길이 L, 조각 크기 B = 65536. 토큰이 조각 경계에서 시작하면 L/B개 조각을 덮고 마지막 `>`가 있는 조각에서 이벤트가 나므로 조용한 조각 = ⌈L/B⌉ − 1; 조각 중간(오프셋 o)에서 시작하면 ⌊(L − (B − o))/B⌋ ≤ ⌊L/B⌋. 따라서 **L ≤ 16B = 1 MiB면 quiet ≤ 16 → 항상 통과**, quiet ≥ 17이면 L ≥ 17B > 1 MiB → **거짓 거부 없음**. 거꾸로 L ≥ 18B = 1.125 MiB면 어느 정렬에서도 quiet ≥ 17 → **항상 거부**. 1 MiB < L < 1.125 MiB는 정렬에 따라 다르다(문서화). 위치(파트 몇 MB 지점)와 **무관**하다. [사실] 설계자 실측(유예 끔, 토큰 앞 텍스트 0·1·1,000·65,529 B): L = 1 MiB − 100 B → quiet 14~15, 1 MiB + 100 B → 15~16, 1.0625 MiB + 100 B → 16~17, 1.125 MiB + 100 B → 17~18. 유예 켬: 각각 14~16, 16~17, 17~18, 18~19.
- 메모리: expat은 끝나지 않은 토큰을 내부 버퍼에 두고 두 배씩 키운다 → 거부 시점에 ≤ 18 조각 ≈ 1.125 MiB, 버퍼 배수 2 → 2.25 MiB [추정]; 기존 테스트의 `peak < 4 MiB` 유지.
- `Limits` 주석·설계 문구를 "끝나지 않은 마크업 하나 1 MiB(64 KiB 조각 단위로 재므로 1 MiB 초과 ~1.125 MiB는 정렬에 따라 통과할 수 있음)"로 고친다.

### 7.1 순서 이유

0단계가 끝나야 모든 파서의 시그니처가 바뀌므로 1~5는 그 뒤. 1~5는 서로 다른 파일이지만 실행자가 한 명이라 순서대로. 4(PDF)는 실측(N3)에 따라 분기하므로 중간에 둔다. 6에서 버전을 한꺼번에 올려 테스트 fixture 기대값을 한 번만 고친다.

### 7.2 금지·주의

- 라이브러리 예외 메시지는 저장·로그하지 않는다(현행). `_Stop`은 `pdf.py` 밖으로 나가지 않는다.
- `release`는 `XmlStream` 한 곳. 새 `Limits` 필드는 `config.toml`에 노출하지 않는다.
- 파서는 경로를 받지 않는다(현행, `test_readonly` 유지). 탐침 생성 파일은 임시 폴더에만.
- 정적 쓰기 검사(`test_readonly.py`)는 `bytearray`·`memoryview` 사용을 막지 않는다 — 확인만.

### 7.3 허용 목록(`tests/test_network_boundary.py`) 변경

- **필수: 없음.** `Budget`은 `_container.py`(`time` 허용됨), 디스패처 digest는 `hashlib`(공통 허용), `pdf.py`·`text.py`·`eml.py`·`hwp.py`는 새 import 없음(`ast`는 테스트 쪽).
- **선택**(§3.11 P5·§4.2 `pdf_stream` 코드화를 택하면): `'parsers/pdf.py'`에 `'pypdf.errors.LimitReachedError'` 1줄 추가. [제안] 택한다 — `failed/exception:LimitReachedError`는 "파서 버그"처럼 읽히는데 실제는 상한이다.

## 8. 피터에게 물을 것 (둘 다 추천안으로 진행 가능, 막힘 아님)

1. **위협 모델을 "우연 + 저비용 적대"로 둔다(§1.1).** 대안 "완전 적대"는 (a) 파서를 자식 프로세스에서 돌려 메모리·시간을 OS가 끊게 하는 것(M0의 프로세스 생성 금지를 바꿔야 함, 회사 PC 보안 소프트웨어와의 마찰 가능)과 (b) pypdf·olefile 내부 퍼징(수일)을 뜻한다. 비용은 (a)가 M1에 1~2일 + 경계 테스트 재설계, (b)는 M1 범위 밖. **추천: 현 모델.** 실제 회사 문서는 M5에서 다시 본다.
2. **단위 하나의 텍스트 상한 8 Mi자를 PDF 쪽·TXT 줄에도 적용한다(§2.3).** 영향: 한 줄이 800만 자를 넘는 TXT(압축되지 않은 한 줄 JSON·로그 덤프)와 한 쪽 800만 자 PDF는 `too_large/unit_chars`로 색인에서 빠진다. 대안은 TXT만 50 M자(파일 전체 상한)까지 허용 — 그러면 TXT 한 줄 단위가 최대 200 MiB가 되어 G1의 F를 400 MiB로 올려야 한다. **추천: 8 Mi 통일.** 그런 파일이 실제로 있으면 M2 청크 단계에서 줄을 쪼개는 쪽이 맞다.
