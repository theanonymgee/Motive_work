### 0.2 실행 규칙

1. 승인 단계 **A → B → C → D → E → F** 순서. 각 단계 앞 "승인 단계" 줄이 그 단계 승인을 뜻한다. 앞 단계 승인이 뒤 단계 승인을 포함하지 않는다.
2. 단계를 시작하기 전에 피터에게 한 줄로 알린다: 어느 단계, 무엇이 바뀌는가(표 0.3), 되돌리는 법. **"예"를 받은 뒤** 첫 명령을 실행한다. 승인은 그 세션·그 단계에만 해당한다.
3. 에이전트가 SSH로 실행하면 **명령은 한 번에 하나**(또는 같은 목적의 짧은 묶음), 출력은 그대로 이 PC에 저장한다(`doc/validation/`에 요약만; 비밀값이 섞였는지 먼저 본다).
4. **토큰 평문은 에이전트 화면에 나오면 안 된다.** 발급(C-4)·등록(F-1)은 "피터 직접" 표시가 있는 대로 한다. 출력에 토큰이 보이면 즉시 멈추고 `token rotate`.
5. 회사 자료는 서버에 올리지 않는다. 이 절차에서 올라가는 데이터는 **합성 묶음**뿐이다(F-3).
6. 기대와 다른 출력이 나오면 그 단계에서 **멈추고** 출력 원문을 피터에게 보인다. 이 문서의 "안 될 때"로 풀리지 않으면 임의로 다른 명령을 시도하지 않는다.
7. 기존 서비스(웹서버 설정, 포트, 방화벽, 다른 사용자의 파일)는 **D 단계의 프록시 조각 하나** 외에 건드리지 않는다.

## 2. 승인 단계 A — 읽기 전용 조사

**승인 단계: A (VPS에 읽기 명령만 실행. 변경 0.)**

### A-1 조사 스크립트 실행

`tools/vps_survey.sh`는 상태만 읽는다(서비스·포트·웹서버·docker·디스크·메모리·python·방화벽·인증서 이름). 파일을 쓰거나 서비스를 건드리지 않고, 외부 접속을 하지 않고, 비밀처럼 보이는 값은 `<redacted>`로 바꾼다. `sudo`는 `sudo -n`(비밀번호 묻지 않음)으로만 쓴다.

파일을 부수적으로 쓰는 명령은 읽기로 바꿨다: `nginx -T`·`apache2ctl -S`는 설정 파일을 `grep`으로 읽고, `certbot certificates`는 `ls /etc/letsencrypt/live`와 `openssl x509 -enddate`로, `ufw status`는 `/etc/ufw/*.rules`를 읽고, python은 `-B -I`(바이트코드 파일 없음)로 메모리 안에서만 돈다. **남는 흔적은 운영체제가 스스로 남기는 것뿐이다**: SSH 로그인과 `sudo` 호출이 시스템 인증 기록(auth.log/journal)에 남고 sudo가 자기 타임스탬프 파일을 둔다. 서비스 상태는 아니다.

**조사 출력 위치(저장소 밖).** 조사 출력은 VPS 설정 정보이므로 git에 넣지 않는다. 이 PC의 `%USERPROFILE%\workmcp-deploy\`(없으면 만든다. 저장소·OneDrive 등 동기화 폴더 밖)에 날짜를 붙여 둔다. 아래 `YYYYMMDD`는 실행일이다. 배포 전 기준 파일은 `survey-before-YYYYMMDD.txt`, 배포 뒤 비교용은 `survey-after-YYYYMMDD.txt`다.

이 PC의 Git Bash에서(`tr`이 필요하다. CRLF가 섞였을 수 있으므로 `tr`로 줄바꿈을 정리한다):

```
mkdir -p "$USERPROFILE/workmcp-deploy"
tr -d '\r' < tools/vps_survey.sh | ssh <VPS_USER>@<VPS_HOST> 'bash -s' > "$USERPROFILE/workmcp-deploy/survey-before-YYYYMMDD.txt"
```

(Windows의 cmd/PowerShell에는 `tr`이 없다. 그 셸이면 파일에 CR이 없음을 확인한 뒤 `type tools\vps_survey.sh | ssh <VPS_USER>@<VPS_HOST> "bash -s" > "%USERPROFILE%\workmcp-deploy\survey-before-YYYYMMDD.txt"`로 같은 일을 한다.)

기대: 그 파일 끝에 `== end of survey (nothing was changed) ==`.
안 될 때:
- 접속 거부·키 오류: 계정·키를 피터가 확인한다. 임의로 다른 계정을 시도하지 않는다.
- `sudo without password: no`: 정상이다. 그 경우 일부 칸(`ss -p`의 프로세스 이름, `ufw status`, 인증서 목록)이 비어 있거나 "not readable"로 나온다. 피터가 sudo 가능 여부를 알려 주면 판정표의 마지막 줄을 따른다.
- 일부 명령 `(not available)`: 그 프로그램이 없다는 뜻이다. 오류가 아니다.

### A-2 판정표 (설계 §9.1)

출력의 해당 칸을 읽고 분기를 정한다. **분기가 "멈추고 피터에게"이면 B 이후로 넘어가지 않는다.**

| 조사 결과 (읽는 칸) | 분기 |
|---|---|
| `port 443` 소유가 nginx / caddy / apache | D에서 **그 설정에 location 추가** (nginx → `nginx-workmcp.conf`, caddy → `caddy-workmcp.txt` A). 인증서가 `certificates` 칸에 이미 있으면 재사용 |
| `port 80`·`port 443` 둘 다 비어 있음 | D에서 caddy 설치(`caddy-workmcp.txt` B) — 설치도 D 승인에 포함해 따로 묻는다 |
| 443을 docker 컨테이너 등 **웹서버가 아닌 것**이 소유 | **멈추고 피터에게**: 그 서비스 앞에 프록시를 둘지, 비표준 포트(예 8443 + 방화벽 열기)를 쓸지 결정이 필요 (설계 Q3) |
| `port 8765` 사용 중 | 다른 포트를 고른다 → `workmcp.service`의 `--http`, 프록시 조각의 주소, `config.toml [server] http`를 **같은 값으로** 바꾼다 |
| `python3.12` 없음 / `venv module: NO` | B-2에서 `apt install python3.12 python3.12-venv` (B 승인에 포함. `apt-cache policy` 칸에서 후보 버전을 먼저 본다) |
| `fts5 trigram: NO` | **멈추고 피터에게**: 어휘 검색이 LIKE로 대체되어 느려진다. 대안: uv가 관리하는 CPython 설치(설계 §9.1) |
| `free -m`의 available < 4 GiB (또는 `8192 − 사용 중 − 3072 < 1024` MiB) | `workmcp.service`의 `MemoryMax`·`MemoryHigh`를 낮추고 `model_idle_seconds`를 줄이거나, **피터에게 결정**(설계 Q6) |
| `sudo without password: no` | 사용자 유닛 + linger 방식으로 바꾸거나(설계 §4.4) 시스템 작업(B~E 일부)은 피터가 직접 실행. 이 경우 B부터 다시 승인 범위를 정한다 |
| `user workmcp`가 이미 있음 | **멈추고 피터에게** (이미 쓰는 사용자일 수 있음) |
| `disk`의 `/` 사용률 > 80% 또는 여유 < 10 GB | 모델 2.3 GB + DB 여유를 감안해 피터에게 알린다 |
| `systemd` 버전 < 246 또는 BPF 미지원 의심 | 유닛에서 `IPAddressDeny`·`IPAddressAllow` 두 줄을 뺀다(점검표 4번이 대신 증명) |

### A-3 전 상태 기록

A-1에서 저장한 `survey-before-YYYYMMDD.txt`(저장소 밖 `%USERPROFILE%\workmcp-deploy\`)의 `sorted listen snapshot` 칸이 D 이후 점검표 16번 비교의 기준이다. 파일을 보관한다.
추가로 이 PC에서 기존 서비스 응답을 기록한다(읽기):

```
curl -sI https://<VPS_HOST>/ -o NUL -w "%{http_code}\n"
```

기대: 지금의 상태 코드(예: 200/301/404). 값을 같은 폴더의 `survey-before-YYYYMMDD.txt` 옆에 적어 둔다. D 이후 같아야 한다.
안 될 때: 연결 실패면 지금 443이 닫혀 있다는 뜻이다 — 조사 출력의 `port 443`과 비교한다.

## 3. 승인 단계 B — 사용자·패키지·venv·코드

**승인 단계: B (새 사용자 `workmcp`, apt 패키지(있을 때), PyPI 설치 1회)**

아래 함수를 각 SSH 호출의 첫 줄에 붙인다(한 줄로 `workmcp` 명령을 그 사용자로 실행). 이 함수는 VPS의 셸 안에서만 정의되며 파일을 만들지 않는다.

```
wm() { sudo -u workmcp -H env WORKMCP_HOME=/home/workmcp/Motive_work bash -c 'cd /home/workmcp/app/Motive_work && exec /home/workmcp/app/.venv/bin/python -I -m workmcp "$@"' _ "$@"; }
```

### B-1 사용자 생성

```
sudo useradd --system --create-home --shell /usr/sbin/nologin workmcp
getent passwd workmcp
```

기대: `workmcp:x:<uid>:<gid>::/home/workmcp:/usr/sbin/nologin`.
안 될 때: "user already exists" → 멈추고 피터에게(A-2 표). `sudo: a password is required` → sudo 권한 없음, 피터에게.

### B-2 python (없을 때만)

```
sudo apt install -y python3.12 python3.12-venv
python3.12 --version
```

기대: `Python 3.12.x`. Ubuntu 24.04의 기본이 3.12이므로 보통 이미 있다 **[추정]**.
안 될 때: apt 잠금(`Could not get lock`) → 다른 apt 프로세스가 끝나기를 기다린 뒤 다시. 저장소 오류 → 출력을 피터에게.

### B-3 코드 반입 (이 PC → VPS)

저장소 공개 전환(M6) 전이므로 `git archive`와 `scp`로 옮긴다(설계 Q10).

이 PC에서 (cmd 기준; PowerShell은 `$env:TEMP\workmcp-<TAG>.tar.gz`):

```
git -c core.autocrlf=false archive --format=tar.gz HEAD -o %TEMP%\workmcp-<TAG>.tar.gz
certutil -hashfile %TEMP%\workmcp-<TAG>.tar.gz SHA256
scp %TEMP%\workmcp-<TAG>.tar.gz <VPS_USER>@<VPS_HOST>:/tmp/
```

VPS에서:

```
sha256sum /tmp/workmcp-<TAG>.tar.gz
sudo -u workmcp bash -c 'mkdir -p ~/app/Motive_work && tar -xzf /tmp/workmcp-<TAG>.tar.gz -C ~/app/Motive_work'
sudo rm /tmp/workmcp-<TAG>.tar.gz
```

주의(2026-10-26 실제 배포에서 발견): 이 PC는 `core.autocrlf=true`라 그냥 `git archive`를 쓰면 묶음 안 파일이 **CRLF**가 되어 셸 스크립트·systemd 유닛·nginx 조각이 리눅스에서 깨진다. 반드시 `-c core.autocrlf=false`로 만든다(저장소의 `.gitattributes`가 이 파일들을 LF로 고정한다).

기대: 두 해시가 같다. 압축을 푼 뒤 `/home/workmcp/app/Motive_work/pyproject.toml`이 있다.
안 될 때: 해시가 다르면 다시 보낸다(풀지 않는다). `scp` 권한 거부 → `/tmp`에 쓸 수 있는 위치인지 확인. `git archive`의 압축에는 최상위 폴더가 없으므로 위 명령은 폴더를 먼저 만들고 그 안에 푼다.

### B-4 venv와 해시 고정 설치

pip는 PyPI에 접속한다 — **설치 단계의 외부 연결이며 서비스가 아니다**(설계 §9.2).

```
sudo -u workmcp -H bash -c 'cd ~/app && python3.12 -m venv .venv && .venv/bin/python -m pip install --upgrade "pip<26.2"'
sudo -u workmcp -H bash -c 'cd ~/app && .venv/bin/python -m pip install --require-hashes -r Motive_work/requirements.lock.txt'
sudo -u workmcp -H bash -c 'cd ~/app && .venv/bin/python -I -m pip install --no-deps ./Motive_work && .venv/bin/python -I -m pip check'
```

기대: 각 줄 끝에 `Successfully installed ...`. 해시 불일치가 없다.
안 될 때:
- `THESE PACKAGES DO NOT MATCH THE HASHES`: 멈춘다. 잠금 파일과 받은 패키지가 다르다 — 출력을 피터에게. 해시 검사를 끄지 않는다.
- `setuptools` 관련 빌드 오류: `requirements.lock.txt`에는 `setuptools`가 **없다**(빌드 도구라 잠금 내보내기에 안 들어감). 위 줄은 빌드 격리를 켠 채 `pyproject.toml`의 `setuptools==84.2.1`을 PyPI에서 받는다(2026-10-26 실제 배포에서 확인). 오프라인이면 그 휠을 먼저 설치하고 `--no-build-isolation`을 붙인다.
- 컴파일 도구 없음: 휠이 없는 패키지가 있다는 뜻 — 어떤 패키지인지 피터에게.

### B-5 진단 (doctor, pytest)

```
wm doctor
sudo -u workmcp -H bash -c 'cd ~/app/Motive_work && WORKMCP_HOME=/home/workmcp/Motive_work nice ../.venv/bin/python -I -m pytest -q'
```

기대:

## 5. 승인 단계 D — 서비스·프록시·방화벽

### D-1 유닛 설치·시작

이 PC에서 파일을 올린 뒤(`tools/deploy/workmcp.service`, 줄바꿈 정리):

```

VPS에서:

```

sudo systemctl daemon-reload && sudo systemctl enable --now workmcp
sudo systemctl status workmcp --no-pager
sudo journalctl -u workmcp -n 20 --no-pager
```

기대: `systemd-analyze verify`가 오류 없음(경고만 있을 수 있음). `Active: active (running)`. 저널에 `serving ...`과 (`model_preload = true`면) `model loading in the background ...`이 시작 뒤 수 초 안에, 모델이 다 올라오면 `model loaded in N s (SHA-256 check M s)`가 나온다. 저널에 본문·토큰이 없다.
안 될 때:
- `status=2/INVALIDARGUMENT` 또는 홈 거부(exit 2): `WORKMCP_HOME` 경로·권한. `status=5`: 8765 포트 사용 중 → A-2의 포트 변경.
- `status=226/NAMESPACE` 또는 `Failed to set up mount namespacing`: `ProtectHome=tmpfs`/`BindPaths`/`ReadWritePaths`/`ReadOnlyPaths` 때문. 유닛은 쓰기를 데이터 홈(`/home/workmcp/Motive_work`)에만 허용하고 코드·venv(`/home/workmcp/app`)는 읽기 전용으로 둔다. `ReadOnlyPaths`가 `BindPaths` 안의 하위 경로에 걸리는 순서는 **[추정]**이므로 이 오류가 나면 두 줄을 따로 빼 보고(`ReadOnlyPaths` 먼저) 원인을 피터에게 보인다. 서비스가 `app/` 아래에 쓰려다 `Read-only file system`으로 죽으면(예: 바이트코드는 `PYTHONDONTWRITEBYTECODE=1`로 막혀 있음) 저널의 경로를 총괄에게. 저널 한 줄을 피터에게 보이고, 안전한 쪽(`ProtectHome=read-only` 등)으로 바꾸기 전에 승인.
- `IPAddressDeny`가 효력 없음/오류(BPF 미지원) **[추정]**: 두 줄(`IPAddressDeny`, `IPAddressAllow`)만 지우고 `daemon-reload`·재시작. 점검표 4번이 대신 증명한다.
- 모델 로드가 `MemoryMax`에 걸려 죽음(`oom-kill`): `systemctl status`의 메시지. 조사 A의 메모리 칸으로 값을 다시 정하거나 피터에게(설계 Q6).

**nginx인 경우:**

```

sudo systemctl reload nginx
```

기대: `syntax is ok`, `test is successful`, reload 후 오류 없음.
안 될 때: `nginx -t`가 실패하면 **reload하지 않는다.** include 줄을 지우고 다시 `nginx -t`. 롤백: include 줄 삭제 → `nginx -t` → reload. 백업 폴더 `/etc/nginx.bak-workmcp`는 확인 뒤 지운다.

caddy adapt --config /etc/caddy/Caddyfile --pretty

```

기대: `Valid configuration`. `caddy adapt`(읽기 전용, JSON을 출력)에서 `/workmcp/*` 경로 매처의 route가 다른 route보다 앞에 있고, 같은 사이트의 `redir`/`rewrite`/`basic_auth` 같은 사이트 수준 지시문이 `/workmcp/*`에도 걸리지 않는다(`tools/deploy/caddy-workmcp.txt`의 순서 설명).
안 될 때: validate 실패 → reload하지 않고 블록을 지운다. 사이트 수준 `basic_auth`/`redir`이 있으면 reload하지 않고 멈춰서 피터에게 묻는다.

**인증서가 없을 때(443 서버 블록이 없는 경우)** **[추정]**: Let's Encrypt 발급은 80 포트 HTTP-01이 필요하다. 기존 서비스가 80을 쓰면 `certbot --webroot` 방식을 쓰고 `--standalone`은 80을 쓰는 서비스를 멈추게 하므로 쓰지 않는다. 발급은 새 서버 블록과 함께 별도 승인 문구로 다시 묻는다.

안 될 때: `database not found`(exit 2) → 서버가 한 번도 시작하지 않았거나 홈이 다르다(`db/work.sqlite3`). `integrity_check failed`(exit 3) → 복사본을 쓰지 않고 지워진다; 출력을 피터에게. `Failed to set up mount namespacing` → D-1과 같은 원인(샌드박스 줄).
복원(필요 시): `sudo systemctl stop workmcp` → 백업 파일을 `db/work.sqlite3`로 교체(`-wal`·`-shm` 파일도 지움) → `sudo systemctl start workmcp`. 복원하면 지식·호출 기록은 백업 시점으로 돌아가고 수집 데이터는 다음 push가 채운다.
**복원 뒤 토큰을 다시 점검한다**(토큰 표도 백업 시점으로 돌아간다): `wm token list`에서 백업 **이후에 폐기했던** 토큰이 폐기 칸이 빈 채로 되살아나 있으면 `wm token revoke <id>`로 **다시 폐기**한다. 백업 이후에 새로 발급한 토큰은 표에 없으므로 필요하면 다시 발급하고(C-4, 피터 직접) 클라이언트·수집기 설정을 갱신한다. `retire`했던 수집기도 `wm collectors`로 상태를 확인하고 다시 `retire`한다.

## 7. 승인 단계 F — 이 PC 원격 연결과 합성 push

**승인 단계: F (이 PC 사용자 설정 변경 + 합성 데이터 업로드)**

### F-1 Claude Code 사용자 범위 등록 — **피터 직접**

등록은 에이전트가 하지 않는다(`~/.claude.json`이 바뀌고 토큰이 들어간다). 피터가 이 PC 터미널에서 실행한다. 토큰이 셸 기록에 남는 것이 싫으면 환경변수 방식(`doc/examples/README.md`의 원격 연결 절)을 쓴다.

```
claude mcp add --scope user --transport http workmcp https://<VPS_HOST>/workmcp/mcp --header "Authorization: Bearer <MCP_TOKEN>"
claude mcp list
```

(2026-10-27 실제 배포, 피터 승인: 앱에 들어 있는 `claude.exe`(`%LOCALAPPDATA%\Claude-Data\...\claude-code\<버전>\...\claude.exe`)로 에이전트가 `claude mcp add --scope user --transport http workmcp-remote https://<VPS_HOST>/workmcp/mcp -H "Authorization: Bearer <MCP_TOKEN>"`를 실행했다(토큰은 저장소 밖 `mcp.token` 파일에서 셸 치환으로 넣어 화면에 내지 않았다). 옵션 이름은 `claude mcp add --help`로 확인했다. 이름을 `workmcp-remote`로 해서 프로젝트의 로컬 stdio `workmcp`와 겹치지 않게 했다. `claude mcp get workmcp-remote`의 결과는 `✔ Connected`였고 헤더는 가려져 나왔다. 이미 열린 세션의 도구 목록은 바뀌지 않으므로, 호출 확인은 새 Code 탭 세션에서 한다. 그 CLI는 따로 로그인돼 있지 않아 `claude -p`로는 확인할 수 없었다.)

**[추정]** 이 PC에서는 `claude` 명령이 PATH에 없어(확인 2026-10-26) `claude mcp add --help`로 옵션 이름을 확인하지 못했다. `--transport http`·`--header`·`--scope user`는 설계 §9.6의 추정이다. 피터가 `claude mcp add --help`로 확인하고 다르면 그 이름으로 바꾼다.
기대: `claude mcp list`에 `workmcp`가 보이고 연결됨(✓) 상태.
안 될 때: 401 → 토큰 오타·폐기(`wm token list`). 연결 시간 초과 → D-5. 옵션 이름 오류 → `claude mcp add --help`. 안 되면 프로젝트 범위 `.mcp.json`(`doc/examples/mcp-remote.json.example`).

### F-2 연결 확인 (Code 탭에서 합성 데이터로)

순서: `status`(role `server`, collectors 1) → `search`(합성 질의) → `get_snippet` → `record_fact`(sources) → `get_entity`. 결과를 `doc/validation/2026-11-XX_M5-원격연결확인_v1.md`에 적는다(총괄).
서버에서 대조:

```
sudo -u workmcp /home/workmcp/app/.venv/bin/python -I -c "import sqlite3; db = sqlite3.connect('file:/home/workmcp/Motive_work/db/work.sqlite3?mode=ro', uri=True); print(db.execute('SELECT client, tool, COUNT(*) FROM tool_calls GROUP BY 1, 2').fetchall())"
```

(읽기 전용으로 연다. `sqlite3` 명령줄이 있으면 같은 SELECT를 써도 된다.) 기대: `client`가 `claude-code`, 호출한 도구 이름과 횟수가 Code 탭에서 한 것과 같다.
안 될 때: `client`가 `unknown`이면 stateful 세션 설정 문제(설계 §4.1) — 총괄에게.

### F-3 합성 수집기 push (이 PC)

실제 회사·개인 자료를 올리지 않는다. 합성 묶음만 쓴다(설계 Q9 (a)). **`push`는 `--root`가 아니라 그 데이터 홈의 저장소 전체를 보낸다.** 그래서 어느 홈을 가리키는지가 가장 중요하다. 홈을 정하지 않으면 기본 홈 `%USERPROFILE%\Motive_work`를 쓰는데, 거기에 다른 자료가 있으면 그것이 올라간다. 아래 순서를 건너뛰지 않는다.

**F-3-1 격리 + 합성 전용 홈 지정.** 모든 `uv run`을 다른 도구의 `PYTHONPATH`·`VIRTUAL_ENV`를 물려받지 않게 실행하고, 같은 셸에서 홈을 합성 전용 폴더로 고정한다(C-4에서 `push.token`을 둔 바로 그 폴더).

PowerShell:

```
Remove-Item Env:PYTHONPATH, Env:VIRTUAL_ENV -ErrorAction SilentlyContinue
$env:WORKMCP_HOME = "$env:USERPROFILE\Motive_work_synthetic"
uv run workmcp doctor
```

Git Bash(같은 뜻): 명령마다 `env -u PYTHONPATH -u VIRTUAL_ENV WORKMCP_HOME='C:\Users\<USER>\Motive_work_synthetic' uv run workmcp ...`.

기대: `data home:` 줄이 `...\Motive_work_synthetic (rules ok ...)`. 다른 폴더(특히 기본 홈)가 보이면 **멈춘다.**

**F-3-2 `config.toml`.** 합성 홈 안 `config.toml`에 서버 주소와 합성 원본 폴더 하나만 적는다(토큰은 넣지 않는다. `push.token` 파일에 있다):

```
[push]
url = "https://<VPS_HOST>/workmcp"

[[sources]]
path = 'C:\Users\<USER>\Motive_work_synthetic_docs'
```

(`path`는 테스트 시점 합성 생성기가 만든 합성 문서만 든 폴더다. 회사·개인 문서 폴더를 넣지 않는다.) 합성 문서 파일 수 N을 적어 둔다.

**F-3-3 수집·색인.**

```
uv run workmcp sources
uv run workmcp scan
uv run workmcp index
```

기대: `sources`가 위 폴더 하나만 보인다. `scan`이 `added N`(= 합성 문서 수). 합성 홈에 모델이 없으면 `uv run workmcp index --model none`으로 색인한다(벡터가 없어 어휘 검색만 확인; 이 단계는 그것으로 통과로 본다). 의미 검색까지 보려면 합성 홈에 모델을 `setup --model-from`으로 먼저 들여놓는다.

**F-3-4 올리기 전 확인(`--dry-run`).**

```
uv run workmcp push --dry-run
```

기대: `(dry run: nothing sent)` 줄과 `state: documents changed N (added N ...)`에서 **N이 합성 문서 수와 같다.** N이 다르면(특히 더 크면) 홈에 합성 아닌 자료가 있다는 뜻이므로 **`push`를 실행하지 않고** 멈춘다.

**F-3-5 올리기.**

```
uv run workmcp push
uv run workmcp push
```

기대: 첫 `push`가 전송 건수(문서·단위·벡터·바이트)를 보고하고, **두 번째 `push`는 `up to date (batches 0, bytes sent 0, ...)`**. `[push] url`은 `https://<VPS_HOST>/workmcp`, 토큰은 `<home>\push.token`. 한 홈에서 `push`를 동시에 두 개 돌리지 않는다.
안 될 때: exit 4(설정·토큰 없음·서버 스키마 불일치) → `[push] url`·`push.token`(합성 홈 안)·서버와 수집기 커밋이 같은지. 토큰 파일이 기본 홈에 있으면 못 찾는다(F-3-1의 홈 확인). exit 6(연결 불가) → D-5. 거부(exit 1) → 보고서의 오류 코드를 총괄에게.
끝난 뒤: 합성 수집기를 정리한다 `wm collectors retire devpc-synthetic`(그 토큰이 폐기됨; 데이터는 남음).

## 8. 업데이트 · 롤백 · 토큰 교체

### 8.1 업데이트 (승인 B의 반입 + 아래; 순서는 **서버 먼저, 수집기 다음**)

```
B-3 반입(새 <TAG>) → B-4의 세 번째 줄(의존성이 바뀌었으면 두 번째 줄부터)
sudo systemctl stop workmcp
wm setup --home /home/workmcp/Motive_work --upgrade
sudo systemctl start workmcp
```

기대:
- `stop`: 열린 Claude Code·Codex 세션이 있어도 **수 초 안에** 끝난다(서버가 열린 요청·스트림을 최대 3 s 기다린 뒤 끊고 세션을 정리; 저널에 `Task cancelled, timeout graceful shutdown exceeded` 같은 줄이 보일 수 있음 — 정상). `Failed with result 'timeout'`(20 s 뒤 SIGKILL)이 나오면 안 된다.
- `--upgrade`가 백업 → 마이그레이션 → `doctor`를 차례로 보고,
- `start`: 몇 초 안에 저널에 `serving ...`·`model loading in the background ...`이 나오고 포트가 바로 응답한다(D-2의 `curl` → `401`). 모델은 뒤에서 올라오고(2026-10-29 실측 기준 수십 초~약 85 s **[추정]**) 끝나면 `model loaded in N s (SHA-256 check M s)` 한 줄 — 이 두 숫자를 총괄에게 알린다(SHA-256 비중 판단용). 그 전에 온 의미·혼합 검색은 최대 25 s 기다린 뒤, 아직이면 어휘 결과와 `semantic_note` `model_loading: ...`으로 답한다. 로드 중 여부는 `status` 도구의 `engine.loading`.
- 시작 뒤 `status` 도구의 `schema_version`이 새 값.

안 될 때: 마이그레이션 실패 → 롤백. 서버 `schema_version`/`chunk_version`이 수집기와 다르면 `push`가 exit 4로 거절한다 — 같은 커밋으로 맞춘다. `stop`이 20 s를 넘겨 SIGKILL되면(데이터 손상은 없음: SQLite는 트랜잭션 단위, 메모리 대기열의 호출 기록만 잃을 수 있음) `sudo journalctl -u workmcp -n 40 --no-pager`의 마지막 줄들을 총괄에게. 저널에 `graceful stop not bounded`가 있으면 uvicorn 버전이 lock과 다르다는 뜻(정지 대기 3 s 제한이 빠짐). `model not loaded: <코드>`면 검색은 어휘로만 동작 — C-1의 `verify-model`로 파일을 확인.

### 8.2 롤백

```
sudo systemctl stop workmcp
(옛 <TAG> 반입 재설치 — B-3, B-4)
(스키마를 올렸다면) 백업 DB 복원 — 6절 복원(복원 뒤 `wm token list`로 백업 이후 폐기한 토큰을 다시 폐기)
sudo systemctl start workmcp
```

스키마 다운그레이드는 없다. 프록시만 되돌릴 때는 D-4의 롤백(include 줄 삭제 → 검사 → reload).

### 8.3 토큰 교체 (유출 의심·정기)

피터 직접:

```
wm token rotate <id>
```

새 평문은 한 번 나온다. 클라이언트(`claude mcp remove workmcp` 후 F-1 다시, 또는 환경변수 갱신)·수집기 `push.token`을 갱신한다. 옛 토큰은 즉시 무효. 확인: 옛 토큰으로 `healthz` → `401`.
