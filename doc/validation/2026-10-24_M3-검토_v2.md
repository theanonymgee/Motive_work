## 3. 새 지적

### N1 (중간) scan이 도는 동안 serve가 시작하지 못한다

- 근거: `server.main`은 시작 때 `store.open_home`(→ `connect` → `migrate`)을 부르고, `migrate`는 적용할 마이그레이션이 없어도 **무조건** `BEGIN IMMEDIATE`를 연다(`store.py` 272행). scan은 걷기 내내 쓰기 트랜잭션을 잡고 200파일마다 COMMIT 직후 다시 연다(v1 M3-1 근거와 같음). `busy_timeout` 5초 안에 틈을 못 잡으면 예외가 `main` 밖으로 나가 traceback·exit 1. M3-1 처리(`LOG_BUSY_MS`·대기열)는 호출 경로만 다뤘다.
- 재현: §1.6 — 실제 첫 scan 중 3번 중 2번 실패(7.0초 뒤 exit 1, `initialize` 응답 없음).
- 영향: 회사 PC의 첫 scan(수십 분)이나 정기 scan 동안 Claude Code·Codex가 새 세션을 열거나 `/mcp`로 다시 붙으면 `workmcp`가 "연결 실패"로 보인다. 두 클라이언트 동시 사용(설계 §7)에서 흔한 상황이다. 데이터 손상은 없다.
- 제안: ① `migrate`가 먼저 읽기만으로 `schema_migrations`를 보고 모두 적용·체크섬 일치면 `BEGIN IMMEDIATE` 없이 돌아온다(경합 시에만 쓰기 트랜잭션 — 두 serve 동시 첫 시작 보장은 그대로). `connect`의 `FTS_SQL`(`CREATE VIRTUAL TABLE IF NOT EXISTS`)도 표가 있으면 건너뛰는지 확인. ② 그래도 잠금이면 serve는 죽지 말고 쓰기 연결 없이 시작해 기록을 대기열에 두고 나중에 연결·마이그레이션(또는 짧은 stderr 한 줄 + 재시도). ③ 테스트: 다른 프로세스가 `BEGIN IMMEDIATE`를 15초 잡는 동안 `serve`의 `initialize`가 2초 안에 응답하고 `status`가 동작.

### N2 (낮음) `StrictInt`는 JSON Schema상 유효한 `5.0`도 거부한다

- §1.4: `limit: 5.0`·`max_chars: 4000.0` → SDK 검증 오류. 도구 `inputSchema`는 `"type": "integer"`인데 JSON Schema(draft 6 이후)에서 `integer`는 "소수부가 0인 수"라 `5.0`도 유효하다. 스키마로 인자를 검증하는 클라이언트나 수를 실수로 내보내는 직렬화기(예: 일부 JS·LLM 출력)는 받아들여질 값으로 알고 보낸다. `"5"`·`true` 거부는 의도대로(L1).
- 제안: `Annotated[int, BeforeValidator(...)]`로 bool·문자열은 거부하고 `float.is_integer()`인 실수만 정수로 받기, 또는 그대로 두고 설계 §8.2에 "정수는 소수점 없이" 한 줄.

### N3 (낮음) 카운터 이전에 만든 저장소는 한 번 더 재사용될 수 있다

- §1.3 `prefix_store`: `meta.chunk_id_high`가 없는 저장소에서 가장 큰 청크 id가 이미 지워져 있으면 카운터가 현재 `MAX(id)`에서 시작해 그 id를 다시 준다 → v1 M3-2와 같은 결과. 해당 저장소는 `bbcf2c7` 전에 만든 개발용 홈뿐이다(시험 홈 `Motive_work_m3test` 포함 [추정] — 만든 시각이 반영 전).
- 제안: ⑤ 연결 확인 전에 시험 홈을 새로 만들거나(scan·index 다시), 설계 §18에 "카운터 이전 저장소는 한 번 재사용 가능 — M5 첫 설치는 해당 없음"을 적는다.

### N4 (낮음) 대기열의 가시성·종료 손실

- 대기 중인 호출은 `status`의 `calls`·`delivery_log_count`에 안 보인다(DB만 셈). 종료 때 `close_log`는 200 ms만 기다려 scan 중 종료면 잃고(§1.2), notice 문구 "다음 호출에서 씁니다"는 그 경우와 맞지 않는다. 클라이언트가 프로세스를 강제 종료하면 stderr 보고도 없다. 대기열 상한 10,000호출 × 최대 50 locator는 최악 수백 MB(현실적 사용량에서는 무관).
- 제안: `status`에 `log_pending`(대기 수)·`log_dropped`; `close_log`는 5초까지 기다림; notice를 "다음 호출이나 잠시 뒤에 씁니다(서버가 그 전에 끝나면 잃음)"로.

## 4. 확인했지만 지적하지 않은 것

- 기록 대기열의 순서·중복·일치(§1.2): `at` 순서 어긋남 0, `call_id` 중복 0, 호출마다 `pieces` == `deliveries` 행 수. 대기열 쓰기는 한 트랜잭션이고 루프 스레드에서만 돌아(호출·ticker 직렬) 경합이 없다. 최종 길이 검사가 기록 전에 있어 `response_too_large`로 바뀐 응답은 조각 0으로 기록된다.
- 크기: 대기열 notice는 최종 길이 검사 **뒤**에 붙지만 맞춘 응답 ≤ 39,800 + 모델 notice 57 + `meta.engine` 6 + 대기열 notice 약 75 < 40,000이라 넘지 않는다(계산).
- `take_chunk_ids`는 배치마다 `MAX(id)`(rowid, O(1))와 `meta` 1행 읽기·쓰기 — 2,692청크 색인에서 문제 없음. `VectorCache`는 id를 배열 첨자로 쓰지 않아(`chunk_ids` int64 배열) id가 커져도 메모리 영향 없음.
- `-I`는 `PYTHONUTF8`·`PYTHONIOENCODING`도 무시한다. 와이어(stdout)는 SDK가 UTF-8로 쓰므로 한국어 응답 정상(§1.4), stderr는 로캘 인코딩 + backslashreplace라 죽지 않는다.
- serve 감사 테스트(④)는 `-I` 없이 `PYTHONPATH=src`로 래퍼를 띄운다 — 경계 판단에는 차이가 없고, 실제 클라이언트 명령은 `serve_smoke.py`가 받은 환경 그대로 검사한다.

## 5. 재검토 때 볼 것

1. N1: 다른 프로세스가 쓰기 잠금을 잡은 동안(그리고 실제 scan 중) serve 시작 성공, `initialize` ≤ 2초; 두 serve 동시 첫 시작(새 홈) 6/6 유지(v1 `probe_two.py`).
2. 낮음 N2~N4는 완료 조건을 막지 않는다.
