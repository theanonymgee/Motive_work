# M6 운영 확인 v1 — 서버 업데이트, Codex·Claude Code 동시 사용, 합성 수집기 정리

- 날짜: 2026-10-29 (Asia/Seoul). 서버 기록 시각은 UTC.
- 실행: 총괄. VPS 명령은 이 PC에서 SSH로 실행했고, 각 단계는 피터의 승인을 받았다(서버 업데이트 2회, 토큰 2개 발급).
- 데이터: 합성 문서만 썼다. 회사·개인 자료는 쓰지 않았다.
- 원문 출력은 저장소 밖에 두었고(`%USERPROFILE%\workmcp-deploy\`), 아래는 그 발췌다. 호스트는 `<VPS_HOST>`, 사용자 이름은 `<USER>`로 적었다. 토큰 평문은 어느 출력에도 없다.

## 1. 서버 업데이트 (서버 먼저, 배포 절차서 §8.1)

### 1차 — 커밋 `f70a253`(검토 v2 통과, 0.0.1 → 0.1.0)

- **반입:** `git -c core.autocrlf=false archive`로 묶었다. 이 PC와 VPS의 SHA-256이 같다(`0208aea1…e4461`).
  - 배포된 `3b9b00e` 이후 지워진 파일은 없다. 그래서 기존 폴더 위에 풀어도 옛 파일이 남지 않는다.
- **설치:** `pip install --no-deps ./Motive_work` → `pip check`가 `No broken requirements found.`, `workmcp.__version__`은 `0.1.0`이다.
- **정지 → `setup --upgrade` → 시작:**

```

schema: v5 -> v5 (no migration needed)
role: server
setup done (exit 0)
```

- **발견 1 — 정지 지연:** 옛 코드의 정지가 20 s 안에 끝나지 않아 SIGKILL로 끝났다(`Failed with result 'timeout'`).
  - 원인은 uvicorn의 무제한 graceful shutdown이다. 이 PC에서 재현했다.
  - 데이터는 백업과 `binding ok`로 확인했다.
- **발견 2 — 시작 지연:** 시작에서 `serving`까지 86 s가 걸렸다. 모델(2.28 GB, SHA-256 검사 포함)을 리스닝보다 먼저 동기로 올렸기 때문이다.
- 두 발견은 커밋 `88098e0`에서 고쳤다(리스닝 먼저, 모델은 백그라운드 로드, 정지 제한 3 s). M5 원격구조설계 반영 기록 #33~#35에 적었다.
- **외부 확인:** 이 PC의 MCP 클라이언트가 HTTPS와 토큰으로 접속했다. 결과는 `server: workmcp 0.1.0 | protocol 2025-11-25`, `tools: 15`.

## 3. Codex 원격 MCP 연결과 Claude Code 동시 사용

### 등록

- 실행 파일은 `%USERPROFILE%\.codex\.sandbox-bin\codex.exe`(codex-cli 0.160.0)를 썼다.
- 등록 전에 사용자 설정 `~/.codex/config.toml`을 저장소 밖에 백업했다.
- 명령: `codex mcp add workmcp-remote --url https://<VPS_HOST>/workmcp/mcp --bearer-token-env-var WORKMCP_MCP_TOKEN`
- 결과: `Added global MCP server 'workmcp-remote'.` 같은 표에 `startup_timeout_sec = 30`·`tool_timeout_sec = 120`을 손으로 넣고 TOML 파싱을 확인했다.
- `codex mcp list`: `workmcp-remote  https://<VPS_HOST>/workmcp/mcp  WORKMCP_MCP_TOKEN  enabled  Bearer token`
- 토큰은 그 실행의 프로세스 환경 변수로만 줬다. 사용자 환경 변수는 바꾸지 않았다(피터가 상시 쓰려면 "계정의 환경 변수 편집"에서 `WORKMCP_MCP_TOKEN`을 설정한다).

### 비대화식 실행에서 만난 것

1. 설정의 모델 `gpt-6.1-sol`은 0.160 CLI와 데스크톱 런타임(0.164.0-alpha.11.1) 모두에서 `model_not_found`(ChatGPT 계정 미지원)였다. 그 실행에만 `-m gpt-6-luna`(모델 캐시에 `list`로 표시된 모델)를 줬다. 설정 파일의 모델은 바꾸지 않았다.
2. `codex exec`는 승인 정책이 `never`라 MCP 도구 호출이 `requires approval`로 막혔다.
   - 공식 설정 참조(https://learn.chatgpt.com/docs/config-file/config-reference, 접근 2026-10-29)의 `mcp_servers.<id>.tools.<tool>.approval_mode`를 그 실행에만 `-c`로 줬다. 대상은 읽기 도구 `search`·`status`이고 값은 `"approve"`다.
   - 설정 파일에는 넣지 않았다. 대화형 Codex에서는 호출마다 승인 창이 뜬다.

### 결과

- Codex 1회차: `mcp: workmcp-remote/search (completed)` → 첫 적중 `long_line.txt` 2행 "담당자 갑이 가상 거래처 A에 견적 1,234,000원을 보냈다.", `delivered_sources` 10개. Claude Code의 같은 질의와 첫 적중이 같다.
- 동시 사용: Codex 2회차를 백그라운드로 돌리는 동안 이 Code 탭 세션(Claude Code)이 원격 `search`를 3회 호출했다.

## 4. 합성 수집기 retire와 시험 지식 정리 (설계 §6.1)

1. **원본 비우기:** 두 합성 수집기의 원본 폴더(`Motive_work_synthetic_docs` 57파일, `m6clean\docs` 8파일)에서 파일을 저장소 밖 보관 폴더로 옮겼다. 되돌릴 수 있게 지우지 않았고, 폴더는 남겼다.
2. **이 PC → 서버 삭제 전파:**

- `unverifiable 25 (not_ok 25)`는 파싱이 정상(ok)이 아니었던 합성 경계 파일(손상·암호화 등)의 버전이다. 실패가 아니다.

4. **시험 사실 철회(Claude Code 원격):** `retract(assertion_id=1, reason="M5 원격 확인 시험 기록 정리 …")` → `status withdrawn`, `recorded_to 2026-10-29T05:01:33+00:00`. 행은 이력에 남는다.
   - `list_knowledge(status=open)`: `total 0`.
   - 개체 1(`org` "합성 거래처 A (원격 확인)")은 남는다. 철회 명령이 없고, 지우면 철회된 사실 1번의 이력이 깨진다. 2026-10-29 피터가 "남김"으로 정했다(설계 §6.1 기본값과 같음). 연결된 사실은 철회됐고, 문서 본문은 없다.
5. **확인:** `search "가상 거래처 A 견적"` → `hits []`, `delivered_sources []`, `eligible_chunks 0`.

정리 뒤 서버에는 검색 가능한 문서·청크·벡터가 0이다. 살아 있는 push 토큰도 0이라, 회사 PC 수집기의 첫 토큰을 받을 준비가 됐다. 살아 있는 MCP 토큰은 2개다(4번 Claude Code, 6번 Codex).
