## 3. 새 지적

### R1 (낮음) serve 종료 코드 2·3이 다른 명령과 뜻이 겹친다

- `serve`는 이제 2 = 데이터 홈 거부 **또는** 개발 스키마 체크섬 변경, 3 = "마이그레이션이 필요한데 다른 프로세스가 저장소를 잡음"이다. CLI 문서(`CLAUDE.md`)의 scan 코드는 2 = 데이터 홈, 3 = scan 잠금. 사람은 stderr 한 줄로 구분할 수 있고 클라이언트는 코드를 쓰지 않으므로 영향은 작다.
- 제안: `CLAUDE.md`·설계 §8에 serve 종료 코드 표 한 줄(0/2/3/4와 뜻).

### R2 (낮음) 마이그레이션이 필요한 업그레이드 직후 scan 중이면 serve는 여전히 시작 못 한다; `-I` 아래 stderr는 로캘 인코딩

- §1.3 `v1 store, lock held` → exit 3. 지금은 개발 홈뿐이지만 M4 이후 새 마이그레이션(v3…)이 생기면, 코드 갱신 직후 scan이 돌고 있을 때 두 클라이언트 모두 붙지 못한다(안내는 명확).
- `-I`는 `PYTHONIOENCODING`·`PYTHONUTF8`를 무시하므로 stderr가 cp949로 나간다: `DEV_SCHEMA_HINT`의 `§`가 UTF-8로 읽는 쪽에서 깨졌다(검토 탐침이 UTF-8로 읽다 `UnicodeDecodeError`; 서버 동작에는 영향 없음, 클라이언트 로그만).
- 제안: M5 업데이트 절차에 "갱신 뒤 첫 시작은 scan/index가 돌지 않을 때"; stderr 문구는 ASCII만 쓰거나 `server.main`에서 `sys.stderr.reconfigure(encoding='utf-8', errors='backslashreplace')`.

## 4. 확인했지만 지적하지 않은 것

- `_up_to_date`는 `schema_migrations`가 없으면 False(새 홈 → 쓰기 경로), 버전이 빠지면 False, 체크섬이 다르면 `migrate`와 같은 `RuntimeError`. 판정과 `BEGIN IMMEDIATE` 사이에 다른 프로세스가 적용해도 트랜잭션 안의 행별 검사가 다시 거른다(§1.4).
- 읽기 우선 판정은 모든 명령에 적용된다: scan 중 두 번째 `scan`도 마이그레이션 단계를 지나 `scan.lock`에서 멈출 것이다 [추정, 실행하지 않음].
- `calls.pending`은 응답 크기에 몇 자만 더한다. 대기열 notice는 길어졌지만(따옴표·쉼표 포함 83자) 맞춘 응답 ≤ 39,800 + 63 + 83 < 40,000(계산).
