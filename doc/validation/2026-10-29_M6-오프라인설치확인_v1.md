## 6. 연결 관찰

push 두 번 동안 별도 PowerShell이 약 50 ms 간격으로 ① 명령줄에 `workmcp push`가 든 `python.exe`를 CIM으로 찾고 ② 그 PID들의 `Get-NetTCPConnection`·`Get-NetUDPEndpoint`를 기록했다(50초, 스크립트는 스크래치패드 `m6_watch_push.ps1`). venv의 `Scripts\python.exe`는 런처라 실제 연결은 자식(uv 관리 CPython) 프로세스가 가진다. 그래서 둘 다 추적했다.

| push | 프로세스 | 관찰된 원격 끝점 |
|---|---|---|
| 1차 | 런처 + 자식 1개 | `<VPS_IP>:443` TCP 연결 8개(로컬 포트 8개 순차, 상태 SynSent → Established), 그 밖의 원격 주소 0 |
| 2차 | 런처 + 자식 1개 | `<VPS_IP>:443` TCP 연결 1개 |

- `<VPS_IP>`는 같은 시각 `Resolve-DnsName <VPS_HOST>`의 A 레코드와 같았다.
- 셸에 `HTTPS_PROXY=http://127.0.0.1:9`가 걸려 있었지만 127.0.0.1:9 연결은 한 번도 없었다. 같은 셸에서 pip는 그 프록시 때문에 인덱스에 닿지 못했다(§2-3). 즉 push는 프록시 환경변수를 쓰지 않고 서버로 직접 연결한다(`push.py`의 `ProxyHandler({})`와 일치).
- 프로세스의 UDP 끝점은 0개였다(이름 해석은 Windows DNS Client 서비스가 한다).
- 요청마다 새 TCP 연결을 연다(1차: 상태 요청 + 6배치 + 마무리에 연결 8개).

## 8. 안내서·설계와 실제의 차이 (고치지 않음, 총괄 반영용)

1. **`make`가 추적되지 않는 `.claude/`에 걸린다.** Claude Code 워크트리(`.claude/worktrees/…`)가 있으면 `git status --porcelain`이 비지 않아 exit 4가 나고, `--allow-dirty`가 필요하다. 묶음은 `git archive`라 영향은 없다. `.gitignore`에 `.claude/`를 넣거나, 검사에서 추적되지 않는 파일을 빼는 것을 검토할 수 있다.
2. **모델 묶음은 zip이 안 만들어진다.** `--zip`은 코드 묶음만 zip으로 쓴다. 설계 §3.2-6·§3.4-1은 "zip 2개"였다. 안내서 §3은 "모델은 `workmcp-model-bge-m3-...` 폴더"라 안내서와는 맞는다.
3. **휠 개수.** 설계 §3.1은 "lock 51개 + workmcp"였는데, 실제는 lock pin 49 중 휠 48 + workmcp = 49, `SHA256SUMS` 53줄이다(안내서에는 숫자가 없다). 설계 표 §3.4의 `ok 55`도 실제는 `ok 53`이다.
4. **`setup`의 홈 표시.** 홈 폴더가 이미 있었는데(피터가 둔 `push.token`만 든 상태) dry run은 `would be created`, 실제 실행은 `created`라고 했다. 안내서 §5의 기대 출력 `push token: missing`은 토큰을 먼저 둔 이 경우에는 `present`였다(정상). 안내서는 "setup 뒤 토큰"을 전제하므로, 토큰을 미리 둔 경우의 출력도 적어 두면 좋다.
5. **`push --dry-run` 줄의 `vectors missing on server 0`.** 새 문서 8개를 앞둔 dry run이 0이라고 했지만 실제 push는 `vectors missing on server 8`이었다. 새 문서의 벡터는 문서를 올린 뒤에야 셈에 들어가는 것으로 보인다[추정]. 읽는 사람을 오해하게 할 수 있다. 또 안내서 §7은 dry run이 "아무것도 보내지 않는다"고 하는데, 실제로는 서버에 상태 요청을 보낸다(문서·벡터는 보내지 않음).
6. **push 번호.** 이 수집기의 첫 실제 push가 `push #3`이었다(이 확인 전에 서버에 #1·#2가 있던 것으로 보이나 원인은 확인하지 않음). `up to date`나 dry run 실행은 로그에 `done | push #None | exit 0 …`으로 적힌다(표시만의 문제).
7. **패키지 설명이 옛 문구다.** `pip show workmcp`의 `Summary:`가 "Personal local work-knowledge MCP server (stdio, local-only storage)."다. 지금 구조(수집기 + 운영 서버)와 다르다.
8. **Git Bash 콘솔에서 `…`가 깨진다.** `server now: documents_sha256 eb10…`의 말줄임표가 CP949 콘솔에서 깨져 보였다. 안내서는 PowerShell 전제라 영향이 작다.
9. **도구 쪽 사실.** 이 PC PATH에는 쓸 수 있는 `python`/`py`가 없다(WindowsApps 스텁뿐이고, `~\.local\bin\python3.11.exe`는 애플리케이션 제어 정책이 차단). 그래서 묶음 venv와 새 폴더 venv 모두 uv 관리 CPython 3.12.13을 썼다. 회사 PC에서는 안내서대로 python.org 사용자 설치기의 `py -3.12`다.

## 9. 남은 것·한계

- 회사 PC 자체가 아니라 이 PC의 새 폴더에서 재현했다. Python은 python.org 설치기가 아니라 uv 관리 CPython이다(같은 3.12, win_amd64).
- 죽은 프록시는 환경변수 수준이다. 실제 회사 프록시·TLS 가로채기·보안 소프트웨어의 DLL 차단은 재현하지 않았다.
- 확인용 수집기 `devpc-bundle`과 그 데이터 8문서는 서버에 남아 있다. retire·정리는 총괄이 한다(설계 §3.4-11, §6). `%USERPROFILE%\m6clean`, `%USERPROFILE%\bundles`, `%USERPROFILE%\m6build-venv`도 남겨 두었다.
