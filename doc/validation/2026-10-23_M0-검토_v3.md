### 1.5 N-1 재시험: append-only 우회 시도 (`<SCRATCH>\v3\replace_probe.py`)

(`recursive_triggers=ON` 블록은 줄마다 OFF 블록과 글자 단위로 같아서 한 줄로 줄였다.)

- **v2 재현 3종이 모두 거부된다.** 철회 행 `INSERT OR REPLACE`, 열린 행 `REPLACE INTO`, evidence 인용 바꾸기가 해당한다.
- **rowid 별칭**(`rowid`·`oid`·`_rowid_`)도 거부된다. `id`가 `INTEGER PRIMARY KEY`라 rowid의 별칭이므로, 트리거의 `NEW.id`에 같은 값이 들어온다.
- **문자열·실수 id**(`'1'`, `' 1'`, `'1.0'`, `'01'`, `1.0`, `CAST`)도 거부된다. 이유는 둘이다. `id = NEW.id` 비교에 INTEGER 친화성이 적용된다. 또 INTEGER PRIMARY KEY에 들어가는 값은 정수로 바뀐다. `x'31'`(BLOB)은 rowid가 될 수 없어 `datatype mismatch`로 거부된다.
- **`INSERT ... SELECT`**도 거부된다. 새 id와 기존 id가 섞인 여러 행 `VALUES` 역시 거부되며, 문장 전체가 롤백돼 새 행 50도 남지 않았다.
- **`UPDATE OR REPLACE`**는 assertions에서 `assertions_update_guard`(`NEW.id <> OLD.id`)에, evidence에서 `evidence_no_update`에 걸린다.
- **upsert**는 `ON CONFLICT DO UPDATE`·`DO NOTHING` 모두 BEFORE INSERT 트리거가 충돌 처리보다 먼저 실행돼 거부된다.
- **`PRAGMA recursive_triggers=ON`**에서도 같은 결과가 나온다. 이 경우 REPLACE의 삭제 단계에서 DELETE 트리거도 실행되지만, 그보다 먼저 `*_no_replace`가 막는다.
- **범위 밖으로 둔 것:** `DROP TRIGGER`, `PRAGMA writable_schema`, 트리거 없는 다른 DB 파일로 교체, `VACUUM INTO` 뒤 수정은 스키마나 파일 자체에 접근하는 경로라 이번 시험에서 뺐다. 스키마 트리거로 막을 수 있는 범위가 아니다.
- **정상 흐름은 그대로 동작한다.** 자동 id INSERT, 새 id 명시, id 없는 `INSERT OR REPLACE`, 철회, 대체(새 행 `supersedes_id=100` + 옛 행 종결), 충돌 표시·되돌림, evidence INSERT, evidence 새 id `REPLACE`가 모두 통과한다.
- 참고(새 지적 아님): evidence가 가리키는 `versions` 행은 지금도 바뀔 수 있다. `INSERT OR REPLACE INTO versions(id=1, …)`는 `foreign_keys=ON`인 우리 연결에서도 통과했다(같은 id로 다시 들어가므로 외래 키 검사를 통과한다. 출력: `foreign_keys=1: ALLOWED -> ffffffff (evidence still points at version 1)`). 그러나 `versions`는 UPDATE도 열려 있고, 총괄이 보호 트리거를 M1로 넘겼다(설계 부록 B `:669` "versions… 보호 트리거(UPDATE/DELETE/REPLACE)"). N-1의 범위인 assertions·evidence는 닫혔다.

### 1.6 N-L4 재시험: serve stdout에 고장 주입 (`<SCRATCH>\v3\inject_stdout.py`)

방법은 이렇다. 검토자 임시 래퍼가 원래 `tests/_audited_server.py`를 `runpy`로 실행하기 전이나 후, 또는 `status` 도구 안에서 stdout에 내용을 쓴다. 테스트 모듈의 `WRAPPER`를 이 래퍼로 바꾸고 `test_serve_path_stays_inside_the_runtime_boundary`를 그대로 호출한다.

```

blank line before start               : FAILED (AssertionError: unt":0},"delivered_sources":[],"notice":["…"]}}}'])
spaces-only line before start         : FAILED (AssertionError: unt":0},"delivered_sources":[],"notice":["…"]}}}'])
tab-only line before start            : FAILED (AssertionError: unt":0},"delivered_sources":[],"notice":["…"]}}}'])

lone CR before start                  : FAILED (AssertionError: unt":0},"delivered_sources":[],"notice":["…"]}}}'])
NBSP-only line before start           : FAILED (AssertionError: unt":0},"delivered_sources":[],"notice":["…"]}}}'])
blank line at exit                    : FAILED (AssertionError: :0},"delivered_sources":[],"notice":["…"]}}}', ''])

extra JSON-RPC notification at exit   : PASSED

```

(`"notice"` 안의 한국어 문장은 콘솔 코드 페이지 때문에 깨져 보여서 `…`로 바꿨다. 실제 응답을 `ascii()`로 찍으면 `'\uc544\uc9c1 \uc218\uc9d1(scan)\ud55c …'`, 곧 "아직 수집(scan)한 적이 없습니다."이고 UTF-8로 바르게 나온다.)

- **v2에서 통과하던 빈 줄(`print()`)이 이제 실패로 잡힌다.** 공백·탭·NBSP만 있는 줄, CRLF 빈 줄, 단독 CR, 종료 직전의 빈 줄과 공백 줄도 모두 실패한다. 근거는 `tests/test_network_boundary.py:501-505`의 세 단언이다. stdout이 줄바꿈으로 끝나야 하고, 마지막 줄바꿈만 떼어 나눈 모든 줄이 공백 아닌 내용을 가져야 하며, 그 줄이 모두 JSON-RPC 객체로 파싱돼야 한다.
- 마지막 줄바꿈이 빠진 경우와 JSON-RPC가 아닌 JSON(`[1]`)도 실패한다.
- **"status 도구 안의 빈 줄" 통과는 테스트의 구멍이 아니다.** `<SCRATCH>\v3\inject_tool_debug.py`로 확인했다. 도구가 실행되는 동안 `sys.stdout.write`·`sys.__stdout__.write`·`print()`·`sys.stdout.buffer.write`·`os.write(1, …)`로 쓴 줄은 모두 stdout(JSON-RPC 3줄)에 나타나지 않고 stderr로 갔다(`stdout lines=3 … stderr='\n'`). mcp 2.2.0 stdio 서버가 실행 중에 프로세스 stdout을 stderr로 돌려 놓기 때문이다. 그래서 오염될 수 있는 구간은 서버 시작 전과 종료 후뿐이고, 테스트는 그 두 구간을 잡는다.
- 추가 JSON-RPC 알림 줄과 앞에 공백이 있는 JSON 줄은 유효한 JSON-RPC 메시지라서 통과한다. MCP stdio 규약("줄마다 JSON-RPC 메시지 하나")에 맞으므로 지적하지 않는다.
