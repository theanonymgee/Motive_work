- v1이 통과시킨 앞 네 가지(되살림, `recorded_to`를 과거로 돌림, 이유 덮어쓰기, 자기 대체)는 모두 거부된다. `active→conflict` 전이는 설계대로 허용된다. 근거 0건인 evidence INSERT는 M4 `knowledge.py`의 몫이다. links·deliveries·versions의 DELETE와 entities UPDATE는 총괄 결정대로 M1/M4로 넘겼다.
- **새 결함(N-1):** `INSERT OR REPLACE`/`REPLACE INTO`에 기존 `id`를 주면 철회된 assertion이 내용·상태·`recorded_to`·이유까지 통째로 바뀐다. evidence 인용도 같다. SQLite는 REPLACE가 행을 지울 때 `recursive_triggers`가 꺼져 있으면 DELETE 트리거를 실행하지 않는다. 기본값은 꺼짐이고, 실측에서도 `0`이었다.
- 고치는 방법도 확인했다. 같은 구조의 메모리 DB에 `BEFORE INSERT … WHEN EXISTS(SELECT 1 FROM e WHERE id = NEW.id) BEGIN SELECT RAISE(ABORT,'append-only'); END` 트리거를 넣었다. 그러자 `INSERT OR REPLACE`·`REPLACE INTO`(기존 id)는 거부되고, 일반 INSERT와 id 없는 `INSERT OR REPLACE`는 통과했다.
- `seq`의 연속성(빈 번호 없음)은 스키마가 강제하지 않는다. M1 수집기의 몫으로 보고 지적하지 않는다.
