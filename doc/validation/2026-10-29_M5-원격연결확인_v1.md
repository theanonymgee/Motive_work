## 3. 서버 기록과 대조

서버 `tool_calls`(읽기 전용으로 연 DB):

```
(3,  'claude-code', 'status',        ok 1,                     62.8 ms)
(4,  'claude-code', 'search',        10 pieces, ok 1,       83323.3 ms)   <- 첫 의미 질의: 모델 첫 로드
(5,  'claude-code', 'search',        10 pieces, ok 1,          67.5 ms)
(6,  'claude-code', 'get_snippet',    1 piece,  ok 1,           3.5 ms)
(7,  'claude-code', 'record_entity',  ok 0 argument_invalid,    0.6 ms)

(9,  'claude-code', 'record_fact',    1 piece,  ok 1,          15.3 ms)
```

`deliveries`: `claude-code` search 20건(942자), get_snippet 1건(36자), record_fact 1건(28자), get_entity 1건(28자).

**대조 결과**
- **일치:** get_snippet 1·record_fact 1·get_entity 1과, 성공한 search의 10건이 클라이언트가 받은 `delivered_sources`와 같다.
- **search 20건 중 10건:** 1차 search(83 s)는 서버에서 끝나 기록됐지만, 클라이언트가 이미 기다리기를 멈췄다. 그래서 서버 기록은 이 응답 10건을 "떠남"으로 센다. 실제로 받지 않은 쪽을 더 세는, 보수적인 방향의 차이다.
- **기록 정책:** `client`는 모두 `claude-code`(2.1.309)다. 인자 기록에는 질의 문구가 없다(M3 정책).

**첫 질의 지연과 조치**
- 원인은 서버가 첫 의미 질의 때 BGE-M3를 올린 것이다(2 vCPU, 83 s). Claude Code가 그 전에 타임아웃을 냈다. 설계 §7의 "첫 의미 질의 ≤ 30 s"를 넘었다.
- 조치(보안 점검표 15번이 정한 방법): `[server] model_preload = true`를 넣고 서비스를 재시작했다.
- 재시작 뒤 12 s 안에 `serving`이 나왔고, 상주 메모리는 1.9 GiB(MemoryHigh 2.4G 안)였다.
- 재시작 직후 이 PC에서 HTTPS로 첫 검색 3회: 서버 166.9·115.4·130.0 ms, 이 PC에서 잰 왕복 0.32·0.25·0.27 s.
