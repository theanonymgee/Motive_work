## 2. 수정이 만든 것 — 점검 결과

### M6-4 잠금

- **경쟁.** `acquire_lock`은 이제 교체 파일을 먼저 쓴다(`_lock_temporary`). 그다음 `_lock_raw`로 마지막 비교 읽기를 하고, 재시도 없는 `os.replace` 한 번을 한 뒤 1.0 s 기다려 다시 읽는다.
  - 두 실행이 같은 오래된 내용을 읽었다면, 나중에 교체한 쪽이 이긴다. 먼저 교체한 쪽은 1.0 s 뒤 남의 nonce를 보고 `Locked`를 낸다.
  - 한쪽이 비교 읽기를 했을 때 이미 교체돼 있으면, 내용이 달라서 바로 `Locked`를 낸다.
  - 비교 읽기의 `_retry_io`(최대 0.2 s) 지연은 **읽기가 끝나기 전**에 생긴다. 그래서 "마지막 읽기 → replace" 창을 넓히지 않는다.
  - 탐침 LR2에서 경계는 1.0 s다.
- **Windows 공유.** 파이썬 `open()`은 `FILE_SHARE_DELETE` 없이 열기 때문에, 그 순간 다른 프로세스가 잠금을 읽고 있으면 `os.replace`가 거부된다. 재시도가 없으므로 인수하려던 쪽은 `Locked`(exit 3)로 끝난다.
  - 이는 안전 쪽 실패다. 동시에 두 실행이 모두 거부되는 경우에도 아무도 진행하지 않을 뿐이고, 다음 실행(작업 스케줄러)이 다시 시도한다.
  - 살아 있는 holder의 요청별 `lock_held`는 **읽기**라서 다른 읽기와 충돌하지 않는다. holder 자신의 `touch_lock` 교체는 같은 스레드에서 순서대로 일어나고 재시도도 그대로다. 다른 실행이 잠금을 읽는 순간과 겹쳐도 20×10 ms 재시도로 흡수된다(이전과 같음).
  - 그래서 새 공유 충돌 경로는 찾지 못했다.
- **성능.** `lock_held`는 0.055 ms/회(1000회 측정)다. HTTP 요청에 비하면 무시할 만하다. 오래된 잠금을 인수할 때마다 1.0 s를 기다리는데, `setup --upgrade`가 오래된 잠금 셋을 모두 인수하는 최악의 경우에도 3 s다.
- **해제.** 읽기 실패는 다시 읽어 보고, 그래도 안 되면 `report['warning']`에 적는다(테스트 있음). 그러나 **삭제** 실패(`os.remove`의 `PermissionError`, 0.2 s 재시도 뒤)는 `release_lock`에서 예외로 나온다. 그 예외는 `execute`의 `finally`를 빠져나가 이미 만든 보고서를 덮는다(M6-2-1).

### 버전 0.1.0

- `uv.lock`의 프로젝트 줄만 0.1.0으로 바뀌었다. `uv lock --check --offline` → `Resolved 50 packages`(오류 없음). `requirements.lock.txt`는 `--no-emit-project`라서 바뀌지 않았고, 다시 export한 결과와 머리 주석 한 줄 말고는 같다.
- `test_the_release_number_is_one_value`는 `uv.lock`을 보지 않는다. `uv.lock`의 프로젝트 버전은 `--frozen` 설치에 영향이 없으므로 문제는 아니다.

### `push.CLIENT_VERSION` = `__version__`

- 서버는 `pushes.client_version`에 **기록만** 한다(`receive.py:454-456`). 버전으로 거부하거나 분기하는 코드는 없다. 호환 판정은 여전히 `protocol`·`schema_version`·`chunk_version`이다.
- 그래서 0.1.0 수집기가 0.0.1 서버로 보내도 버전 문자열 때문에 거부되지는 않는다. 서버 먼저 갱신하는 순서는 M6 1단계의 receive 변경(V3-3·V3-6) 때문에 여전히 필요하다.
- 이 값은 `batch_id`(정준 JSON 해시)에 들어간다. 업그레이드 전후로 같은 배치를 다시 보내면 다른 id가 되지만, 새 `begin`이 앞선 push를 `aborted`로 닫으므로 영향이 없다.
- 서버의 과거 `pushes` 행은 `0.0.1`로 남는다(정보성).

## 7. 하지 못한 것

- 실제 묶음 생성(PyPI 다운로드, `pip wheel`)과 회사 PC 재현은 하지 않았다(네트워크, 2단계 E의 몫).
- 실제 `claude mcp add`·`codex mcp add` 실행, PowerShell에서의 실제 펼침과 `~/.claude.json` 내용은 확인하지 않았다. 셸 동작에 대한 판단은 언어 규칙 기준이다.
- `[Environment]::SetEnvironmentVariable(… 'User')` 실행과 작업 스케줄러의 환경변수 반영은 확인하지 않았다(실제 사용자 설정 변경).
