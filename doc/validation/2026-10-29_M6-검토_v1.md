## 0. 결론

**판정: 조건부 통과 — 높음 0, 중간 2, 낮음 16.**

- **V3 다섯 건(V3-2·3·5·6·7)은 설계 §1대로 들어갔고, 의도한 경우에는 동작한다.** 탐침 S-D 재현 테스트(V3-3), 두 실행의 오래된 잠금 동시 인수(V3-5), units 단계 거부(V3-6), 진행 중 버전 숨김(V3-2), SQLite 3.44 미만 경로(V3-7)가 모두 테스트로 고정돼 있고, 전체 테스트는 **2220 passed**다.
- **V3-5의 "정확히 하나만"은 확률적이다.** 오래된 잠금을 같이 본 두 실행 중 하나가 판정과 교체 사이에서 0.2 s(정착 시간) 넘게 늦으면 **둘 다 잠금을 얻는다**(탐침 LR). 늦어지는 이유로 이 코드의 `PermissionError` 재시도(최대 20×10 ms = 0.2 s)도 꼽힌다. 빼앗긴 쪽은 다음 heartbeat 때(최대 5분 뒤) 멈추고, 서버는 `begin`이 앞선 push를 `aborted`로 만들어 데이터는 지켜진다. 그래서 낮음(M6-4)으로 둔다.
- **`workmcp setup`은 설계 §2와 맞는다.** 비대화식, 멱등(두 번째 실행에서 홈 파일 해시 불변), AppData 홈은 `--yes` 없이 exit 2, `http://` `--push-url`은 exit 4, 라이브 `push.lock`이 있으면 `--upgrade`가 exit 3, 오래된 잠금은 경고를 남기고 넘긴 뒤 백업(`integrity_check ok`)·"no migration needed"까지 간다. 가짜 토큰(환경변수·`.claude.json` 헤더)은 출력·결과·홈 어디에도 없다. 작은따옴표와 한글이 든 소스 경로는 TOML 기본 문자열로 이스케이프되고 다시 읽힌다.
- **중간 2건은 둘 다 회사 PC 문서·운영 경로에 있다.** (M6-1) 오프라인 묶음으로 **업데이트**하면 버전이 그대로 `0.0.1`이라 pip가 `Requirement already satisfied`만 내고 **새 코드를 설치하지 않는다**(탐침 PIP으로 확인). (M6-2) 안내서가 로밍 프로필 대책으로 권하는 `--home D:\Motive_work`처럼 기본이 아닌 홈을 쓰면, 이후 `scan`·`push`·작업 스케줄러가 `WORKMCP_HOME`을 모른다. setup도 안내서도 그 변수를 설정하라고 하지 않는다.
- 셸 기록 안내는 세 곳이 서로 다르다. `setup` 출력은 PowerShell 기록 **파일 전체** 삭제(`Remove-Item (Get-PSReadLineOption).HistorySavePath`)를 권하고, 안내서는 바로 그 명령을 하지 말라고 경고한다(M6-3, 낮음). `--header "Authorization: Bearer $env:WORKMCP_MCP_TOKEN"`을 쓰면 기록에는 변수 이름만 남는다.
- `tools/make_bundle.py`는 lock 대조(이름·버전·해시), 저장소 밖 출력, `git archive`로 만든 휠, 목록 밖 파일·경로 탈출 탐지를 갖췄다. 다만 `INSTALL.txt`가 `SHA256SUMS`에서 빠져 있다. 그래서 `INSTALL.txt`를 바꿔도 검증은 통과하고, 그 안의 "must equal <해시>"는 같은 묶음 안의 값이라 기준점이 되지 못한다(M6-10, 낮음; 설계 §3.3이 받아들인 신뢰 한계 안).
- 경계는 유지된다. 외부 AI 호출 0, 수집기 egress는 서버(`push`)와 모델 다운로드(`models.fetch`, `setup --model download`)뿐이다. `setup`은 프로세스를 만들지 않고 전역 클라이언트 파일을 쓰지 않는다. 새 import는 `tomllib`(읽기 전용) 하나이고, 설계 밖의 패키지 import로 `setup → push`(상수 두 개용)가 있다(M6-13, 낮음).
- 공개 예정 저장소 기준으로 새·바뀐 파일 전체 diff에 실제 사용자 경로·메일·호스트·IP는 없다(`127.0.0.1` 제외).

## 4. `tools/make_bundle.py` — 설계 §3과의 대조

- 해시: `pip download --only-binary=:all: --require-hashes`로 lock을 파일마다 대조한 뒤, `check_wheels`가 다시 이름·버전·해시를 lock과 대조한다. lock에 없는 휠은 실패, 마커 없는 pin의 휠이 빠져도 실패, 마커 있는 pin은 휠이 없어도 통과한다(M6-11).
- 저장소 밖 출력: `realpath` 기준으로 판정해 정션도 잡는다. `--out`이 상대 경로면 거부. 테스트 4개.
- 프로젝트 휠: 커밋의 `git archive`(zip)를 임시 폴더에 풀어 `pip wheel --no-deps`로 만든다. 작업 트리를 쓰지 않는다. lock도 커밋에서 꺼낸다. 빌드 격리 setuptools 문제는 M6-9.
- `verify`: 절대 경로, 드라이브, `..`, 빈 구성 요소를 거부하고 목록 밖 파일을 탐지한다(대소문자가 다르면 실패 쪽으로 판정). `INSTALL.txt` 제외와 `ok 0` 문제는 M6-10.
- 자식 프로세스(`pip`, `git`): `tests/test_tools_dir.py` 규칙은 import만 검사하고, docstring도 자식 프로세스를 허용 범위로 적는다. 설계 §3.5의 [추정]대로 규칙 위반이 아니다. `-I`와 `PYTHONPATH` 제거로 실행한다.
- pip 자체: 회사 PC의 pip는 python.org 설치기에 든 ensurepip 휠이다(서명된 설치기의 일부). 묶음은 pip 버전을 고정하지 않는다. 받아들일 만한 한계다.

- 관리자 권한: 안내서의 명령(`Test-NetConnection`, `netsh winhttp show proxy`, `certutil -hashfile`, 사용자 환경변수, 사용자 작업 스케줄러, venv·pip)은 모두 관리자 권한이 필요 없다. 예외는 python.org 설치기 체크박스(M6-15 a)다.
- 비밀·개인 정보: `git diff e4ce7d3 5f1d012`의 추가 줄에 실제 사용자 경로, 메일, 호스트, IP(루프백 제외)가 0건이다. 토큰은 모두 자리표시자다.
- 프록시 확인 단계는 "push는 프록시를 쓰지 않음 → 강제 프록시면 멈춤"을 바르게 설명한다. 다만 `curl` 확인에 `--noproxy`가 빠졌다(M6-12).
- 업데이트 절: 오프라인 경로가 실제로는 갱신하지 않는다(M6-1). 기본이 아닌 홈의 후속 명령 문제는 M6-2.

## 8. 하지 못한 것

- 실제 묶음 생성(`make_bundle.py make`, PyPI 다운로드)과 회사 PC 재현(설계 §3.4)은 하지 않았다. 네트워크 사용은 2단계 E의 몫이다.
- VPS·실제 서버 push, 실제 `claude mcp add`·`codex mcp add` 실행, Claude Code 사용자 범위의 `${VAR}` 확장 여부는 확인하지 않았다.
- M6-5(검색 경로의 진행 중 청크)는 재현하지 않았다(코드 읽기). M6-4의 해제 실패 분기도 재현하지 않았다.
- python.org 설치기 체크박스의 기본 상태(M6-15 a)는 이 PC에서 확인하지 않았다 [추정].
- 성능: `IN_PROGRESS_SQL`의 비용(코드 주석: 24만 청크에서 전체 검색 +약 10 %)은 다시 측정하지 않았다.
