- 날짜: 2026-10-23 (Asia/Seoul)
- 작성: 검토자. 독립 재검토만 했다. 코드·설정·다른 문서는 고치지 않았고 커밋하지 않았다. 저장소에 쓴 파일은 이 문서 하나다.
- 검토 대상: 커밋 `8342e92`(1차 검토 처리), 비교 기준 `0c08885`. 범위는 `git diff 0c08885..8342e92`(26개 파일, +1,518/−281). 처리 내역은 M1 설계 §15·§13 #14·#15. 작업 트리는 깨끗했다.
- 기준: 1차 검토 `doc/validation/2026-10-23_M1-검토_v1.md`, `docs/PLAN.md` §4 M1 완료 조건 ①~⑦, `AGENTS.md`.
- **판정: 조건부 통과(미충족).** 1차 중간 2건 중 **M1-2는 해소**, **M1-1은 부분 해소**다. 1차 재현 경로(P2·P3·P4)는 확실히 막혔고(32 MiB `<w:p/>` 2,825 → 61 MiB, 64 MiB HWP 문단 2,236 MiB → `too_large/hwp_para` 171 MiB) 메모리 회귀 테스트는 옛 코드에서 실제로 실패한다. 그러나 새 스트리밍 방식 `iter_xml`에 **우회 2개**가 있다. 하나는 깊은 중첩으로, 열린 조상 경로에 상한이 없고 떼어내기 루프가 깊이에 비례해 돌아 시간이 이차로 는다(17 KiB 파일 → +514 MiB·67.6초, 66 KiB 파일 → 2.1 GiB·24분, 164 KiB 파일 → 30분 안에 끝나지 않고 3.5 GiB 넘게 증가). 다른 하나는 속성·이름 폭탄이다(12.6 MiB 파일 → +1,926 MiB, 부분 크기의 약 30배). 낮음 처리분 9건(L2·L3·L5~L11)은 모두 해소됐고, L1·L4는 한계로 인정한다. **미해결 높음 0, 중간 2(M1-3·M1-4), 새 낮음 3.** 따라서 완료 조건 ⑥은 아직 충족되지 않는다.
- 표기: 출력에 든 검토자 임시 폴더 경로(사용자 폴더 아래 `AppData\Local\Temp\…\scratchpad`)는 `<SCRATCH>`로 바꿨다(소문자 표기는 `<scratch>`). 나머지는 원문이다. 합성 입력·데이터 홈·임시 스크립트는 모두 `<SCRATCH>` 아래에 두었다. 실제 문서 폴더나 OneDrive는 scan 대상으로 쓰지 않았고, 외부 네트워크는 쓰지 않았다. 옛 코드는 `git archive 0c08885 src tests`를 `<SCRATCH>\old`에 풀어 썼다(저장소 쓰기 없음).
- 측정: `peak_commit`은 `K32GetProcessMemoryInfo`의 `PeakPagefileUsage`(프로세스 최대 커밋)이고, `base`는 입력을 읽고 파서를 한 번 데운 뒤의 커밋이다. 케이스마다 새 프로세스에서 쟀다. 이 PC는 16코어, 물리 메모리 27.8 GiB다.
