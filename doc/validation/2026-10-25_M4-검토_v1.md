## 2. 지적

### 높음

없음.

### 중간

**M1. `scan --reparse`가 근거가 가리키는 버전의 단위를 제자리에서 바꾼다 — 조회는 `source_state: current`로 어긋난 인용을 보이고, 중간 행 대체가 막힌다.**

- 재현: §1.8. 근거 기록 → 파서 버전이 바뀐 뒤 `scan --reparse` → 같은 `version_id`의 `units`가 새 파서 출력으로 교체됨(`versions` 행 1개 그대로) → `get_entity`·`assertion_row`가 `source_state current`, `requote None`, notice 없음, 그러나 그 근거 locator로 `get_snippet`은 `locator_text_mismatch`. `supersede(old_valid_to=…)`는 `_copy_evidence`의 `locator.check_text`에서 `LocatorError`로 실패해 클라이언트에는 locator를 주지도 않은 호출에 `locator_invalid`가 간다. 일반 `supersede`는 통과.
- 근거: `collect.py` 228~236행(`fill` 경로: `drop_chunks` → `DELETE FROM units WHERE version_id=?` → `UPDATE versions SET … parser_version …`), `needs_retry`(195행: `reparse`이고 파서 버전이 다르면 ok 버전도 다시 채움). `units`에는 보호 트리거가 없다(M1 설계). `knowledge_query.source_state`(135~139행)는 문서 상태와 `superseded_at`만 본다. `knowledge._copy_evidence`(458~471행)는 `check_text`의 예외를 잡지 않는다. `binding.verify`는 이것을 잡는다(`evidence:locator_text_mismatch`) — 검출 수단은 있으나 조회 도구가 보여 주는 상태가 틀린다.
- 영향: 완료 조건 ③("인용이 locator 원문과 일치")이 쓰기 시점에는 지켜지지만 그 뒤 정상 유지 명령 하나로 깨지고, 클라이언트는 "현재 원문"이라고 안내받는다. M5 업데이트 절차(새 파서 → `--reparse`)가 바로 이 경로다.
- 제안(택1 또는 함께): (a) `collect.record(fill=…)`에서 그 버전을 가리키는 `evidence`가 있으면 제자리 채우기 대신 새 버전(`supersede` + `seq+1`)으로 기록 → 근거는 `changed`가 되고 `requote`가 동작. (b) 조회 쪽 방어: `_evidence`에서 저장 단위로 `locator.check_text`를 한 번 해(단위 1행 조회) 어긋나면 `source_state`에 새 값(예: `mismatch`)과 notice; `_copy_evidence`는 `KnowledgeError`로 바꿔 사유를 말함. 테스트: 근거 기록 → 파서 버전 패치 → `scan(reparse=True)` → 조회 상태·`verify`·중간 행 대체.

**M2. 열린 중간 행 C를 다시 대체하면 이력이 갈라진다 — `get_history`가 새 행을 빠뜨리고 `superseded_by_id`가 틀린다.**

- 재현: §1.4 끝. `supersede(A, old_valid_to=D)` → O=A 닫힘, C 열림(`supersedes_id=A`), N(`supersedes_id=C`). 총괄 결정대로 C가 열려 있으니 `supersede(C, value=…)`가 허용되고(옛 기간의 값을 교정하는 자연스러운 쓰임) N2(`supersedes_id=C`)가 생긴다. 이후 `get_history(A)`·`get_history(N)` 체인은 `[A, C, N]`이고 N2가 없다. `get_history(N2)`는 `[A, C, N2]`인데 그 안의 C는 `superseded_by_id: 4`(N)로 나온다; C의 `superseded` 이벤트는 `related_id 5`(N2). 대체 전에도 C는 `status active`인데 `superseded_by_id: 4`, O는 `superseded_by_id: 3`(C)인데 O의 `superseded` 이벤트는 `related_id 4`(N)라 같은 응답 안에서 두 표시가 엇갈린다.
- 근거: `knowledge_query.chain_ids`(493~507행)와 `_row`의 `superseded_by_id`(221행)는 "한 행의 대체는 하나뿐"(닫힌 행은 다시 대체 못 함)을 전제로 `MIN(id) WHERE supersedes_id = ?`를 따라간다. 중간 행 C를 열어 둔 반영 결정(설계 §4.3 반영 기록)으로 한 행이 자식 둘(N과 N2)을 가질 수 있게 됐는데 체인 규칙은 바뀌지 않았다. 설계 §5.2 "분기는 없다"가 더는 참이 아니다. 시점 질의 결과 자체는 맞다(T=10-10 → N2, T=10-25 → N).
- 영향: 완료 조건 ④의 "이력" 표시가 실제로 기록된 행 하나를 숨기고 대체 관계를 틀리게 말한다. 테스트에 C를 다시 대체하는 경우가 없다(`test_knowledge.py::test_supersede_with_old_valid_to_cuts_the_period`, `test_tools.py::test_a_cut_supersede…`는 한 번만).
- 제안: `superseded_by_id`는 그 행의 `superseded` 이벤트 `related_id`(닫힌 행만; 열린 C는 None, 대신 `continued_by`나 `cut_by` 같은 별도 필드에 N)로; `chain_ids`는 앞으로 갈 때 닫은 행(이벤트의 `related_id`)을 우선 따라가고, 같은 부모를 `supersedes_id`로 가진 다른 행은 체인에 넣거나(시간순) `branches`로 표시. 아니면 C의 재대체를 막는 규칙(`kind_mismatch`류)을 정하고 docstring에 쓴다 — 다만 그러면 옛 기간 교정 방법이 없어진다. 테스트: 위 재현 그대로.

### 낮음

**L1. 트리거가 막지 않는 직접 SQL 변경(코드 경로는 없음).** §1.3 "ALLOWED". (a) 열린 행에 `change_reason`만 먼저 넣을 수 있고(v1 `assertions_update_guard` 129행은 NULL→값 1회를 닫기와 무관하게 허용), 그러면 그 행은 영영 철회·대체되지 않는다(`IntegrityError` → `internal_error`). (b) `evidence` INSERT가 `my_note` 행·닫힌 행에도 들어가 "내 메모"인데 `evidence_count 1`·`source_state current`가 된다(조회는 그대로 보인다). (c) 열린 충돌 링크가 있는데 `conflict→active`, (d) 지난 시각으로 닫기·지난 `recorded_from`으로 INSERT(기록 시점 질의를 바꿈), (e) 임의 `links` INSERT, (f) 별칭 삭제·`note` 덮어쓰기. DB를 직접 쓰는 사람은 트리거도 지울 수 있으므로 위협 모델상 낮음. 제안: 값싼 것만 — `evidence` BEFORE INSERT에 `(SELECT source_kind FROM assertions WHERE id=NEW.assertion_id)='evidence' AND recorded_to IS NULL`, `change_reason`은 `NEW.recorded_to IS NOT NULL`일 때만 설정, 열린 충돌 링크가 있으면 `conflict→active` 거부. `check_evidence` 같은 불변식 검사를 `workmcp verify`에 넣는 것도 방법(옛 버전 근거는 지금 `verify`가 전혀 다시 보지 않는다 — 설계 §3.4대로 `stale`이지만 저장 단위 대조는 싸다).

**L2. 겹치는 일치가 모호로 잡히지 않는다.** `'아아아'`에서 `'아아'`가 `[0,2)`로 바로 결속(§1.2). `_exact`(382~387행)가 겹치지 않게 찾기 때문. 저장 인용은 원문과 같으므로 결속 자체는 맞지만 "두 곳 이상이면 모호"(M0 L-11) 규칙과 다르다. 제안: 다음 검색 시작을 `at + 1`로.

**L3. 크기 상한 아래로 줄일 수 없는 행 — 저장은 됐는데 되읽을 수 없다.** `response_max_chars = 4000`(허용 최소값)에서 최대 길이 결정(문장 1,000 + 선택지 20×200 + chosen·rationale 각 1,000)이나 충돌이 여럿인 사실(충돌마다 `value` ≤ 1,000자, 행의 `conflicts`와 응답의 `conflicts`에 두 번)은 쓰기 응답이 `response_too_large`(저장 id를 알려 줌 — 좋음)이고, 안내대로 `get_history`·`list_knowledge`로 읽으면 `chain: 0, truncated: true`·`items: 0, limit: 0`이 `ok`로 온다(§1.7). `list_knowledge`의 notice는 "offset으로 이어서 받으세요"인데 limit 0이라 진행할 수 없고, 충돌 notice는 빠진 행까지 센다. 기본 40,000자에서는 같은 주어·속성에 1,000자 값 충돌이 약 18개 이상일 때만 생긴다. 제안: 행의 `conflicts`를 상한(예: 10개 + `conflicts_total`)으로, shrink 단계에 "행 안의 긴 문자열(`conflicts[].value`, `options`)을 줄이고 표시"를 행 제거 앞에 두고, 행이 0개가 되면 `response_too_large`로 답하기.

**L4. 초 단위 오프셋을 가진 시각은 조용히 빈 결과.** `as_of_recorded='2026-10-25T06:35:00+05:30:15'` → `[]`(§1.4). `recorded_instant`(105~118행)가 `isoformat`으로 `+05:30:15`를 남기고 SQLite `julianday`는 그 형식을 NULL로 본다. M3 `search._instant`(since/until)도 같다. 제안: 정규화 때 UTC로 바꾸거나(`astimezone(timezone.utc)`) 초가 있는 오프셋은 `argument_invalid`.

**L5. 기록과 닫기 사이에 PC 시간대가 바뀌면 닫기가 거부된다.** §1.4 끝: +09:00에 기록한 행을 +00:00 시각으로 철회하면 v1 `assertions_status_guard`의 문자열 비교(`recorded_to < recorded_from`)가 막아 `internal_error`(IntegrityError). 시간대 차이만큼 시간이 지나야 풀린다. 설계 §14 #6이 한계로 둔 것과 같다 — 회사 PC(KST 고정)에서는 드묾. 제안: 새 트리거(v4 때)에서 `julianday` 비교, 또는 `store.now()`를 UTC로.

**L6. 클라이언트 locator의 단위 라벨이 오류 메시지에 그대로 들어간다.** `sources[].locator.unit`의 시트 이름에 넣은 `SENTINEL`이 `not_found` 메시지("unit not found (시트 … A1)")에 나온다(§1.7). 클라이언트가 보낸 값을 그 클라이언트에만 돌려주고, `tool_calls`(오류 코드만)·stderr에는 없으며 200자 상한이 있다 — M3 `get_snippet`과 같은 동작. 설계 §8.3이 라벨은 허용하므로 정보 공유 수준.

**L7. `supersede`로 필드를 비울 수 없다.** `None`은 "옛 값 복사"라서 `unit`·`valid_to`·`due`·`owner_entity_id`·`chosen`을 없애는 교정이 불가능하다(`knowledge.supersede` 663행 `given = {… if value is not None}`). 예: 끝 날짜가 있던 계약이 무기한으로 바뀐 경우는 철회 후 새로 기록해야 하고 이력 체인이 끊긴다. 제안: 빈 문자열(또는 `clear: [names]`)로 지우기.

**L8. 커밋 뒤 응답 조립에서 예외가 나면 저장 id 없이 `internal_error`.** `server.handle`의 `stored`는 `TOOLS[tool]`이 봉투를 돌려준 뒤에만 채워진다. `knowledge.record` 등은 COMMIT 뒤 `knowledge_query.assertion_row`를 부르므로 거기서 예외(드묾 — 읽기만)면 클라이언트는 실패로 보고 다시 부를 수 있다(중복 기록). 제안: 쓰기 함수가 커밋한 id를 `state`에 남기고 `internal_error`에도 `STORED_TOO_LARGE`와 같은 "stored (id …)" 문구.

## 4. 범위·한계

- 회사 자료·실제 Code 탭 연결(완료 조건 ⑥)은 보지 않았다(시험 홈 금지). `doc/validation/2026-10-25_M4-연결확인_v1.md`는 아직 틀(실행 전)이다.
- 두 serve 프로세스의 stdio 동시 쓰기는 기존 테스트로, 많은 쓰기의 직렬화는 `knowledge.record` 직접 호출 세 프로세스로 확인했다(§1.6). §1.6의 scan은 300개 작은 파일이라 0.3초에 끝나 긴 scan 트랜잭션 중 5초 대기 → `store_busy`는 기존 테스트(잠금 쥔 연결)에 의존한다.
- M1 재현은 파서 출력을 패치해 흉내 냈다(실제 파서 변경 없음). 어떤 파서 변경이 단위 텍스트를 바꿀지는 M5 업데이트 때 정해진다.
- 다음 검토(v2)에서 볼 것: M1·M2 수정과 그 테스트, L 항목 중 반영한 것.
