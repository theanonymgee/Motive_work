## 6. 남은 한계

1. **Windows에서 종료가 가끔 멈춘다** [사실].
   - 증상: 부하가 있을 때 긴 e2e 흐름 뒤 SIGTERM을 보내면, uvicorn이 `Shutting down`을 찍은 뒤 남은 연결·작업이 없는데도(그 로그가 없음) lifespan 종료, 즉 SDK 세션 관리자 정리가 끝나지 않는다. SIGINT로 강제 종료를 걸어도 풀리지 않았다.
   - 빈도: 오늘 e2e 포함 실행 약 30회 중 4회. 반복 시도(합계 20회 이상)로 재현을 노렸지만 다시 나오지 않았다. stderr를 확보한 2회는 모두 그 앞에 asyncio의 Windows proactor 로그(`ConnectionResetError` in `_call_connection_lost`)가 있었다.
   - 테스트에서의 처리: launcher가 5 s 뒤 SIGINT, 15 s 뒤 강제 종료(9)하고, 테스트는 이 경우만 경고와 함께 통과시킨다(`test_remote.assert_stopped`, 감사 래퍼는 `stalled` 표시와 이벤트 보존). 원인 추적용으로 `WORKMCP_TEST_STOP_DIAG=1`이 남은 작업을 찍는다.
   - 운영 영향 [추정]: 리눅스(selector 루프)에서는 이 proactor 경로가 없다. 그래도 같은 정지가 나면 systemd가 `TimeoutStopSec`(기본 90 s) 뒤 SIGKILL한다. SQLite 쓰기는 트랜잭션 단위라 데이터 손상은 없고, 메모리 대기열의 호출 기록만 잃을 수 있다. **권고: 유닛에 `TimeoutStopSec=20`, VPS에서 `systemctl stop` 시간 확인.**
2. **리눅스 SIGTERM 경로·`[::1]` 바인드·`IPAddressDeny`·프록시 경유 Host 헤더는 VPS에서 확인**해야 한다(이 PC에서는 Windows SIGTERM/SIGBREAK와 127.0.0.1만 확인).
3. **MCP 경로의 거부 기록**: 토큰 없음, 또는 push 토큰을 MCP에 쓴 경우는 SDK가 401만 내므로 stderr 기록이 없다. unknown·revoked는 경로와 무관하게 기록된다.
4. **첫 대량 push 처리량**은 이 PC에서 해제 기준 ≈ 3.3 MB/s, 설계 추정 5 MiB/s보다 낮다(§4.3).
5. 실모델 e2e는 측정 스크립트에서만 돌렸다(기본 pytest에는 없음, 모델 2.3 GB 필요). 수집기 `search --mode semantic`과 서버 cosine의 ±1e-3 대조(설계 §8 선택 항목)는 하지 않았다.
6. VPS 메모리·지연은 모두 추정이다. 배포 뒤 같은 스크립트를 리눅스에서 돌려야 한다. 측정 스크립트의 메모리 함수는 Windows 전용이라, 리눅스에서는 `/proc/<pid>/status`로 바꿔야 한다.
