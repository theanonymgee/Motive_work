## 3. 지적

### M3-1 (중간) scan이 쓰기 잠금을 사실상 계속 잡아, 그동안 모든 도구 호출이 11초 멈추고 전달 기록을 잃는다

- 근거(코드): `collect.scan`은 `BEGIN IMMEDIATE` 뒤 걷기 전체를 한 트랜잭션으로 돌고, `_Scan.tick`은 파일 200개(`commit_every`)마다 `COMMIT` 직후 곧바로 `BEGIN IMMEDIATE`를 연다(`collect.py` 145~151·488~495행). 파일 읽기·해시·파싱이 모두 이 트랜잭션 안이다. `server._record`는 호출마다 `BEGIN IMMEDIATE`를 쓰고 `busy_timeout` 5초 × 2회 시도한다(`server.py` 130·167~175행). 도구가 `async def`라 그 대기가 **이벤트 루프 스레드**에서 일어난다. 설계 §3.5의 "[추정] busy_timeout 5초 안에 풀린다"가 scan에는 맞지 않는다.
- 재현(`probe_busy.py`): 합성 텍스트 1,500개(각 약 120 KB)를 다른 프로세스에서 `workmcp scan`(95.2초)하는 동안 0.5초 간격으로 `server.handle(search)`:

```
at    1.0s call 11.12s ok=True notice_log_fail=True
at   12.6s call  0.33s ok=True notice_log_fail=False
at   13.5s call 11.11s ok=True notice_log_fail=True
  … 같은 양상 7회 …
scan exit 0 after 95.2 s
tool_calls rows 8          (호출 16회 중 7회의 tool_calls·deliveries 행 없음)
```

  잠금만 흉내 낸 `probe_hold.py`(다른 프로세스가 `BEGIN IMMEDIATE`를 15초 잡음): `call took 11.10s`, notice `로컬 전달 기록(deliveries) 실패: OperationalError`, 기록 0행.
- 영향: 회사 PC 첫 scan(수천 파일·PDF·HWP, 수십 분)이나 정기 scan 동안 두 클라이언트의 모든 호출이 11초씩 늦고(그동안 ping·다른 요청도 멈춤), 로컬 전달 기록(설계 §3의 2차 가시성)이 절반 넘게 빠진다. 응답 자체와 `delivered_sources`는 맞다.
- 제안: (택1 이상) ① scan의 트랜잭션을 파일 단위 또는 시간 기준(예: 0.5초)으로 짧게 하거나, 파싱을 트랜잭션 밖에서 하고 쓰기만 묶는다. ② serve 기록은 짧은 대기(예: `busy_timeout` 200 ms, 재시도 없이)로 시도하고, 실패한 행은 프로세스 메모리 큐에 두었다가 다음 호출·ticker에서 다시 쓴다(종료 시 남으면 stderr). ③ 테스트: 다른 프로세스가 쓰기 잠금을 15초 잡는 동안 호출 하나가 1초 안에 끝나고, 잠금이 풀린 뒤 그 호출의 `tool_calls`·`deliveries`가 생김.

### M3-2 (중간) 재사용된 `chunk_id`로 `get_snippet`이 다른 문서의 본문을 경고 없이 준다

- 근거: `chunks.id`는 `INTEGER PRIMARY KEY`(AUTOINCREMENT 아님, `store.py` 78행)라 가장 큰 id가 지워진 뒤 새 청크가 같은 id를 받는다. `search._hits`는 `expected` 텍스트 해시로 이를 막지만(M2-1), `snippet.by_chunk`는 id만 보고 그 행을 그대로 준다(`snippet.py` 120~140행). 설계 §2.3은 `chunk_id`를 "검색 hit의 조각"으로 정의한다.
- 재현(`probe_reuse2.py`): a.txt·b.txt scan·index → `search('브라보필드 일정')` hit `chunk_id 2`(b.txt) → b.txt 삭제·scan·index → z.txt 추가·scan·index → `get_snippet(chunk_id=2)`:

```
hit 2 b.txt 베타 고유어 브라보필드 일정
get_snippet(chunk_id=2) -> True z.txt ['제타 전혀 다른 새 파일 내용'] latest True []
```

- 영향: 대화 중에 받은 hit를 백그라운드 scan/index 뒤 펼치면 다른 문서 본문이 "그 hit"로 온다. 조각의 locator·`delivered_sources`는 z.txt를 정확히 가리키므로 출처 결속은 깨지지 않지만, 클라이언트 모델이 내용을 엉뚱한 hit에 붙일 수 있다(notice 없음).
- 제안: `get_snippet`에 선택 인자 `version_id`(hit에 이미 있음) 또는 `text_sha256`을 받아 다르면 `not_found`("이 chunk_id는 이제 다른 버전/텍스트를 가리킴 — locator로 다시 부르세요"); 도구 설명에 "chunk_id는 scan/index 뒤 바뀔 수 있음, 오래된 hit는 locator로". 근본책은 다음 마이그레이션에서 청크 id 재사용을 없애는 것(예: `meta`의 단조 카운터로 id 지정). 테스트는 위 재현 그대로.

### M3-3 (중간) 오류 봉투는 크기 상한을 거치지 않는다 — 클라이언트 입력을 되돌린 109,004자 응답

- 근거: `tools.fit`은 `ok:false`를 그대로 돌려주고(`tools.py` 228~229행), `server.handle`의 `snippet.NotFound` 메시지(`str(exc)`)는 클라이언트가 보낸 locator의 `unit_label`을 담는다(`snippet.py` 156행). `locator.check_unit`은 `sheet` 문자열·`columns` 목록의 길이를 제한하지 않는다(`locator.py` 139~144행).
- 재현(§1.2): `get_snippet(locator={…, "unit": {"kind":"sheet_cell","sheet":"S"*60000,"cell":"A1"}})` → `not_found`, 응답 60,117자; `{"kind":"cell","row":1,"columns":[1..19999]}` → 109,004자(메시지 108,932자). 설계 §4 "응답 전체 ≤ 40,000자"와 완료 확인 요청 "모든 도구·모든 입력"에 어긋난다. 본문 유출은 아니다(보낸 값을 되돌릴 뿐).
- 제안: `handle`의 마지막에 길이 보호 — 오류 메시지를 고정 상한(예: 300자)으로 자르거나 `NotFound`·`LocatorError` 메시지에서 클라이언트 값(단위 라벨)을 빼고 `doc` id·sha12만 둔다. 직렬화 결과가 `RESPONSE_MAX_CHARS`를 넘으면 무조건 `response_too_large`로 바꾸는 최종 검사를 두면 앞으로의 경로도 막힌다. 테스트: 위 두 입력 → 응답 ≤ 40,000자.

### M3-4 (중간) 이 PC의 앱 환경 `PYTHONPATH` 때문에 템플릿 그대로의 serve가 시작하지 못한다

- 근거 **[사실]**: 이 셸(Claude 앱 Code 탭 → claude.exe → 셸)의 프로세스 환경에 `PYTHONPATH=C:\Users\<USER>\AppData\Local\hermes\hermes-agent;…\hermes-agent\venv\Lib\site-packages`(Python 3.11 venv, `mcp 1.26.0`·`pydantic_core`·`numpy` 포함)가 있다. 사용자·시스템 영구 환경에는 없다(PowerShell `[Environment]::GetEnvironmentVariable('PYTHONPATH','User'/'Machine')` 빈 값) — 앱 프로세스가 물려준 값이다. 프로젝트 테스트 명령이 `env -u PYTHONPATH`인 이유이기도 하다.
- 재현: 그 환경 그대로 템플릿 명령을 실행하면

```
> printf '<initialize>' | WORKMCP_HOME=<tmp 홈> .venv/Scripts/python.exe -m workmcp serve
  File "…\hermes-agent\venv\Lib\site-packages\pydantic_core\__init__.py", line 8, in <module>
ModuleNotFoundError: No module named 'pydantic_core._pydantic_core'
exit=1
> … .venv/Scripts/python.exe -I -m workmcp serve        → initialize 응답 정상
> … PYTHONPATH= .venv/Scripts/python.exe -m workmcp serve → initialize 응답 정상
```

- **[추정]** Claude Code가 stdio 서버에 자기 환경 전체를 넘기면 Code 탭 연결(⑤)이 이 이유로 실패한다(Codex는 `env_vars` 허용 목록 방식이라 덜할 수 있음). 넘기지 않더라도 사용자 PC마다 `PYTHONPATH`·작업 폴더의 같은 이름 모듈이 서버 import를 바꿀 수 있다(회사 PC M5 위험).
- 제안: `doc/examples/mcp.json.example`·`codex-config.toml.example`의 `args`를 `["-I", "-m", "workmcp", "serve"]`로(격리 모드: `PYTHONPATH`·사용자 site·작업 폴더 무시, venv의 편집 설치는 그대로 동작 — 위에서 확인), README에 이유 한 줄, ⑤ 증거 문서 환경 표에 `PYTHONPATH` 유무 칸. `serve_smoke.py`와 serve 감사 테스트도 `-I`로 띄워 같은 명령을 검증.

### L1 (낮음) SDK가 `true`·`2.0`을 정수로 바꿔 우리 범위 검사를 지나친다

- §1.3: `limit: true` → limit 1, `limit: 2.0` → 2, `chunk_id: true` → chunk 1의 본문. pydantic 느슨한 모드가 먼저 변환해 `tools._int_in`의 `type(...) is int` 검사가 보지 못한다. 해는 작다.
- 제안: 도구 함수 인자를 `Annotated[int, Strict()]`(pydantic `StrictInt`)로 두거나 문서화.

### L2 (낮음) 파이썬 `print`의 버퍼 잔여는 종료 때 와이어로 나간다

- `serve_boom.py`(도구가 `print` + `os.write(1, …)` 후 예외): `os.write(1)`은 stderr로 갔지만 `print('STRAY-PRINT-FROM-TOOL')`은 **stdout 마지막 줄**로 나왔다 — SDK가 종료 때 fd 1을 되돌린 뒤 버퍼가 비워졌다. 우리 코드에는 stdout `print`가 없어(확인) 현재 영향 없음; 설계가 말한 "보조 안전장치"가 파이썬 수준 버퍼는 덮지 못한다는 사실.
- 제안: `server.main`에서 `sys.stdout = sys.stderr`(SDK가 전송에 쓰는 것은 자기 복제 fd라 무관 — 확인 필요) 또는 serve 감사에 "패키지 코드가 `sys.stdout`에 쓰지 않음" 정적 검사.

### L3 (낮음) `tool_calls.args_json.query_sha12`로 짧은 질의를 추측 확인할 수 있다

- 소금 없는 SHA-256 12자리라 사람 이름·과제명 같은 짧은 질의는 사전 대입으로 확인된다(DB는 PC 로컬이므로 위험은 작다). 설계 §3.3이 정한 것이라 계약 위반은 아니다.
- 제안: 홈마다 무작위 키(`meta`)로 HMAC, 또는 길이만 남김.

### L4 (낮음) `.mcp.json`·`.codex/` 추적 금지 테스트가 없다

- `.gitignore`는 동작하고 이력에도 없다(§1.9). 설계 §14.4 [제안]의 `test_fixture_rules.py` 한 줄("추적 파일에 `.mcp.json`·`.codex/config.toml` 없음")은 구현되지 않았다. `git add -f` 실수를 막을 장치가 없다.
- 제안: `git ls-files`(테스트 코드의 subprocess) 또는 `.git/index` 읽기로 한 줄 추가.

### L5 (낮음) index 뒤 옛 hit의 `chunk_id`는 안내 없는 `not_found`

- §1.6: `get_snippet(chunk_id=1)` → `{'code': 'not_found', 'message': 'chunk 1 not found'}`(같은 hit의 locator로는 옛 버전이 `latest:false`로 정상). 설계 §16이 `chunk_not_found` 안내를 M4로 넘겼으므로 계약 위반은 아니다.
- 제안: 메시지에 "scan/index 뒤 청크가 바뀜 — hit의 locator로 다시 부르세요"(M3-2와 함께).

### L6 (낮음) 삭제 → 클라우드 자리표시자(skipped) 전이는 이벤트가 없다

- `collect.placeholder`가 `deleted` 문서를 `skipped`로 바꿀 때 `document_events`를 남기지 않는다(`collect.py` 255~258행). 설계 부록 B가 `skipped`를 이벤트에서 뺐으므로 계약 위반은 아니며, 앞선 `deleted` 이벤트는 남는다. `recent_changes`만 보면 그 문서가 다시 보인 사실을 모른다.
- 제안: 그대로 두되 설계 부록 B에 한 줄, 또는 M4에서 `kind='skipped'` 추가 검토.

## 4. 확인했지만 지적하지 않은 것

- `fit`의 반복 직렬화(최악 500행 × 약 40,000자): 0.27~0.36초 — 수용.
- 긴 경로(Windows 장경로 사용 시 최대 32,767자)는 한 hit에 경로가 세 번(doc·locator·display) 실려 search가 hit 0으로 줄 수 있고 get_snippet은 `response_too_large`가 될 수 있다 — 설계 §4의 "한 조각도 못 싣는 경우"에 해당, 오류 형태가 맞다.
- 모델 로드(≈3.4 s) 동안 루프 정지 — 설계 §6.2·위험 #6에서 수용.
- R5 임계 0.49는 같은 합성 표본에서 고르고 평가했다(seed 7 holdout 0.946/0.000은 문서에 있음) — 신호측정 문서가 M5 재측정을 명시.
- `status`가 AppData 홈에서 호출마다 `home/tmp`에 마커를 썼다 지운다 — 홈 안 쓰기, 설계 §10.3대로.
- 오류 traceback(stderr)에 예외 메시지가 그대로 남는다(`serve_boom.py`: `ValueError: C:\secret\SENT`) — 설계 §8.1 "전체는 stderr"대로. 질의 문법 공격 38회에서 내부 예외 0이라 질의가 traceback에 실린 경우는 찾지 못했다.
