### 2.2 88098e0 — 정지 3 s 제한과 데이터 무결성

- **uvicorn 내부 의존.** `uvicorn/server.py`(0.54.0, lock `uvicorn==0.54.0`과 venv가 같음)를 보면 이렇다.
  - `serve()`가 `capture_signals()` 안에서 `_serve`를 돌린다.
  - `capture_signals`는 주 스레드에서 `signal.signal(sig, self.handle_exit)`를 설치한다.
  - `_serve` → `startup()` → `lifespan.startup()` 순서라서 lifespan 시작 때 `signal.getsignal(SIGTERM).__self__`가 그 `Server`다.
  - `shutdown()`은 `self.config.timeout_graceful_shutdown`을 **정지 때** 읽는다.
  - SDK 2.2.0의 lifespan은 `StreamableHTTPSessionManager.run()`에서 프로세스당 한 번 들어간다(`streamable_http_manager.py:156`). 그래서 `on_serve`도 한 번만 돈다.
  - sse-starlette 3.5.0도 같은 방법을 쓴다(`sse.py:100`).
  - 못 찾으면 `False` → stderr `graceful stop not bounded`. 이때는 이전처럼 무한 대기하고 systemd `TimeoutStopSec=20` 뒤 SIGKILL된다. 테스트 `test_serve_listens_before_the_model…`이 이 줄이 **없음**을 단언하므로, uvicorn을 올려서 내부가 바뀌면 테스트가 먼저 깨진다. 받아들일 만한 위험이다.
- **3 s 뒤 취소가 끊는 것.** uvicorn은 `server_state.tasks`(요청 태스크)에 `cancel()`을 보낸다. asyncio 취소는 다음 `await`에서만 효과가 있다.
  - push(`remote.py` `push_endpoint`): `await _body()`(쓰기 전) → `receive.apply`(동기, `await` 없음, 명시 BEGIN/COMMIT) → `JSONResponse` 전송.
    - 수신 중 취소 → 아무것도 쓰지 않음.
    - 전송 중 취소 → 배치는 커밋됐고 응답만 잃음. 수집기는 같은 배치를 재전송하거나 exit 6으로 끝나고, 다음 push가 상태 비교로 이어 간다. 서버 버전 대응은 내용 기준이다(`receive.py:486-524`). 이는 프로세스가 죽을 때와 같은, 이전부터 있던 동작이다.
  - 지식 쓰기: `handle`은 동기이고 `_settle_knowledge`로 커밋하거나 롤백한다. 응답 전송 중 취소되면 "기록됐는데 클라이언트는 모름"이 가능하다. 창은 응답 전송 시간(밀리초)뿐이고, 이전에도 SIGKILL·연결 끊김으로 같았다.
  - 연결은 `isolation_level=None`(`store.py:488`)이라 `await`를 가로지르는 암묵 트랜잭션이 없다.
  - 메모리 대기열의 호출 기록(`pending`)은 `close_log`가 마지막에 한 번 쓴다. 배포절차서 §8.1이 이 대기열만 잃을 수 있다고 밝힌다.
- **결론:** 3 s 제한은 SQLite 원자성을 해치지 않고, push 부분 적용은 재개된다.

### 2.3 88098e0 — 첫 의미 질의 약속(V-L4)

### 2.4 edf89fc — 공급망(M6-9)

- `requirements-build.lock.txt`: `setuptools==84.2.1` + sha256 하나. `pyproject.toml` `[build-system] requires = ["setuptools==84.2.1"]`와 같다(테스트로 고정). setuptools 84는 `bdist_wheel`을 내장하고 의존성을 vendoring하므로, 빌드 의존성은 이 하나로 **전부**다.
- `make_bundle.build_wheel`의 흐름은 이렇다.
  1. `sys.executable -I -m venv build-env`
  2. `pip install --only-binary=:all: --require-hashes --no-deps -r requirements-build.lock.txt`
  3. `pip wheel --no-deps --no-build-isolation --no-index`

  빌드 단계는 인덱스에 닿을 수 없다. 원문 출력 168·170행에서 `Using cached setuptools-84.2.1…` → `Successfully installed setuptools-84.2.1`가 `--require-hashes` 아래에서 나왔다. pip가 준 파일의 해시가 pin과 같았다는 뜻이다.

  - 별도로, VPS 배포절차서 B-4의 `pip install --upgrade "pip<26.2"`는 PyPI에서 pip를 **범위 지정·해시 없이** 받는다. 이번 diff 밖이고 이전부터 있던 것이다(M6-3-3에 함께 적음).
- **덮지 않는 경로.** 운영 서버 배포(B-4 3번째 줄 `pip install --no-deps ./Motive_work`)와 수집기 온라인 설치(README 2단계, 안내서 §4 온라인)는 빌드 격리를 켠 채 `setuptools==84.2.1`을 버전으로만 받는다. #20이 "온라인 `pip install --no-deps .`도 같음"이라 적었는데, #27은 묶음 경로만 고쳤다(M6-3-3).
